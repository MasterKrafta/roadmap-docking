## Проверки проекта
Проверки выполняет пользователь в своём локальном окружении. Агент не имеет доступа к локальному терминалу пользователя и не должен пытаться запускать проверки самостоятельно.
Основные команды, которые пользователь запускает по мере необходимости:
```bash
cargo fmt --all -- --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-features
cargo check --all-targets
```
Правила:
- После каждого логического изменения агент сообщает, что именно изменено и какие проверки следует выполнить, затем ждёт результатов от пользователя. Это правило также действует при последовательной декомпозиции файлов.
- Не заявляйте, что код компилируется или тесты проходят, пока пользователь не предоставил подтверждающий результат.
- Не пытайтесь запускать локальные команды через удалённые сервисы, GitHub Actions, API или другие обходные способы. Не отправляйте сетевые запросы для проверки доступности окружения.
- Если пользователь прислал ошибку компиляции или теста, внимательно прочитайте весь вывод, включая подсказки компилятора, и исправляйте конкретную причину.
- Если проверка не пройдена, не переходите к следующему пункту работы до устранения ошибки и получения нового результата от пользователя.
## Стиль кода
- **Форматирование:** соблюдайте форматирование Rust через `rustfmt` (`cargo fmt`). Не форматируйте код вручную и не меняйте `rustfmt.toml` без запроса. Запуск команд форматирования и проверок выполняет пользователь.
- **Именование (RFC 430):**
  - `snake_case`: функции, переменные, модули, крейты.
  - `UpperCamelCase`: типы, трейты, варианты `enum`.
  - `SCREAMING_SNAKE_CASE`: константы и `static`.
- **Геттеры:** для простых геттеров предпочитайте имена без префикса `get_`: `name()`, а не `get_name()`. Соблюдайте существующий стиль публичного API и не переименовывайте методы без необходимости.
- **Конвертации:**
  - `as_*` — представление или преобразование, обычно без передачи владения.
  - `to_*` — преобразование, создающее новое значение или владеющий результат.
  - `into_*` — преобразование с передачей владения исходным значением.
  - Учитывайте общепринятый смысл префиксов и не используйте их произвольно.
- **Публичный API:** следуйте [Rust API Guidelines](https://rust-lang.github.io/api-guidelines/) и существующим соглашениям проекта.
- **Итераторы:** предпочитайте итераторы ручным циклам с индексами, когда это делает код понятнее и безопаснее. Не усложняйте код ради формального следования этому правилу.
- **Параметры:** если владение не требуется, предпочитайте `&str`, `&[T]`, `&Path` вместо `&String`, `&Vec<T>`, `&PathBuf`.
## Организация реализаций типов
- **Один inherent `impl Type { ... }` на файл:** это правило действует при любом написании и изменении кода, а не только при декомпозиции существующих файлов.
- В одном файле допускается не более одного блока inherent `impl Type { ... }` — блока обычных методов конкретного типа (`struct` или `enum`). Все обычные методы этого типа должны находиться в одном таком блоке; не распределяйте их по нескольким `impl Type`.
- Несколько связанных `struct` и `enum` могут находиться в одном файле, если собственный inherent `impl` нужен только одному из них. Типы, которым не нужен собственный inherent `impl`, можно оставить рядом.
- Если другому типу в этом же файле понадобятся собственные обычные методы, вынесите этот тип вместе с его inherent `impl` в отдельный файл. При выборе границ файлов сохраняйте смысловую связность и не создавайте искусственные модули для несвязанных с задачей мелочей.
- Реализации трейтов вида `impl Trait for Type { ... }` не считаются inherent `impl` и сами по себе не нарушают это правило.
## Размер файлов и структура модулей
Эти правила действуют с самого начала работы. Не пишите большой файл с намерением разделить его позже, но и не дробите связанный код на множество мелких файлов ради формального соблюдения размеров. **Сначала определяйте ответственность модуля, затем выбирайте его размер и структуру.**
- **Размер файла:**
  - Ориентир — примерно 600–700 строк на файл.
  - При достижении 800 строк остановитесь и оцените структуру: действительно ли файл выполняет несколько независимых обязанностей и можно ли выделить осмысленные модули.
  - Файлы больше 1100 строк без явного разрешения пользователя не создавайте. Если существующий файл уже такого размера, сначала предложите обоснованный план декомпозиции.
  - Не разделяйте файл автоматически только из-за количества строк. Если модуль имеет единую ответственность, а разделение ухудшит читаемость и навигацию, сохраните его целостность и объясните решение.
  - Не объединяйте несвязанные подсистемы в один большой файл ради уменьшения количества файлов.
- **Одна ответственность — один модуль.**
  - Модуль должен представлять понятную предметную область или связанную группу операций, а не отдельную функцию.
  - Не создавайте production-файл ради одной функции по умолчанию. Небольшие вспомогательные функции оставляйте рядом с вызывающей логикой, если у них нет самостоятельной ответственности, отдельного типа или API, независимого алгоритма либо реального повторного использования.
  - Тесно связанные операции объединяйте в тематические модули. Например, открытие, закрытие и операции с вкладками могут находиться вместе, если образуют единый жизненный цикл панелей.
  - Не создавайте множество файлов с именами отдельных действий только ради разделения кода на мелкие части.
  - Перед разделением перечислите назначение предполагаемых модулей и объясните, почему эти границы упрощают понимание кода.
- **Функции и тесты:**
  - Ориентир для функции — до 50–60 строк. При превышении 100 строк обязательно пересмотрите её структуру и ответственность.
  - Не разбивайте функции механически на множество вспомогательных функций. Выделяйте части, когда это улучшает читаемость, устраняет повторение или создаёт самостоятельную операцию.
  - Тесты в `#[cfg(test)] mod tests` входят в общую длину файла.
  - Не переносите тесты в отдельный `tests.rs` автоматически из-за размера. Выносите их, если это действительно улучшает навигацию и организацию тестов.
  - Сохраняйте существующие тесты при декомпозиции и проверяйте, что они продолжают покрывать прежнее поведение.
- **Структура файлов и каталогов:**
  - Не складывайте предметную логику в `main.rs` и `lib.rs`. В них должны оставаться точка входа, объявления модулей, реэкспорты и минимальная инициализация.
  - Если крупный модуль действительно нужно разделить, используйте понятную структуру, например `network.rs` и каталог `network/` с отдельными тематическими модулями.
  - Не используйте `mod.rs`, если этого не требуют соглашения проекта или особенности существующей структуры.
  - Обычно достаточно 2–3 уровней вложенности каталогов. Не создавайте лишнюю иерархию без необходимости.
  - Не создавайте отдельный файл для каждой структуры. Связанные типы, их `impl` и относящиеся к ним вспомогательные элементы обычно держите вместе.
  - Выносите общие типы, ошибки и константы в отдельные модули, только если у них действительно есть самостоятельная или разделяемая ответственность.
  - Выделяйте отдельные крейты в workspace, когда для этого есть реальная архитектурная причина: независимое использование, отдельная граница зависимостей или необходимость изоляции. Не создавайте крейты только ради дополнительного разделения.
- **Планирование новой функциональности:**
  - Если новая функциональность затрагивает несколько файлов или модулей, сначала предложите структуру файлов: перечислите предполагаемые файлы и кратко укажите назначение каждого.
  - Для небольшой локальной правки отдельный план структуры не требуется.
  - Не создавайте новые модули до определения их ответственности и связей с существующим кодом.
- **Разделение существующего файла:**
  - Выполняйте декомпозицию отдельным логическим изменением, по возможности отдельным коммитом, без изменения поведения.
  - Сначала переносите код как есть, сохраняя логику, видимость, импорты и тесты. Поведенческий рефакторинг выполняйте отдельным шагом.
  - Разделяйте код постепенно: один законченный пункт за раз.
  - Сохраняйте существующий публичный API. При необходимости используйте `pub use` или совместимые обёртки, чтобы внутреннее перемещение кода не ломало внешний интерфейс.
**Главный принцип:** структура должна помогать понимать и сопровождать код. Предпочитайте несколько цельных тематических модулей множеству микрофайлов. Размер — ориентир для анализа, а не повод автоматически дробить функции или объединять несвязанные обязанности.
## Обработка ошибок
- **Обработка ошибок:** используйте `Result` и оператор `?`, когда ошибку нужно вернуть вызывающему коду. Не используйте панику как обычный способ обработки ожидаемых ошибок.
- **Паники и потенциально аварийные операции:** `unwrap()`, `expect()`, `panic!`, `unreachable!` и индексацию, способную вызвать панику, разрешено использовать:
  - в тестах, примерах и бенчмарках;
  - в рабочем коде, когда корректность операции гарантирована проверяемым инвариантом, это обосновано комментарием и альтернативная обработка не нужна.
  - Не используйте эти конструкции вместо нормальной обработки ошибок или проверки входных данных.
- **Типы ошибок:**
  - В библиотечных крейтах предпочитайте типизированные ошибки. Используйте `thiserror`, если он уже доступен в проекте или его добавление согласовано.
  - В бинарных крейтах для обработки ошибок на границе приложения допустим `anyhow` с контекстом, например `.context("что пытались сделать")`, если он уже доступен или согласован.
  - Следуйте существующим соглашениям проекта и не добавляйте зависимости без согласования.
- **Не игнорируйте ошибки:** не используйте `let _ = fallible();` для подавления ошибки без объяснимой причины. Если ошибку намеренно допускается проигнорировать, укажите причину в комментарии или явно обработайте результат.
- **Сообщения об ошибках:** пишите с маленькой буквы, без точки в конце и с полезным контекстом, позволяющим понять, что не удалось и при какой операции. Сохраняйте единый стиль сообщений в рамках проекта.
## Владение и производительность
- **Владение и `.clone()`:** не добавляйте `.clone()` только ради устранения ошибки компиляции. Сначала проверьте владение, заимствования и времена жизни. При этом не усложняйте код ради устранения дешёвого и оправданного клонирования.
- **Совместное владение и изменяемое состояние:** не используйте `Rc<RefCell<_>>` или `Arc<Mutex<_>>` только для обхода ограничений borrow checker. Применяйте их, когда это обосновано архитектурой, и учитывайте стоимость синхронизации и сложность управления состоянием.
- **Оптимизация:** не оптимизируйте преждевременно. Сначала обеспечьте корректность, понятность и простоту кода. Оптимизируйте на основании измерений и выявленных узких мест, а не предположений.
- **Аллокации и горячие пути:** избегайте ненужных выделений памяти и копирований в критичных по производительности участках, особенно если код часто выполняется. Не ухудшайте читаемость ради сомнительной экономии без подтверждённой необходимости.
## Unsafe
- **По умолчанию:** сохраняйте `#![forbid(unsafe_code)]`, если он уже установлен для крейта. Не ослабляйте ограничение и не добавляйте `unsafe` без явного согласования.
- **Если `unsafe` необходим и согласован:**
  - ограничьте небезопасный код минимальным участком;
  - непосредственно перед блоком или операцией добавьте комментарий `// SAFETY: ...`, объясняющий конкретные инварианты, гарантии безопасности и основания, по которым операция корректна;
  - добавьте тесты, проверяющие соответствующие инварианты и граничные случаи;
  - по возможности проверьте код с помощью Miri: `cargo +nightly miri test`, если инструмент доступен и тесты совместимы с ним.
## Зависимости
- **Согласование:** не добавляйте новые зависимости без предварительного согласования. Сначала объясните, зачем нужна зависимость, и рассмотрите альтернативы, включая стандартную библиотеку и уже используемые в проекте библиотеки.
- **Оценка:** перед добавлением оцените поддержку и актуальность библиотеки, лицензию, размер дерева зависимостей, дополнительные транзитивные зависимости и необходимые функции (`features`).
- **Добавление:** рекомендуйте `cargo add` как предпочтительный способ добавления зависимости. Указывайте только необходимые `features` и проверяйте итоговые изменения в `Cargo.toml` и `Cargo.lock`, включая согласованность версий в workspace; команды выполняет пользователь в своём локальном окружении.
- **Обновления:** не выполняйте мажорные обновления существующих зависимостей без отдельного согласования. Не меняйте версии и `features` без необходимости для текущей задачи.
- **Предварительно одобренные библиотеки:** `serde`, `thiserror`, `anyhow`, `tracing`, `tokio` (если проект использует асинхронность), `clap` (для CLI). Этот список не означает, что их нужно добавлять автоматически. Если библиотека отсутствует в проекте, согласуйте её добавление в соответствии с правилом выше.
## Актуальность API
- **Проверка API:** не выдумывайте методы, типы и сигнатуры. Если не уверены в API библиотеки, проверьте документацию соответствующей версии или доступные исходники в `~/.cargo/registry`. При необходимости предложите пользователю открыть документацию через `cargo doc --open`.
- **Версии:** сверяйтесь с версиями зависимостей в `Cargo.lock` и настройками workspace. Не переносите API и примеры из документации другой версии без проверки совместимости. Это особенно важно для библиотек с заметными изменениями API между версиями, например `tokio`, `axum`, `clap`, `sqlx` и `reqwest`.
- **Нестабильные возможности:** не добавляйте `#![feature(...)]` и другие нестабильные возможности Rust без явного согласования.
## Асинхронный код (если применимо)
- **Блокирующие операции:** не выполняйте блокирующие операции в async-задачах, если они могут надолго остановить выполнение других задач рантайма. Для подходящих блокирующих операций используйте `spawn_blocking` или другой обоснованный механизм.
- **Блокировки:** не удерживайте `std::sync::Mutex` и другие блокировки, не предназначенные для удержания через `.await`, во время ожидания. Удерживайте блокировку только на необходимом участке кода; async-блокировку допускается удерживать через `.await`, только если это осознанно требуется архитектурой и не создаёт риска взаимной блокировки.
- **Сеть:** для сетевых операций предусматривайте таймауты, корректную обработку ошибок и отмену, если это поддерживается используемым API.
- **Рантайм:** придерживайтесь рантайма, принятого в проекте. Если используется `tokio`, не добавляйте другой async-рантайм без явного обоснования и согласования.
## Тесты
- **Проверка поведения:** изменения поведения должны сопровождаться тестами, если их можно обоснованно покрыть автоматическими проверками. Исправление бага по возможности начинайте с теста, воспроизводящего проблему.
- **Модульные тесты:** размещайте рядом с тестируемым кодом, обычно в том же файле в `#[cfg(test)] mod tests`, если структура модуля и существующие соглашения проекта не требуют другого решения.
- **Интеграционные тесты:** размещайте в каталоге `tests/`, когда проверяется взаимодействие нескольких модулей или публичный API крейта.
- **Детерминированность:** делайте тесты независимыми от случайного времени, порядка выполнения и внешней сети. Для внешних сервисов используйте моки, заглушки или другие контролируемые тестовые зависимости.
- **Именование:** называйте тесты по проверяемому поведению, например `returns_error_on_empty_input`, а не `test1`.
- **Сохранение покрытия:** не удаляйте и не ослабляйте существующие тесты только для устранения ошибок сборки или прохождения проверок. Если тест необходимо изменить из-за намеренно изменившегося контракта, обоснуйте изменение и сохраните проверку актуального поведения.
## Документация
- Для публичных элементов обязательны doc-комментарии `///`; для модулей и крейтов `//!`.
- По возможности добавляйте примеры: они выполняются как doctest через `cargo test`.
- Если функция возвращает ошибку, документируйте условия её возникновения в разделе `# Errors`. Если функция может паниковать, опишите конкретные условия в разделе `# Panics`. Не добавляйте пустые разделы, если соответствующее поведение невозможно.
- Комментарии объясняют **почему**, а не **что** делает код.
- Изменили поведение: обновите README и CHANGELOG (если ведётся).
