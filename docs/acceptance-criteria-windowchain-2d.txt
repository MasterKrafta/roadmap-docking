КРИТЕРИИ ПРИЁМКИ WINDOWCHAIN В ДВУМЕРНУЮ СЕТКУ FLOATING-ОКОН
Проект: MasterKrafta/roadmap-docking
Источник плана: docs/plan-peredelki-windowchain-2d.txt
Ветка: main

НАЗНАЧЕНИЕ И ПОРЯДОК РАБОТЫ

Этот документ — единый чек-лист проверки реализации WindowChain 2D.
Пункты расположены по этапам исходного плана. Проверяем последовательно,
не перескакивая через этапы. После фактической проверки отмечаем пункт [x].
Если пункт не пройден, оставляем [ ] и записываем рядом сценарий и результат.

Важно:
- «Реализовано в коде» не означает «принято»: нужны локальная сборка,
  автоматические тесты и ручная проверка там, где они указаны.
- Сборку и тесты запускает пользователь в своём локальном окружении.
- Проверяем реальное поведение приложения, а не только наличие кода или теста.

======================================================================
0. ОБЩИЕ ИНВАРИАНТЫ И ПОВЕДЕНИЕ
======================================================================

[ ] Каждое Floating-окно остаётся самостоятельным: собственные
    FloatingGroupId, HWND/WindowId, Core Layout, содержимое, bounds
    и minimum size.
[ ] WindowGrid хранит только отношения между окнами, порядок их перемещения,
    Z-order и правила сохранения стыковки; он не вводит общие размеры строк
    или столбцов.
[ ] Стыковка целых окон не объединяет их Core-композиции. Каждое окно
    продолжает соответствовать отдельному FloatingGroup.
[ ] Работают все четыре направления стыковки целых окон: Left, Right, Top,
    Bottom.
[ ] Обычный внутренний Dock содержимого, Group и Tab не смешивается
    со стыковкой целых окон.
[ ] При вертикальном Drop ширина перетаскиваемого окна становится равной
    ширине конкретного окна-цели; целевое окно сохраняет свою ширину.
[ ] При вертикальном Drop не используется максимальная ширина всей сетки
    и не изменяются размеры остальных участников.
[ ] Если ширина целевого окна меньше Core minimum width переносимого окна,
    Drop отклоняется без изменения цели и без публикации новой связи.
[ ] Геометрия рассчитывается в согласованных физических client/frame
    координатах с учётом inset и DPI каждого HWND.
[ ] Верхнее окно перекрывает шапку нижнего через native Z-order; постоянное
    скрытие шапки нижнего окна не используется.
[ ] Перетаскивание за шапку любого участника перемещает всю связанную сетку
    одинаковым физическим смещением, сохраняя размеры и взаимное расположение.
[ ] Изменение правой/нижней границы перемещает только зависимую восточную/
    южную область; размеры соседних окон не меняются.
[ ] Повторные layout/reconcile при неизменных входных данных не вызывают
    дрейфа bounds или изменения топологии.
[ ] Ошибка валидации/геометрии не публикует частично изменённую сетку
    и не оставляет несогласованные Core/native bounds.

======================================================================
1. ЭТАП 1 — МОДЕЛЬ WINDOW GRID И ЧИСТАЯ ГЕОМЕТРИЯ
======================================================================

Автоматические проверки модели:

[ ] Существующая горизонтальная цепочка A-B-C сохраняет прежнее поведение.
[ ] Модель представляет A слева от B и A сверху B без обращения
    к GPUI Entity или NativeWindowOps.
[ ] Проверяются все четыре направления и согласованность обратных связей:
    Right/Left и Below/Above.
[ ] Объединение двух сеток сохраняет все внутренние связи обеих сеток.
[ ] Повторяющиеся FloatingGroupId, дублирующие связи и связь узла с самим
    собой отклоняются.
[ ] Некорректная циклическая/конфликтующая топология отклоняется без
    частичного изменения исходного состояния.
[ ] Удаление участника не оставляет висячих ссылок.
[ ] Удаление углового, среднего и связующего узла корректно обновляет
    структуру связей.
[ ] Существующая горизонтальная логика и её тесты сохранены без изменения
    поведения.

Результат этапа 1: модель WindowGrid проверена независимо от native-кода.

======================================================================
2. ЭТАП 2 — DROP В ЧЕТЫРЁХ НАПРАВЛЕНИЯХ
======================================================================

[ ] Два независимых Floating-окна соединяются слева и справа.
[ ] Два независимых Floating-окна соединяются сверху и снизу.
[ ] Перенос целого Floating-окна маршрутизируется в WindowGrid,
    а не в DockCommand::DockFloating.
[ ] Перенос содержимого сохраняет прежний сценарий: сначала создаётся
    отдельный FloatingGroup, затем его HWND присоединяется к целевой сетке.
[ ] При переносе существующей сетки в другую сетку переносятся все её связи,
    а не только захваченное окно; внутренняя топология источника сохраняется.
[ ] Если выбранная сторона уже занята, создаётся отдельная ветвь на этой
    стороне; окно не вставляется автоматически между существующими соседями.
[ ] Для Top/Bottom Drop ширина переносимого окна становится равной ширине
    конкретного окна-цели.
[ ] При этом ширина окна-цели не меняется.
[ ] Если ширина цели меньше minimum width переносимого окна, операция
    отклоняется без изменения целевого окна и исходной топологии.
[ ] Core Layout после стыковки по-прежнему содержит два отдельных
    FloatingGroup.
[ ] Внутренний Dock вкладок и групп продолжает работать как раньше.

======================================================================
3. ЭТАП 3 — ДВУМЕРНАЯ ГЕОМЕТРИЯ И ПЕРЕКРЫТИЕ
======================================================================

Автоматические/синтетические проверки:

[ ] Горизонтальная стыковка не изменилась относительно прежнего поведения.
[ ] NativeFrameGeometry учитывает outer/frame и client geometry,
    client origin/size, inset и scale factor.
[ ] Окно B размещается под A с перекрытием CompositionHeader
    в физических client-координатах.
[ ] Окно C размещается под B с таким же перекрытием.
[ ] Размеры и высоты B/C при расчёте положения не меняются.
[ ] Anchor-окно остаётся на месте при первоначальном соединении.
[ ] Ширина переносимого окна нормализуется по ширине конкретного окна-цели;
    ширина окна-цели и размеры остальных участников не меняются.
[ ] Если нормализованная ширина меньше Core minimum width переносимого окна,
    операция отклоняется до изменения WindowGrid.
[ ] Повторный расчёт одинаковых связей и размеров даёт те же bounds.
[ ] Расчёты корректны при разных scale factor, в том числе fractional DPI
    1.25x и 1.5x, и при разных client/frame inset.
[ ] При отсутствующем HWND, невалидных frame/client rect, переполнении
    или временно недоступных bounds сетка не публикуется частично.

Ручная проверка:

[ ] Перенос между мониторами с разным DPI не создаёт зазоров и смещения
    относительно реальных видимых границ окна.

======================================================================
4. ЭТАП 4 — Z-ORDER И ШАПКИ
======================================================================

[ ] Верхнее окно перекрывает шапку нижнего окна.
[ ] Левое окно получает приоритет перекрытия относительно правого.
[ ] Все шапки продолжают рендериться как обычная часть каждого FloatingHost;
    нижние шапки не отключаются отдельным постоянным флагом.
[ ] Верхняя/левая шапка остаётся доступной для перетаскивания всей сетки.
[ ] Z-order детерминирован и не зависит от порядка обхода HashMap.
[ ] Порядок повторно применяется после соединения окон.
[ ] Порядок повторно применяется после активации любого участника.
[ ] Порядок повторно применяется после перемещения всей сетки и Resize.
[ ] Порядок восстанавливается после reconcile и lifecycle reconnect host.
[ ] Повторный focus/activation не поднимает нижнее окно поверх верхнего.
[ ] Для изменения видимости шапки не пересоздаются FloatingHost или HWND.
[ ] Временный hide_header при native move не превращён в постоянное состояние
    членства в WindowGrid.

Автоматические сценарии Z-order:

[ ] A сверху B.
[ ] A слева B.
[ ] Вертикальная цепочка A/B/C.
[ ] Прямоугольная сетка и Т-образная сетка.
[ ] Активация каждого окна не инвертирует порядок.

======================================================================
5. ЭТАП 5 — ПЕРЕМЕЩЕНИЕ ВСЕЙ СЕТКИ
======================================================================

[ ] Перетаскивание за шапку A перемещает все окна сетки.
[ ] Перетаскивание за шапку B перемещает все окна сетки.
[ ] Перетаскивание за шапку C перемещает все окна сетки.
[ ] Для каждого HWND применяется одинаковое физическое dx/dy.
[ ] После перемещения сохраняются взаимные смещения, размеры и связи.
[ ] При свободном перемещении конечные bounds всех участников фиксируются
    одной native history transaction и одним Undo.
[ ] При Drop на другую Floating-сетку объединяются связи обеих сеток,
    но Core-композиции не сливаются.
[ ] Drop на участника той же сетки не меняет топологию и корректно фиксирует
    bounds всех участников.
[ ] При отмене/Escape восстанавливаются исходные native positions всех окон.
[ ] Undo/Redo не оставляет разрывов между окнами.
[ ] Поддерживаемый Drop целой сетки обратно на Main сохраняет существующий
    сценарий возврата Floating Columns в Main.

======================================================================
6. ЭТАП 6 — RESIZE ПО X И Y
======================================================================

Автоматические проверки геометрии и транзакций:

[ ] Изменение правой границы определяет восточную область, которую нужно
    сдвинуть.
[ ] Изменение нижней границы определяет южную область, которую нужно сдвинуть.
[ ] Смещения рассчитываются по фактическим физическим client/native bounds
    и scale factor каждого HWND.
[ ] Соседние окна получают только новые origin; их Size остаётся прежним.
[ ] Окна до изменяемого участника не перемещаются.
[ ] При Resize последнего участника в направлении соседей нет и другие окна
    не перемещаются.
[ ] При угловом Resize X/Y-смещения объединяются до формирования команд.
[ ] Один FloatingGroup не получает несколько конфликтующих наборов bounds.
[ ] Сдвиг соседей рассчитывается по фактической границе, принятой Core после
    применения minimum size, а не по необработанному значению HWND.
[ ] Primary Resize и зависимые Move/ResizeFloatingBounds остаются в одной
    native resize history transaction и одном согласованном event flush.
[ ] Для общего левого ребра отключается Left Resize окна, у которого слева
    есть сосед.
[ ] Для общего верхнего ребра отключается Top Resize окна, у которого сверху
    есть сосед.
[ ] Внешние правые и нижние границы остаются доступными для Resize.
[ ] Minimum size изменяемого FloatingGroup сохраняется; минимумы соседей
    не суммируются.
[ ] Не возникают циклы синхронизации HWND/Core.

Ручная приёмка:

[ ] Resize A по правой границе перемещает только окна справа от A.
[ ] Resize A по нижней границе перемещает только окна ниже A.
[ ] Размеры соседних окон после Resize не меняются.
[ ] Resize среднего окна не перемещает окна, расположенные до него.
[ ] Resize последнего окна не сдвигает другие окна.
[ ] Нижняя шапка остаётся перекрытой после изменения высоты верхнего окна.
[ ] Угловой Resize не создаёт двойного или конфликтующего смещения.
[ ] Проверены правая и нижняя границы в горизонтальной, вертикальной,
    прямоугольной и Т-образной конфигурациях.

======================================================================
7. ЭТАП 7 — ЖИЗНЕННЫЙ ЦИКЛ, ИЗВЛЕЧЕНИЕ И RECONCILE
======================================================================

Автоматические проверки:

[ ] Удаление среднего/вертикального узла корректно перестраивает связи.
[ ] Удаление нескольких подряд отсутствующих узлов корректно сокращает
    временный участок графа.
[ ] Удалённые участники не остаются в registry и не создают висячих ссылок.
[ ] Singleton не сохраняется как WindowGrid и остаётся обычным Floating-окном.
[ ] Кандидат прямого соединения бывших соседей не публикуется до проверки
    доступности native hosts и успешного расчёта полной геометрии.
[ ] При конфликте геометрии бывшие соседи остаются раздельными.
[ ] При временно недоступном HWND/frame операция откладывается до следующего
    reconcile, а не публикует частичное состояние.
[ ] После удаления участника оставшиеся многоконные компоненты выравниваются.
[ ] При объединении нескольких компонентов pending alignment anchors
    схлопываются к одному target anchor; конфликтующие проходы не запускаются.
[ ] Повторный reconcile идемпотентен.
[ ] Потеря/смена PanelWindow host помечает сетку для выравнивания.
[ ] После lifecycle reconnect восстанавливаются native Z-order и политика
    доступных общих Left/Top Resize edges.
[ ] DragHost handoff сохраняет HWND источника, пока у него остаётся содержимое.
[ ] Новый FloatingGroup создаётся отдельно и включается в целевую WindowGrid
    только после создания Core-группы.

Ручная приёмка:

[ ] Извлечение Tab из окна сетки не повреждает исходное окно и связи.
[ ] Извлечение Group из окна сетки не повреждает исходное окно и связи.
[ ] Закрытие окна из середины сетки корректно обрабатывается.
[ ] После закрытия/извлечения оставшиеся окна занимают ожидаемые места.
[ ] Undo/Redo после закрытия или извлечения восстанавливает согласованное
    состояние.
[ ] Escape/cancel во время переноса не оставляет изменённых bounds или связей.
[ ] Повторный reconcile после lifecycle-событий не вызывает дрейфа или
    повторного соединения уже связанных окон.

======================================================================
8. ЭТАП 8 — ПОЛНЫЙ РЕГРЕССИОННЫЙ ПРОГОН
======================================================================

Автоматическое покрытие чистых модулей:

[ ] Связи во всех четырёх направлениях.
[ ] Объединение двух сеток с сохранением внутренних связей.
[ ] Вставка нового участника между существующими соседями там, где сценарий
    модели это допускает.
[ ] Удаление углового, среднего и связующего окна.
[ ] Декомпозиция сетки после удаления соединителя.
[ ] Горизонтальные и вертикальные формулы с DWM inset/client offset.
[ ] Fractional DPI и разные client/frame inset.
[ ] Направленный Resize с сохранением размеров соседей.
[ ] Угловой Resize.
[ ] Стабильный native Z-order.
[ ] Повторный layout/reconcile не меняет рассчитанные bounds.
[ ] Duplicate members, disconnected graph, лишние/некорректные рёбра
    и конфликтующие связи отклоняются без частичного результата.
[ ] Неоднозначная граница присоединяемой WindowGrid отклоняется без изменения
    обеих исходных компонент.

Полный ручной регрессионный сценарий:

[ ] Два окна: A слева B.
[ ] Два окна: A справа B.
[ ] Два окна: A сверху B.
[ ] Два окна: A снизу B.
[ ] Три окна вертикально: A/B/C; шапки B и C перекрыты.
[ ] Три окна горизонтально: A/B/C; прежнее поведение не сломано.
[ ] Сетка 2x2 с независимыми размерами.
[ ] Т-образная сетка с независимыми размерами.
[ ] Перетаскивание всей сетки за шапку каждого участника.
[ ] Resize правой и нижней границ первого, среднего и последнего окна.
[ ] Угловой Resize.
[ ] Активация каждого окна по очереди; Z-order не инвертируется.
[ ] Вертикальный Drop: переносимое окно шире цели — переносимое окно
    сужается до ширины цели, цель не меняется.
[ ] Вертикальный Drop: переносимое окно уже цели — переносимое окно
    расширяется до ширины цели, цель не меняется.
[ ] В обоих сценариях вертикального Drop нижняя шапка полностью перекрыта;
    максимальная ширина всей сетки не вычисляется.
[ ] Разные DPI/мониторы.
[ ] Извлечение Tab/Group и закрытие окна из середины сетки.
[ ] Undo/Redo, Escape/cancel и повторный reconcile.
[ ] Обычный внутренний Dock Group/Tab между композициями продолжает работать.

9. ЭТАП 9 — THEMEMETRICS, DOCKMETRICS И ФОРМУЛЫ
======================================================================

Автоматические проверки:

[ ] ThemeMetrics.composition_header_height — единый источник высоты общей
    CompositionHeader для Main и Floating Composition.
[ ] ThemeMetrics.group_header_height и ThemeMetrics.tab_strip_height остаются
    независимыми метриками Group и Tab strip.
[ ] GPUI использует единый dock_metrics_from_theme(); dock-core не зависит
    от ui crate.
[ ] DockMetrics.column_header_height используется для CompositionHeader,
    резервирования Column, Core sizing/hit-test и WindowGrid geometry;
    Group header и Tab strip используют отдельные метрики.
[ ] Конвертер валидирует исходные ThemeMetrics и итоговые DockMetrics.
[ ] DockController::set_metrics() проверяет новую конфигурацию и текущий Layout.
[ ] Обновление метрик запрещено во время pointer/native move/native resize
    session и DragHost transfer.
[ ] Фактическая смена метрик увеличивает metrics_revision, сбрасывает
    rect/floating caches и публикует MetricsChanged.
[ ] Повторная установка тех же метрик является no-op и не публикует
    лишний MetricsChanged.
[ ] FloatingWindowManager получает MetricsChanged, запускает reconcile
    и повторное выравнивание каждой существующей WindowGrid.
[ ] После изменения метрик повторно применяются native bounds, Z-order
    и resize constraints.
[ ] Встроенный запуск, первичная синхронизация DockHost и preview Composition
    используют тот же GPUI-конвертер.
[ ] DockHost применяет исходную тему один раз и не перезаписывает
    последующие явные изменения через DockController::set_metrics().
[ ] Above/Below overlap проверен при высоте 12, 20 и базовом значении
    DockMetrics с разным DPI и inset.

Ручная приёмка:

[ ] Установить ThemeMetrics.composition_header_height = 12 px; проверить
    общую шапку и резервируемое пространство Column в Main/Floating.
[ ] Повторить проверку при 20 px.
[ ] Повторить проверку при 32 px.
[ ] Для каждого значения создать вертикальные связи Above и Below;
    зазора между перекрываемыми client-областями нет.
[ ] Изменить метрику при уже существующей WindowGrid через
    DockController::set_metrics(); существующие окна выравниваются заново,
    но размеры и связи не меняются.
[ ] После изменения метрики повторить Resize и активацию окон;
    Z-order и общие resize edges сохраняются.
