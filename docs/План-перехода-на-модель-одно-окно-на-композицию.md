# План перехода на модель «одна Floating Column — одно HWND»

Проект: `MasterKrafta/roadmap-docking`  
Ветка: `main`  
Дата: 19 ноября 2026 г.  
Статус: кодовая очистка этапа 8 внесена в `main`: постоянный Floating HWND представлен только `Column(NodeId)`, Main остаётся одним HWND, старые постоянные Header/Group host и их типы удалены. Reconcile, prune, native move/resize, DPI, Z-order и Column handoff оставлены на Column HWND. **Полная локальная ручная приёмка сценариев из раздела 7 ещё не подтверждена**, поэтому этап не объявляется окончательно принятым. Сборка и тесты агентом не запускались. Внутренняя горизонтальная граница Floating обслуживается правой native Resize-кромкой первой Column, отдельный Floating Axis::X SplitterView не используется.

> **Текущий архитектурный контракт имеет приоритет над ранними заметками этого плана.** Main — один постоянный HWND. Floating — один постоянный HWND на каждую Column; внутри него отображаются Header и вертикальный стек Group этой Column. Отдельных постоянных Header/Group HWND нет. Упоминания промежуточных `FloatingPartHost`, `DockWindowPart` и Header/Group окон в описании предыдущих этапов — только история миграции, не действующая спецификация. Для Group/PanelTab drag используется временный DragHost lifecycle.

> Имя файла сохранено от предыдущей редакции плана. Актуальная целевая модель — **Main в одном HWND, Floating — одно HWND на каждую Column**. Предыдущая модель «одно окно — одна Composition» больше не является целью.

## 1. Цель и выбранная модель

Зафиксировано следующее решение:

- **Main** остаётся одним нативным окном (один Main HWND). Все его Column и Group продолжают отображаться внутри этого окна как GPUI-компоненты.
- **Floating** использует отдельное нативное окно для каждой Column.
- Внутри Floating Column HWND находятся её Header, все вертикально расположенные Group, Tabs, PanelView и внутренние вертикальные Splitter.
- Горизонтальные связи между Floating Column HWND сохраняются через WindowGrid и синхронизируются с Core Layout.
- Для переноса отдельной Group или PanelTab используется временное окно без Column Header.
- При переносе всей Main DockArea создаётся по одному временному окну на каждую исходную Column. Например, Main с четырьмя Column и двумя Group в каждой создаёт **четыре временных окна**, а не двенадцать.
- В постоянном Floating-состоянии число HWND для одной Floating Composition равно числу её Column.


Пример:

```text
Main HWND
└── Composition
    ├── Column A
    │   ├── Header
    │   ├── Group A1
    │   └── Group A2
    ├── Column B
    │   ├── Header
    │   ├── Group B1
    │   └── Group B2
    └── Column C
        ├── Header
        └── Group C1

После переноса в Floating:

Floating Column HWND A     Floating Column HWND B     Floating Column HWND C
┌─────────────────────┐    ┌─────────────────────┐    ┌─────────────────────┐
│ Header              │    │ Header              │    │ Header              │
├─────────────────────┤    ├─────────────────────┤    ├─────────────────────┤
│ Group A1            │    │ Group B1            │    │ Group C1            │
├─────────────────────┤    ├─────────────────────┤    │                     │
│ Group A2            │    │ Group B2            │    │                     │
└─────────────────────┘    └─────────────────────┘    └─────────────────────┘
       └──────────────────── WindowGrid ────────────────────┘
```

Таким образом, четыре колонки с двумя группами в каждой — это четыре постоянных Floating HWND, а не отдельное окно на каждый Header и каждую Group.

Главная цель перехода — убрать необходимость синхронизировать нативный Resize между Header и Group одной колонки. Вертикальная структура колонки снова становится обычным внутренним GPUI layout, а отдельными нативными окнами остаются только колонки.

## 2. Архитектурные инварианты

### 2.1. Core Layout — единственный источник логической структуры

Core Layout продолжает описывать Composition и её содержимое:

```text
Composition / DockArea
└── Split (Axis::X)
    ├── Column
    │   ├── Group
    │   └── Group
    ├── Column
    │   └── Group
    └── Column
        ├── Group
        └── Group
```

- `Axis::X` — колонки рядом.
- `Axis::Y` — группы друг над другом внутри Column.
- Порядок Column, Group, размеры, ratios, minimum sizes и DropZone определяет Core.
- Main и Floating используют одну Core-модель. Различается только способ представления Column в нативных окнах.
- GPUI не создаёт второе независимое дерево Column/Group.
- Переносы и стыковка выполняются существующими Core-командами. Менять их семантику ради нового числа HWND нельзя без отдельного подтверждённого дефекта.

**Core Layout не переписывать и не заменять WindowGrid.**

### 2.2. WindowGrid — физическая связь окон Floating Column

WindowGrid не является логической сеткой Docking. Она отвечает за взаимное физическое расположение отдельных HWND и поведение связанных окон.

В новой модели:

- Main HWND не является участником WindowGrid для своих внутренних Column.
- Постоянный участник Floating WindowGrid — целое окно одной Column.
- Header и Group одной Column не являются самостоятельными участниками WindowGrid.
- Связанные Floating Column HWND должны сохранять физический порядок, соседство и согласованную геометрию, соответствующие Core Axis::X.
- WindowGrid не определяет Core-порядок колонок и не хранит вторую копию их ratios.
- Независимые Floating Composition могут существовать отдельно. Не объединять их в одну WindowGrid только потому, что они одновременно открыты.

Идентичность постоянного окна должна однозначно соответствовать Floating Column. Предпочтительный логический ключ:

```text
FloatingColumnKey = (FloatingGroupId, ColumnNodeId)
```

Если аудит подтвердит глобальную уникальность и стабильность Column NodeId на всём жизненном цикле, можно использовать существующую более простую идентичность. Не вводить новый тип только ради обёртки: сначала проверить текущие ID и реестр.

Текущие `WindowGridMember::Header(NodeId)` и `WindowGridMember::Group(NodeId)` должны быть заменены одним Column-level представлением. Конкретное имя варианта (например, `Column(NodeId)`) выбрать после проверки места, где доступен `FloatingGroupId`.

### 2.3. Типы окон целевой модели

**A. Main HWND**

Одно существующее главное окно. Отображает Main Composition целиком — все колонки и группы. В обычном состоянии не создаёт дополнительных HWND для своих Column.

**B. FloatingColumnWindow**

Постоянное нативное окно одной Floating Column. Оно содержит:

- Header этой Column;
- все её Group в Core-порядке;
- Group controls и GroupGrip;
- Tabs и PanelView;
- вертикальные Splitter между Group;
- DropZone, Preview и прочие локальные overlays.

Внутренние Group не должны превращаться в отдельные нативные окна.

**C. ColumnDragWindow**

Временное окно Column, используемое при переносе всей Main DockArea или набора колонок. Его содержимое совпадает с полноценной Column-презентацией, включая Header и все Group. Количество таких окон при переносе Main соответствует количеству переносимых Column, а не количеству Header/Group.

После успешного Drop в Floating эти окна могут быть повышены до постоянных FloatingColumnWindow без повторного монтирования PanelView. При Drop обратно в Main или Cancel временные окна закрываются, а состояние восстанавливается в Main.

**D. GroupDragWindow**

Временное окно без Column Header, предназначенное для переноса одной Group. Оно показывает только переносимую Group и не резервирует пустое место под Header.

При успешном Drop в существующую Column содержимое передаётся окну-получателю через безопасный handoff. При Drop на свободную область временное окно может быть повышено до FloatingColumnWindow новой самостоятельной Column: Header добавляется в ту же оконную поверхность, а не создаётся отдельным HWND.

Для PanelTab используется тот же временный путь, если вкладка отделяется от исходной Group.

## 3. Геометрия и Resize — обязательный предварительный этап

Переход нельзя начинать с массовой замены окон. Сначала нужно проверить текущие Core bounds, реальные HWND bounds и старый Resize-дефект.

### 3.1. Геометрическая связь Column и HWND

Для каждой Floating Column нужно однозначно определить:

- Core rect самой Column;
- область Header;
- область вертикального стека Group;
- клиентскую область HWND;
- внешние native bounds HWND;
- frame/client insets и DPI scale.

Не предполагать заранее, что Core Column rect уже включает Header. Проверить текущие расчёты и зафиксировать преобразование. Окно должно точно соответствовать своей Column-презентации, а Header не должен приводить к скрытой прибавке/потере высоты при передаче Group между Main и Floating.

Горизонтальные границы всех окон одной Floating Composition должны соответствовать Core-размерам Column и порядку Axis::X. Вертикальная высота и Y-позиция принадлежат отдельному HWND Column и не синхронизируются с соседними Column только из-за общей Floating Composition.

Внешние bounds Floating Composition определяются объединением bounds её колонок, но не становятся отдельным независимым источником размеров.

### 3.2. Зафиксированное поведение изменения размера

Это важная часть целевой модели, а не деталь реализации.

**Горизонтальные native Resize-кромки Floating Composition:**

- левая внешняя кромка первой Column меняет ширину первой Column;
- правая кромка первой Column — единственный внутренний горизонтальный handle: меняется только первая Column, а все следующие Column сдвигаются, сохраняя свои ширины;
- правая кромка последней Column — внешний правый Resize: меняется только последняя Column, если справа нет внешнего WindowGrid-соседа;
- правые кромки промежуточных Column отключены;
- левая кромка Column отключена, если слева находится соседнее окно WindowGrid;
- горизонтальный Resize не пересчитывает пропорционально ширины внутренних Column.

Это намеренно не Main-style Splitter между произвольной соседней парой: физический handle внутренней границы закреплён за правой кромкой первой Column.

**Верхняя или нижняя граница отдельной Floating Column:**

- изменяется только высота и/или Y-позиция HWND, за кромку которого тянут;
- соседние Column той же Floating Composition сохраняют свои собственные высоты и Y-позиции;
- Core пересчитывает вертикальную раскладку Group только выбранной Column по её фактическому native viewport;
- внутренние Axis::Y Splitter остаются Core/GPUI-элементами внутри этого Column HWND;
- связи WindowGrid с отдельными внешними Floating Composition сохраняют свою направленность: при необходимости сдвигается только затронутая ветвь, но соседние Column текущей Composition не растягиваются.

**Внутренняя горизонтальная граница Floating Column:**

- представлена правой native Resize-кромкой первой Column;
- Core меняет ширину только первой Column;
- все последующие Column перемещаются на принятую разницу, сохраняя собственные ширины;
- отдельный `SplitterView` между окнами не создаётся;
- Core ratios и minimum sizes остаются единственным источником логической геометрии.

**Внутренний Splitter Axis::Y между Group:**

- остаётся внутри одного FloatingColumnWindow;
- меняет только вертикальные размеры соседних Group в Core;
- не вызывает native resize HWND и не создаёт дополнительных окон.

Если существующая реализация задаёт другой подтверждённый контракт для внутреннего Axis::X Splitter, на Этапе 0 нужно записать его явно. Не менять UX Splitter случайно в процессе переноса оконной модели.

### 3.3. Два направления синхронизации

Native HWND → Core:

```text
Изменение HWND / интерактивный Resize
    ↓
Native client bounds
    ↓
DPI + frame/client insets
    ↓
Core Column bounds / Core resize command
    ↓
Пересчёт Column, Group и Splitter rects
    ↓
Обновление содержимого FloatingColumnWindow
```

Core → Native HWND:

```text
Core DockCommand / Drop / изменение layout
    ↓
Новые bounds и размеры Column
    ↓
FloatingWindowManager reconcile
    ↓
WindowGrid согласует соседние окна при необходимости
    ↓
Атомарное обновление native bounds затронутых HWND
    ↓
Обновление GPUI viewport
```

Не допускать цикла, в котором изменение HWND обновляет Core, а reconcile тут же записывает назад устаревшие bounds.

### 3.4. Native Resize session

Проверить существующие механизмы:

- `NativeResizeSession`;
- `sync_native_resize_bounds`;
- `apply_native_resize_bounds`;
- `sync_window_bounds`;
- `core_bounds_from_native_window`;
- `DockCommand::ResizeFloatingBoundsFromEdge`;
- `DockGeometry`;
- существующие Core операции изменения Axis::X boundary.

Нужно выяснить, какие из них можно сохранить без PanelId-host lookup и без привязки к отдельным Header/Group HWND.

Во время системного интерактивного Resize:

1. Зафиксировать исходные Core bounds и начать resize session.
2. Не позволять reconcile записывать старые размеры поверх HWND, пока ОС выполняет Resize.
3. Принимать актуальные native client bounds и переводить их в Core logical units.
4. Для внешнего edge resize обновлять только соответствующую крайнюю Column по правилам выше.
5. Для верхней/нижней кромки обновлять только viewport выбранной Column; общие стыки WindowGrid должны передавать Resize соседнему HWND и не менять высоты соседних Column.
6. Для внутренней границы между Column обрабатывать пару соседних окон как одну Core split-операцию.
7. Учитывать Core minimum size и DPI.
8. На отпускании мыши завершить транзакцию и выполнить финальную сверку Core/HWND.

### 3.5. Аудит старого Resize-дефекта

По Git history и существующему коду восстановить, почему прежняя модель одного HWND на Floating Composition давала неверное поведение.

Записать в этот раздел перед началом реализации:

- конкретный сценарий воспроизведения;
- какую сторону окна тянули;
- сколько было Column и какие размеры/ratios имели;
- какие внутренние линии должны были оставаться неподвижными;
- фактическое поведение HWND;
- фактическое поведение Core bounds и внутренних Column rects;
- где появлялось устаревшее значение (например, кэш bounds или задержка native resize tick), если это подтвердится кодом;
- какие существующие resize helpers участвовали;
- какое поведение должно быть обеспечено новой моделью.

Не выдавать предположение о причине за установленный факт. Если дефект не удаётся восстановить по истории, сначала воспроизвести его вручную в приложении и записать результат. Этап 0 не закрывать без зафиксированного контракта и понятного способа проверки.

### Текущие ограничения, которые нужно учитывать

1. `FloatingPartHost` уже умеет представлять постоянную Column целиком; его Header/Group варианты и связанные typed host helpers остаются переходными путями для отдельных Group/Tab и handoff.
2. `FloatingWindowManager` содержит reconcile и resize переходы, исторически связанные с Header/Group members и PanelId-host.
3. `WindowGrid` уже содержит сложную логику native geometry, DPI, связей, Z-order и Resize. Не удалять её целиком до выяснения, какие механизмы нужны между отдельными Column HWND.
4. `DragHostSurface` уже отображает временную Group. Не создавать новый Group renderer параллельно существующему.
5. `PanelView` кэшируется DockController. Один и тот же экземпляр нельзя одновременно монтировать в source и destination HWND.
6. Core Column/Group identity должна оставаться стабильной на протяжении drag/handoff либо должна явно заменяться по существующим правилам Core. Не привязывать постоянное окно к случайному PanelId внутри Group.

## 5. Жизненный цикл и операции

### 5.1. Обычное состояние Main

- Все Main Column отображаются в одном Main HWND.
- Header, Group и Axis::Y Splitter остаются компонентами общего Main GPUI дерева.
- Постоянные FloatingColumnWindow для Main не создаются.
- WindowGrid не участвует в расположении Main Column.

### 5.2. Перенос всей Main DockArea в Floating

Для Main из четырёх Column:

1. Header/drag handle запускает перенос соответствующей Main DockArea по существующей семантике.
2. Для каждой переносимой Column создаётся одно временное ColumnDragWindow.
3. Каждое окно отображает свой Header и весь вертикальный стек Group.
4. Окна физически располагаются в том же порядке, что и Column в Core Axis::X.
5. Временные окна связываются WindowGrid или эквивалентным временным механизмом, чтобы сохранять взаимное расположение во время жеста.
6. Исходный Main получает корректное drag placeholder-состояние; PanelView не монтируется одновременно в двух окнах.
7. Drop в Floating фиксирует Core-операцию и повышает ColumnDragWindow до постоянных FloatingColumnWindow.
8. Drop обратно в Main или Cancel закрывает временные окна и восстанавливает исходное Main-состояние.
9. Ошибка handoff не должна оставлять часть Column в Main, часть во Floating и часть в невидимых HWND.

Четыре исходные Column должны приводить к четырём временным окнам независимо от количества Group в них.

### 5.3. Перемещение уже Floating-сетки

- Каждая Column остаётся отдельным HWND.
- Их порядок и относительные bounds поддерживаются WindowGrid и соответствуют Core Axis::X.
- Перетаскивание за Header любой Column запускает перемещение всей связанной WindowGrid; при отсутствии соседей это перемещение одного Column HWND. Состав перемещения берётся из `WindowGridRegistry::members_for`, а не из Core Composition. Сохранять эту семантику при следующих изменениях.
- Если перемещается вся сетка, её окна движутся с сохранением расстояний и общего порядка.
- Если перемещается одна Column, Core и WindowGrid должны корректно обработать разрыв/перестройку связи.
- Удаление или слияние Column должно обновлять обе модели без осиротевших HWND.

### 5.4. Перенос отдельной Group

1. GroupGrip запускает существующий Group drag.
2. Создаётся или переиспользуется один временный GroupDragWindow без Header.
3. В исходной Column остаётся корректный placeholder.
4. Остальные Group исходной Column перераскладываются внутри того же Column HWND; отдельные Group окна не создаются.
5. Drop в Main передаёт Group существующему Main renderer через Core.
6. Drop в существующую Floating Column передаёт Group в окно-получатель через handoff.
7. Drop на свободную область создаёт новую самостоятельную Floating Column: временный GroupDragWindow получает Column Header и роль постоянного FloatingColumnWindow.
8. Если исходная Column стала пустой, её постоянное окно закрывается после подтверждённого изменения Core.
9. Cancel/Escape/NoOp восстанавливает исходный Group, placeholder, bounds и PanelView.

Особенно проверить случай, когда в исходной Floating Column была только одна Group. Не создавать одновременно новое окно и оставлять старое пустое окно. На этапе реализации выбрать безопасный вариант: promotion/reuse существующей поверхности, если её lifecycle это допускает, либо handoff в одно временное окно с последующим закрытием source. Решение должно исключать двойное монтирование PanelView.

### 5.5. Перенос PanelTab

- Внутренний reorder вкладок остаётся локальным, если текущий путь уже работает.
- При отделении PanelTab используется временная поверхность без Column Header.
- При Drop в Group существующей Column вкладка передаётся целевому renderer.
- При Drop на свободную область создаётся самостоятельная Group/Column в FloatingColumnWindow по Core-операциям.
- Не создавать отдельное постоянное окно на Header или Group только ради завершения Tab drag.
- Сохранить focus, activation, cancel и запрет одновременного mount одного PanelView.

## Текущий прогресс реализации

В код уже внесены следующие части целевой модели:

- Общий renderer одной Column использует существующие `render_column_content`, Group и Header компоненты.
- Постоянные Floating hosts формируются по одному на каждую Core Column; WindowGrid связывает эти окна по Axis::X.
- Main DockArea drag создаёт одно временное окно на каждую переносимую Column и показывает в нём Header со всем стеком Group.
- При свободном Drop отдельной Group существующий GroupDragWindow может стать постоянным Floating ColumnWindow; это поддержано для источников Main и Floating.
- Handoff PanelView и выбор единственной кнопки закрытия перенесены на Column host.
- Добавлен базовый native Resize для постоянного Column HWND: сессия адресуется через `WindowGridMember::Column`, клиентские bounds переводятся в Core bounds и проходят через существующие `ResizeFloatingBoundsFromEdge` / `ResizeFloatingBounds`.
- После Core resize reconcile обновляет соседние Column HWND той же Floating Composition; HWND, которым в этот момент управляет Windows, защищён от обратной записи устаревших Core bounds.
- Native Column HWND размещаются вплотную: каждая следующая колонка сдвигается влево на накопленную ширину предшествующих Axis::X splitter gaps. Core rects не меняются и остаются источником размеров/хит-тестов; отдельный Core Splitter в Floating не рисуется.
- Внутренняя граница Axis::X в Floating обслуживается правой native-кромкой первой Column: Core меняет только её ширину через `ResizeFloatingBoundsFromEdge { edge: Left }`, а последующие Column сдвигаются, сохраняя собственные ширины. Отдельный `SplitterView` между окнами не создаётся.
- Native minimum size учитывает Core minimum Column (включая `metrics.min_column_width` и ограничения Panel); физическое схлопывание splitter gaps не меняет ширину содержимого.
- Верхний/нижний native Resize хранит отдельные высоту и Y-offset в записи конкретной Column HWND и передаёт их в `compute_floating_column_rects`; вертикальный Resize не записывает общую высоту в `FloatingGroup.bounds` и не растягивает соседние Column той же Composition.
- Правая native Resize-кромка последней Column включена как внешний Resize, когда справа нет внешнего WindowGrid-соседа; промежуточные правые кромки отключены. При DPI reconciliation сохранённый Y-offset пересчитывается из старого scale в текущий.
- При присоединении целой WindowGrid к Floating GroupEdge target Group преобразуется в содержащую её Column; `NativeMoveTarget::FloatingChain` использует `WindowGridMember::Column`, совпадающий с постоянной идентичностью окна.
- При миграции legacy FloatingComposition endpoints верхняя/нижняя граница выбирается по фактическим Y-offset и высоте каждой Column, включая сохранённый native viewport.
- Выравнивание WindowGrid различает внутренние связи одной Floating Composition и внешние связи между Composition: внутренние сохраняют относительные смещения по перпендикулярной оси, внешние выравнивают присоединяемые края. Это не схлопывает независимые Y-позиции Column при отложенном alignment.
- Native move за Header Floating Column проверяет активный источник по `WindowGridMember::Column`; GroupGrip по-прежнему проверяет `WindowGridMember::Group`. Исправлено расхождение между постоянным Column host и старой Header identity; добавлены регрессионные тесты на выбор member identity.
- При смене FloatingGroupId для существующего Column HWND reconcile обновляет registry owner, а `FloatingPartHost` перечитывает актуальные FloatingGroupId/Column из Core Layout без пересоздания окна.
- При Core merge ребро, которое из внешнего стало внутренним для одного FloatingGroup, не переносится как внешнее: оно восстанавливается из новой Column topology; добавлен регрессионный тест перехода двух владельцев в один.
- Добавлен регрессионный тест для `WindowGridRegistry::link_to_side` на объединение двух многоколоночных Column-сеток: он фиксирует сохранение внутренних рёбер и порядка обеих сторон для `WindowGridMember::Column`.
- GroupGrip из Main и Floating теперь использует одинаковые Core DropTarget для боковых зон другой Floating Composition; физический WindowGrid side-join оставлен для отделяемого PanelTab. Добавлен тест Floating → Floating GroupGrip по всем шести боковым зонам и трём видам целевого хоста.
- Floating-origin GroupDragWindow теперь использует тот же promotion/deferred-layout путь, что и Main-origin: при создании новой Floating Column временный HWND может стать её постоянным Column host; при существующем host сохраняется безопасный handoff.
- При старте GroupDragWindow передаётся `source_window_id` и берётся DPI исходного HWND (Main или Floating Column), а DPI Main используется только как fallback; добавлено покрытие приоритета исходного масштаба и fallback.
- Для подготовки Stage 7 `PanelTab` и `FlyoutPanel` также передают `source_window_id` в DragHost; общий выбор DPI использует масштаб исходного HWND, а Main оставляет fallback.
- Обновлён регрессионный тест PanelTab side-join: Floating Column → Floating Column покрывает все шесть зон; тест Main → Floating дополнительно проверяет роль постоянного `Column` host.
- Политика native кромок кэшируется отдельно и учитывает позицию Column и соседей WindowGrid: правая кромка включена у первой Column как внутренний handle и у последней — как внешний край, когда справа нет соседа; промежуточные правые кромки отключены. Для одиночной Column правая внешняя кромка также доступна только при отсутствии правого соседа. Левые, верхние и нижние общие кромки блокируются по соседям WindowGrid.
- Переведён внешний WindowGrid reflow на Column identity: существующий `shift_window_grid_after_resize` получает реальные bounds и frame metrics Column HWND, а смещение соседних окон агрегируется в один `MoveFloating` на каждую соседнюю Floating композицию.
- Grid reflow использует размер Column, принятый Core после применения minimum constraints, а не исходный WM_SIZING proposal.
- Обновлены Win32 hit-test unit tests для новой сигнатуры и добавлено покрытие занятой нижней кромки.

**Пока не завершено:** локальная сборка и ручная приёмка отсутствия зазоров/перекрытий между Column HWND; внутреннего Resize первой Column и внешнего Resize последней; независимого top/bottom Resize каждой Column; общих стыков WindowGrid; minimum clamp; DPI; Undo/Redo/Cancel; Drop/Split/Merge во время и после Resize. После подтверждения этих сценариев можно считать Этап 3 принятым. Переходные Header/Group оконные ветви пока нужны для GroupDragWindow/PanelTab и handoff — удалять их до завершения этапов 6–7 нельзя.

## 6. Этапы реализации

Каждый этап выполнять отдельно. После этапа пользователь проверяет приложение локально; к следующему этапу переходить после подтверждения результата. Проверки и сборки агентом не запускать.

### Этап 0. Аудит архитектуры, геометрии и Resize

**Цель:** до изменения кода зафиксировать реальный контракт размеров и окон.

Действия:

1. Проследить Core Layout от FloatingGroup до Column и Group rects.
2. Найти, как вычисляется высота Header и входит ли она в Core bounds.
3. Сопоставить Core rects с native client/outer bounds существующих Floating окон.
4. Проследить все текущие WindowGrid member types и их использование в move/resize/reconcile.
5. Проследить создание, обновление и закрытие Header/Group HWND.
6. Восстановить старый баг resize по истории/коду или воспроизвести его вручную.
7. Зафиксировать правила внешнего resize, внутреннего Axis::X resize и Axis::Y resize, изложенные в разделе 3.
8. Проверить уникальность и стабильность Column NodeId и связь с FloatingGroupId.
9. Зафиксировать фактическую семантику drag за Header Floating Column.

**Готово, когда:** существует точная схема Core rect → Column rect → client bounds → native bounds; зафиксированы resize-сценарии и текущая семантика перемещения; понятны места перехода с Header/Group identities на Column identity. Код на этом этапе не менять.

### Этап 1. Общая презентация одной Column

**Цель:** получить renderer, способный показать одну целую Column в одном окне.

Действия:

1. Найти существующую реализацию вертикального размещения Group и переиспользовать её.
2. Выделить общий Column-level presentation path: Header + все Group + Axis::Y Splitter + controls.
3. Не копировать Group rendering, tab layout, hit testing и drop overlay.
4. Обеспечить корректную геометрию клиентской области и Header по результатам Этапа 0.
5. Подключить Pointer input, GroupGrip, Tab drag, context menu, Escape, Drop overlay и splitter interaction.
6. Не менять обычное Main отображение и не переводить постоянные Floating окна на новую модель в этом этапе.
7. Проверить, что одна Column с одной Group и одна Column с несколькими Group выглядят и работают одинаково по правилам Core.

**Готово, когда:** одну Column можно отобразить в тестовой/временной поверхности; все её Group находятся в одном GPUI дереве и работают без отдельных Header/Group HWND. Main не изменился.

### Этап 2. Постоянный FloatingColumnWindow и reconcile

**Цель:** заменить постоянные Header/Group HWND на одно окно для каждой Floating Column.

Действия:

1. Ввести или адаптировать Column host, который отображает целую Column presentation.
2. Перевести постоянную идентичность окна на FloatingGroupId + Column NodeId (либо подтверждённый стабильный Column key).
3. В `FloatingWindowManager::reconcile` создавать ровно один постоянный HWND на каждую живую Floating Column.
4. Обновление состава Group внутри Column должно менять содержимое существующего HWND, а не создавать окна.
5. Добавление/удаление Column должно создавать/закрывать только HWND соответствующей Column.
6. Перенести WindowGrid registration на Column member.
7. Main оставить одним существующим HWND; не регистрировать его внутренние Column как отдельные нативные окна.
8. На этом этапе не удалять старые typed Header/Group host helpers, пока drag пути не переведены.

**Критерий количества окон:** Floating Composition с четырьмя Column и восемью Group создаёт ровно четыре постоянных HWND. Изменение числа Group внутри этих колонок не меняет число HWND.

**Готово, когда:** reconcile стабильно поддерживает по одному окну на Column; повторный reconcile не создаёт дубликатов; Main по-прежнему однооконный.

### Этап 3. WindowGrid и синхронизация Resize Column HWND

**Цель:** сделать геометрию набора окон эквивалентной Core Axis::X и устранить старые resize-дефекты.

Действия:

1. Перевести WindowGrid members с Header/Group на Column-level identity.
2. Удалить внутренние связи Header↔Group одной Column: они теперь GPUI layout внутри HWND.
3. Сохранить связь соседних Column HWND в Core-порядке Axis::X.
4. Оставить вертикальные bounds каждой Column независимыми; WindowGrid не навязывает соседним Column общую высоту.
5. Реализовать/адаптировать resize внешнего левого/правого края так, чтобы менялась только крайняя Column, а внутренние границы оставались неподвижными.
6. Для верхнего/нижнего края обновлять только native viewport выбранной Column и пересчитывать её Group stack без изменения соседних Column.
7. Использовать правую кромку первой Column как внутренний горизонтальный handle: менять только первую Column и сдвигать последующие с сохранением их ширин; правую кромку последней Column оставить внешним Resize.
8. Оставить Axis::Y Splitter полностью внутри Column HWND.
9. Перевести native resize session на Column identity, не используя PanelId как идентичность окна.
10. Обеспечить блокировку обратной записи старых Core bounds в HWND во время системного resize loop.
11. Сохранить DPI/frame-client conversion и minimum sizes.
12. Проверить reconcile после Split/Merge/Move/Drop/Undo/Redo и закрытия Column.
13. Проверить native resize в одной Floating Composition и в WindowGrid, связанном с другими Floating Composition; внешняя сетка должна сохранять свои физические отношения.
14. Проверить четыре внешние системные кромки и их передачу соседнему HWND: общий левый, правый, верхний или нижний стык не должен начинать Native Resize.
15. Проверить, что при Core minimum clamp соседние окна сдвигаются на принятую Core величину, а не на исходный размер WM_SIZING.

Не упрощать WindowGrid до линейной цепочки, пока аудит не докажет, что существующие сценарии не требуют других физических связей. Убирать только связи, ставшие ненужными из-за объединения Header и Group в одно окно.

**Готово, когда:** правила раздела 3 выполняются; все Column HWND соответствуют Core; resize одной горизонтальной кромки не двигает внутренние границы; верхний/нижний Resize меняет только выбранную Column; вертикальные Group Splitter не меняют размер HWND.

### Этап 4. Перенос всей Main DockArea — по одному временному окну на Column

**Цель:** убрать создание отдельных временных окон Header и каждой Group при переносе Main.

Действия:

1. Перевести Main DockArea drag на ColumnDragWindow.
2. Создавать один временный ColumnDragWindow на каждую переносимую Column.
3. В каждом окне отображать Header и все Group этой Column.
4. Сохранять Core-порядок и физическое взаимное расположение окон через временную WindowGrid.
5. Использовать существующие drag session, placeholders, DropZone resolver и rollback.
6. При успешном Drop в Floating повышать временные окна до постоянных FloatingColumnWindow без повторного mount PanelView.
7. При Drop в Main или Cancel закрывать все временные окна и возвращать содержимое в Main.
8. Исключить частичную фиксацию, при которой часть колонок уже стала постоянной, а часть осталась временной.

**Готово, когда:** перенос Main с четырьмя Column и любым количеством Group создаёт четыре временных окна; после успешного Floating Drop они становятся четырьмя постоянными окнами; отмена полностью восстанавливает Main.

### Этап 5. Перенос Floating Column и сохранение физической сетки

**Цель:** согласовать drag уже Floating окон с Column-level WindowGrid.

Действия:

1. Проверить перемещение всей Floating-сетки и перетаскивание отдельной Column согласно контракту Этапа 0.
2. Сохранить взаимные позиции при совместном перемещении окон.
3. При отделении одной Column обновлять Core Composition и WindowGrid без осиротевших связей.
4. При добавлении Column к другой Floating Composition правильно менять FloatingGroupId/Column ownership и постоянные host identities.
5. Сохранять native activation, Z-order, DPI и bounds при преобразовании состава.
6. Не менять Core DropZone и семантику Docking ради физического перемещения HWND.

**Готово, когда:** Floating Column можно перемещать и соединять существующими способами; количество окон и их взаимные границы всегда соответствуют актуальному Core Layout.

### Этап 6. Перенос отдельной Group через GroupDragWindow

**Цель:** сохранить Group drag без постоянных Group HWND.

Действия:

1. Использовать одну временную поверхность GroupDragWindow.
2. Для источников Main и Floating использовать одинаковую Core/DropZone семантику.
3. Оставлять placeholder в исходной Column.
4. При Drop в существующую Main/Floating Column передавать PanelView целевому renderer через безопасный handoff.
5. При свободном Drop повышать временную поверхность до FloatingColumnWindow новой Column с Header.
6. При исходной Column с одной Group корректно закрывать/reuse source HWND — без дубликата и пустого постоянного окна.
7. При Cancel/Escape восстанавливать исходные Core bounds, состав, focus и PanelView.

**Готово, когда:** Group переносится Main↔Floating и Floating↔Floating; после операции постоянные окна соответствуют числу Column, а временное окно всегда закрывается или становится одной новой Column.

### Этап 7. Перенос PanelTab

**Цель:** завершить переход всех drag типов на новую оконную модель.

Действия:

1. Сохранить внутренний tab reorder локальным.
2. При отделении PanelTab использовать временную поверхность без Header.
3. При Merge передавать вкладку существующей Group в целевом Main или FloatingColumnWindow.
4. При свободном Drop создать самостоятельную Group/Column через существующие Core operations и повысить временную поверхность до постоянной Column window.
5. Удалить специальные пути, создающие отдельные постоянные Header/Group HWND ради Tab drag.
6. Сохранить focus, activation, rollback и запрет двойного mount PanelView.

**Готово, когда:** PanelTab работает из Main и Floating во всех текущих направлениях; после завершения не остаётся дополнительных Header/Group HWND.

### Этап 8. Удаление старой оконной модели и документация

<badge label="Кодовая очистка внесена" color="success" />  
**Локальная ручная приёмка остаётся обязательной перед окончательным закрытием этапа.**

Внесено в `main`:

1. [x] Постоянные окна больше не создаются для Header(NodeId) или Group(NodeId). Физический Floating host всегда содержит одну Column целиком.
2. [x] Старый `FloatingPartHost` удалён. Полезные presentation/input механизмы сохранены в `FloatingColumnHost` и общих Column presentation helpers.
3. [x] Удалены `DockWindowPart`, `FloatingPartKind`, старые Header/Group snapshots, PanelId → HWND registry и старые Header/Group варианты WindowGrid.
4. [x] Floating reconcile строит и удаляет физические окна по Core Column: `FloatingGroupId → Column(NodeId) → HWND`.
5. [x] WindowGrid больше не содержит Header/Group members. Сохранён только короткоживущий `FloatingComposition(FloatingGroupId)` endpoint для переноса Core-level связи до регистрации реальных Column HWND; он не представляет физическое окно и мигрирует на Column members.
6. [x] Сохранены Column native move/resize, ограничения размеров, DPI, Z-order, pruning и восстановление WindowGrid-связей.
7. [x] Удалена отдельная постоянная Group HWND/native-move ветвь. Перенос всей Main DockArea использует временное окно на Column; Group и PanelTab продолжают использовать временный DragHost lifecycle.
8. [x] Документы со старой постоянной моделью Header/Group HWND помечены как устаревшие и ссылаются на этот план.
9. [x] В актуальной спецификации явно закреплено: Main — один HWND; Floating — один HWND на Column.

**Осталось для окончательного закрытия:** выполнить локальную сборку и всю ручную приёмку из раздела 7, особенно количество HWND, все направления GroupGrip/PanelTab, resize на нескольких DPI и объединение/разделение WindowGrid. До этого этап имеет статус «кодовая очистка внесена», а не «полностью принято».

## 7. Ручная приёмка

Проверки выполняются пользователем локально после соответствующего этапа. Не запускать cargo check/test/build агентом.

### 7.1. Количество и состав окон

- [ ] Main с 1 Column и 1 Group — один Main HWND.
- [ ] Main с 4 Column и 8 Group — один Main HWND.
- [ ] Floating с 1 Column и 1 Group — один Floating HWND.
- [ ] Floating с 1 Column и несколькими Group — один Floating HWND.
- [ ] Floating с 4 Column и 8 Group — четыре Floating HWND.
- [ ] Изменение числа Group внутри Column не меняет число постоянных HWND.
- [ ] Добавление/удаление Column создаёт/закрывает ровно соответствующее окно.
- [ ] Reconcile, повторный Drop и Undo/Redo не создают дубликаты или пустые окна.

### 7.2. Resize и геометрия

- [ ] Изменить внешний левый край Floating-сетки: меняется только левая Column, внутренние границы неподвижны.
- [ ] Изменить внешний правый край: меняется только правая Column, внутренние границы неподвижны.
- [ ] Изменить верхний/нижний край одной Column: меняется только её высота/позиция, соседние Column остаются на месте.
- [ ] Правая кромка первой Column меняет только её ширину и сдвигает следующие; промежуточные правые кромки отключены, правая кромка последней меняет последнюю Column.
- [ ] Изменить Axis::Y Splitter: меняются только соседние Group внутри одного окна.
- [ ] Каждая Column HWND сохраняет собственные вертикальные bounds независимо от соседних окон той же Floating Composition.
- [ ] Не появляются пустые полосы, перекрытия или щели между соседними окнами.
- [ ] Проверить resize за угол и минимальные размеры.
- [ ] Повторить на мониторах с разным DPI.
- [ ] Проверить Drop/Split/Merge во время и после изменения размеров.
- [ ] Проверить Undo/Redo и Cancel.

### 7.3. Перенос всей DockArea

- [ ] Main с четырьмя Column и восемью Group начинает перенос с четырьмя временными окнами.
- [ ] Каждое временное окно содержит Header и весь стек Group соответствующей Column.
- [ ] Временные окна сохраняют Core-порядок и взаимную геометрию.
- [ ] Drop в Floating превращает их в четыре постоянных FloatingColumnWindow.
- [ ] Drop обратно в Main закрывает временные окна и восстанавливает Main.
- [ ] Escape/Cancel закрывает временные окна и не теряет PanelView.
- [ ] Ошибка handoff не оставляет смешанное состояние Main/Floating.

### 7.4. Group и PanelTab

- [ ] GroupGrip: Main → Main.
- [ ] GroupGrip: Main → Floating.
- [ ] GroupGrip: Floating → Main.
- [ ] GroupGrip: Floating → другая Floating Column.
- [ ] GroupGrip: Floating → свободная область с созданием новой Column window.
- [ ] Group drag из Column с одной Group.
- [ ] Group drag из Column с несколькими Group, включая извлечение средней Group.
- [ ] PanelTab отделяется и возвращается без двойного mount.
- [ ] Внутренний reorder вкладок остаётся локальным.
- [ ] NoOp, Escape и неподдерживаемая цель восстанавливают исходное состояние.

### 7.5. WindowGrid и жизнь окон

- [ ] Перемещение Floating Column сохраняет ожидаемое поведение связанной сетки.
- [ ] Если перемещается вся сетка, расстояния и порядок Column сохраняются.
- [ ] При отделении Column её старые связи корректно удаляются.
- [ ] После Merge соседние HWND не перекрываются и не имеют щелей.
- [ ] Закрытие одной Floating Composition не затрагивает другие.
- [ ] Закрытие/создание Column не оставляет осиротевшие HWND и WindowGrid members.

## 8. Что нельзя делать в процессе перехода

- Не возвращаться к модели отдельных постоянных Header и Group HWND.
- Не создавать одно окно на каждую Group.
- Не превращать Main в набор постоянных Column HWND: Main остаётся одним окном.
- Не переписывать Core Layout и DropZone ради изменения количества HWND.
- Не делать WindowGrid вторым источником Core-порядка или ratios.
- Не удалять WindowGrid до переноса и проверки всех физических связей Floating Column.
- Не включать старый `FloatingHost` без аудита прежнего Resize-дефекта.
- Не менять одновременно рендеринг, drag lifecycle, WindowGrid и sizing в одном этапе.
- Не создавать новый renderer, если существующий `group.rs` или presentation helper можно переиспользовать.
- Не дублировать вычисления геометрии, hit testing и drop validation.
- Не монтировать один PanelView одновременно в двух окнах.
- Не запускать проверки агентом: локальные проверки выполняет пользователь после каждого этапа.

## Принцип выполнения

Сначала аудит и точный контракт Resize. Затем одна общая Column presentation, затем постоянные FloatingColumnWindow и WindowGrid. После этого перенос Main DockArea по одному временному окну на Column, затем GroupDrag и PanelTab. Старые Header/Group HWND удалять только после ручной проверки всех направлений переноса.

**Итоговый критерий:** Main всегда остаётся одним HWND. Каждая Floating Column — одно HWND, внутри которого находятся её Header и все Group. Core Layout задаёт логическую структуру и размеры; WindowGrid синхронизирует физические связи отдельных Floating Column окон.
