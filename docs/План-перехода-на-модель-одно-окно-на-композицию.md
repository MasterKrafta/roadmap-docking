# План перехода на модель «одно окно — одна Composition»

Проект: `MasterKrafta/roadmap-docking`  
Ветка: `main`  
Дата: 18 ноября 2026 г.  
Статус: планирование. Код не изменялся этим документом.

---

## 1. Цель перехода

Перейти от текущей модели, в которой Floating Composition разбита на отдельные нативные окна Header и Group, к более простой модели:

- одна Main Composition отображается в существующем Main HWND;
- одна Floating Composition отображается в одном постоянном Composition HWND;
- временное окно без Composition Header используется для переноса отдельной Group;
- при переносе всей Composition используется одно окно с полной композицией, а не отдельное окно для каждой Column и Group;
- все внутренние Column, Group, Header и Splitter отображаются как обычные GPUI-компоненты внутри соответствующего окна.

Пример: Floating Composition с четырьмя колонками и двумя группами в каждой — это **одно постоянное HWND**, а не двенадцать окон.

Это сознательный компромисс относительно Photoshop: мы сохраняем единую сетку и единое окно композиции вместо независимых нативных окон для каждого визуального элемента.

Главная цель — упростить оконную архитектуру, не потеряв логические операции Docking, DropZone, перенос содержимого, размеры и отмену операций.

## 2. Термины: две разные сетки и два типа окон

До начала изменений важно не смешивать логическую структуру Docking и физические связи HWND.

### 2.1. Core Layout — логическая сетка Docking

Это единственный источник истины для внутренней структуры и геометрии композиции:

```text
Composition / DockArea
└── Split (Axis::X)
    ├── Column
    │   ├── Group
    │   └── Group
    └── Column
        └── Group
```

- `Axis::X` — колонки рядом.
- `Axis::Y` — группы друг над другом.
- Header, Group, Splitter и Panel получают геометрию из Core.
- Main и Floating используют одну и ту же Core-модель и одинаковые правила внутреннего расположения.
- Отдельное GPUI-дерево колонок/групп создавать нельзя.

**Core Layout сохраняется. Его не откатывать и не переписывать ради изменения количества HWND.**

### 2.2. WindowGrid — физическая связь Floating-окон

`WindowGrid` не является сеткой колонок и групп внутри Composition.

Исторически она решала другую задачу: позволяла соединить несколько самостоятельных Floating Composition HWND, перемещать их совместно и сохранять взаимное расположение. Для этого в ней есть направленные связи, native frame/client geometry, DPI, Z-order, Resize и pruning.

При новой модели:

- WindowGrid не связывает Header и Group внутри одной композиции — они больше не отдельные HWND;
- Main не нуждается в WindowGrid для внутренних колонок и групп — всё находится в одном Main HWND;
- WindowGrid может остаться для связи **разных целых Floating Composition**, если сохраняем поведение нескольких физических Floating-окон, состыкованных между собой;
- её участником снова должна быть целая Floating Composition, идентифицируемая через `FloatingGroupId`, а не `Header(NodeId)` или `Group(NodeId)`.

Не удалять WindowGrid до отдельного решения и проверки сценариев нескольких независимых Floating Composition. Но не использовать её как второе дерево Core Layout.

### 2.3. Два типа окон

**A. CompositionWindow — окно с Composition Header**

Постоянное окно Floating Composition. Оно отображает целиком:

- Header каждой Column;
- все Column и Group;
- все Tab и PanelView;
- внутренние Splitter;
- DropZone и Preview.

Одна Composition — один HWND вне зависимости от числа колонок и групп.

Для Main роль CompositionWindow выполняет уже существующее главное окно.

**B. GroupDragWindow — временное окно без Composition Header**

Окно существует только для жеста переноса отдельной Group:

- показывает переносимую Group общим компонентом `group.rs`;
- не рисует Composition Header и не резервирует место под него;
- использует существующие PanelView и placeholder/handoff механизмы;
- следует за курсором и показывает DropZone цели;
- после завершения операции либо закрывается после handoff в CompositionWindow-получатель, либо переходит в роль постоянного CompositionWindow, если создаётся самостоятельная Floating Composition.

Это не означает, что нужно постоянно скрывать и показывать Header в одном и том же рендерере. У окон разные назначения и разные корневые представления. При promotion временного HWND меняется его роль/корневое содержимое целиком, а не флаг видимости шапки.

Для переноса целой Main DockArea используется один временный host с полной Composition-презентацией и Header. Нельзя создавать временное HWND на каждую Column или Group.

## 3. Самая важная нерешённая проблема — синхронизация размеров

Ранее мы уже пробовали отображать Floating Composition в одном HWND с условным скрытием/показом Header. От этой модели отказались в том числе из-за проблем с изменением размера окна относительно изменения размера композиции.

**Эту проблему нельзя считать решённой только потому, что мы снова используем старый FloatingHost.** До восстановления старого пути нужно отдельно выяснить и воспроизвести прежний дефект.

### 3.1. Два направления синхронизации

Нужно поддерживать оба направления без циклических обновлений.

**Направление 1: пользователь меняет размер нативного окна**

```text
Native HWND client bounds
    ↓
Преобразование в Core logical bounds (учёт DPI и frame/client insets)
    ↓
DockCommand::ResizeFloatingBounds / ResizeFloatingBoundsFromEdge
    ↓
FloatingGroup.bounds в Core Layout
    ↓
Пересчёт всех Column / Group / Splitter rects
    ↓
Повторный рендер Composition в том же HWND
```

Ожидаемое поведение: внутреннее содержимое композиции использует доступную клиентскую область окна. Изменение внешнего размера не должно оставлять старые размеры групп, обрезанное содержимое или свободные полосы.

**Направление 2: Core меняет размер или геометрию композиции**

```text
DockCommand / изменение состава Composition / изменение метрик
    ↓
Новые FloatingGroup.bounds и Core rects
    ↓
FloatingWindowManager получает канонические bounds
    ↓
Один атомарный native update позиции и размера HWND
    ↓
GPUI обновляет viewport и перерисовывает Composition
```

Примеры изменений, после которых окно должно согласоваться с Core:

- новая Column добавлена снаружи или сбоку;
- Group вынесена из композиции или вставлена в неё;
- композиция стала самостоятельной после GroupDrag;
- композиция слилась с другой или изменила свои границы;
- изменились метрики/масштаб DPI;
- восстановлены bounds после отмены операции или Undo/Redo.

Размер окна должен соответствовать **внешним bounds целой Floating Composition**, а не случайно выбранной Group или Header.

### 3.2. Разделить Resize окна и Resize внутренних Splitter

Это два разных взаимодействия:

- Resize внешней границы HWND меняет `FloatingGroup.bounds`. Core заново распределяет доступное пространство между внутренними элементами согласно правилам ratios/minimum sizes.
- Перетаскивание внутреннего Splitter меняет только Core ratios/размеры соседних Column или Group. Размер самого HWND не меняется, пока этого отдельно не требует операция изменения границ Composition.

Нельзя допускать, чтобы внутренний Splitter запускал native resize окна или чтобы обычное изменение размера HWND сбрасывало сохранённые внутренние пропорции.

### 3.3. Во время нативного Resize

Windows может менять HWND чаще, чем GPUI успевает сообщить об изменении bounds. Поэтому:

1. На старте Resize фиксируются исходные Core bounds и начинается resize session.
2. Пока ОС управляет интерактивным Resize, фактические HWND client bounds являются входом для Core.
3. Reconcile не должен записывать старые Core bounds обратно в HWND посреди resize-жеста.
4. Измерения HWND преобразуются с учётом DPI и frame/client insets.
5. Core применяет minimum size и принимает канонические bounds.
6. После отпускания мыши resize transaction завершается, а финальные Core bounds синхронизируются с HWND.
7. Изменение DPI при переносе между мониторами должно приводить к повторной проверке физического размера.

Нужно использовать существующие механизмы, если они подходят: `NativeResizeSession`, `core_bounds_from_native_window`, `sync_window_bounds`, `ResizeFloatingBoundsFromEdge`, `DockGeometry`. Но их текущие зависимости от PanelId-host и WindowGrid проверить и при необходимости заменить.

### 3.4. Обязательный предварительный аудит старого Resize-дефекта

До реализации однооконной модели нужно восстановить по Git history и старому коду, что именно ломалось в предыдущей реализации. Не предполагать причину.

В отдельной заметке в этом плане записать:

- точный пользовательский сценарий, при котором появлялся дефект;
- какое действие меняло размер: native edge resize, внутренний Splitter, Dock/Drop, изменение состава или promotion DragHost;
- что было ожидаемым размером HWND и Core Composition;
- что происходило фактически;
- какой источник bounds оказывался устаревшим;
- какой код в старом решении пытался синхронизировать размеры.

Если точный сценарий не удаётся восстановить из истории, не скрывать неопределённость: сначала проверить старый путь в приложении и зафиксировать наблюдение. Не считать этап закрытым без этой проверки.

### Важные наблюдения по текущей реализации

1. В `floating_host.rs` сохранился путь рендеринга целой Floating Composition.
2. В `floating_window_content.rs` сохранился рендер Columns, Groups, Splitters и CompositionHeader в одной поверхности.
3. Постоянный путь целого окна в `FloatingWindowManager::reconcile` сейчас фактически отключён: `next_hosts` и `desired_panels` создаются пустыми, а видимой моделью объявлены typed Header/Group members.
4. `FloatingHost` ещё содержит динамический `hide_header` и запрашивает его через `hide_floating_header`. В целевой модели постоянное CompositionWindow всегда рисует Header; этот флаг не должен определять архитектуру окон.
5. `FloatingWindowManager` уже содержит часть старой синхронизации bounds и native resize, но она связана с PanelId-host и содержит обработку связанного WindowGrid. Её нужно адаптировать, а не бездумно включать как есть.
6. `DragHostSurface` уже умеет отображать временную переносимую Group. Его можно развивать как GroupDragWindow вместо создания нового Group renderer.
7. Promotion текущего DragHost сейчас переводит временную поверхность в постоянный `FloatingPartHost`. Это нужно заменить promotion в целый CompositionHost.

## 5. Целевая модель жизненного цикла

### 5.1. Перенос всей Composition за Header

1. Main Header начинает drag с payload всей соответствующей Main DockArea.
2. Создаётся не более одного временного окна с полной Composition-презентацией, включая все её Columns, Groups и Header.
3. Все внутренние DropZone остаются результатом Core resolver.
4. При Drop в Floating выполняется существующая Core-команда, а временное окно становится постоянным CompositionWindow либо выполняется безопасный handoff в уже существующее окно целевой Composition.
5. При Drop в Main или отмене временное окно закрывается, а Main снова отображает актуальный Layout.
6. Никакие окна отдельных Header/Group не создаются.

Для перетаскивания существующей Floating Composition за её Header перемещается её единственный HWND. Внутренние элементы вместе с ним перемещаются автоматически.

### 5.2. Перенос отдельной Group

1. GroupGrip начинает перенос всей Group, а не отдельного PanelView.
2. Создаётся одно GroupDragWindow без Composition Header.
3. В исходной Composition на время переноса остаётся placeholder; источник и цель не должны одновременно монтировать один AnyView.
4. Если Drop направлен в Main или другую Floating Composition, Core выполняет существующую Split/Merge/Move команду.
5. PanelView передаются существующему окну-получателю через уже работающий handoff. GroupDragWindow закрывается после подтверждения detach/render.
6. Если Drop завершился на свободном рабочем столе и Core создал новую Floating Composition, GroupDragWindow становится её CompositionWindow. При promotion:
   - тот же HWND сохраняется, если GPUI позволяет безопасно заменить root view;
   - bounds окна приводятся к новым bounds всей Composition, включая её Header;
   - временная Group-only презентация перестаёт использоваться;
   - постоянный Composition renderer начинает отображать всю новую структуру.
7. Если операция отменена или Drop отклонён, исходное расположение и PanelView восстанавливаются; временное окно закрывается.

Нужно отдельно определить promotion для случая, когда GroupDragWindow был создан из Main и когда он был создан из Floating. Нельзя полагаться на старый прямой перенос отдельного Floating Group HWND: в новой модели такого постоянного Group HWND нет.

### 5.3. Перенос отдельной Tab

- Внутренний drag вкладки в том же TabStrip по возможности остаётся локальным и не создаёт HWND.
- Отделение вкладки использует существующий DragHost/PanelView handoff.
- Если вкладка после Drop образует самостоятельную Group/Floating Composition, временный HWND проходит тот же promotion pipeline, что и GroupDragWindow, с правильным итоговым Composition Header.
- Если вкладка сливается в существующую Group, сохраняется окно получателя, а временное окно закрывается только после подтверждённой передачи PanelView.

### 5.4. Стыковка Floating → Floating

- Перенос отдельной Group идёт через GroupDragWindow.
- Перенос всей Floating Composition идёт перемещением одного CompositionWindow.
- Core решает, меняется ли внутреннее дерево целевой Composition или создаётся новая Floating Composition.
- Если отдельные целые Floating Composition остаются физически объединяемыми в WindowGrid, меняются только связи между их Composition HWND.
- Внутренние Column/Group не добавляются как участники WindowGrid.

## 6. План реализации по этапам

Каждый этап ограничен небольшим набором связанных изменений. После каждого этапа пользователь выполняет локальную проверку. Следующий этап начинается только после подтверждения предыдущего. Сборки и тесты агентом не запускаются.

### Этап 0. Зафиксировать Resize-регрессию и контракты окон

**Цель:** выяснить, почему прежний однооконный путь не справлялся с изменением размеров.

**Действия:**

1. Проверить Git history до введения постоянных Header/Group HWND.
2. Найти старую реализацию `FloatingHost`, `FloatingWindowManager::reconcile`, native Resize и синхронизации Core bounds.
3. Сопоставить старый Resize с текущими `NativeResizeSession`, `sync_window_bounds`, `apply_native_resize_bounds` и `core_bounds_from_native_window`.
4. Записать конкретный сценарий старой ошибки в раздел 3.4 этого документа.
5. Утвердить идентичность трёх runtime-поверхностей: MainWindow, CompositionWindow и временная GroupDragWindow. Не вводить дополнительные постоянные окна на Column/Group.
6. Зафиксировать судьбу WindowGrid: связи только между целыми Floating Composition или полное удаление, если совместное движение отдельных Floating Composition больше не требуется.

**Основные файлы для чтения:** `floating_host.rs`, `floating_manager.rs`, `floating.rs`, `native_resize_session.rs`, `window_chain_geometry.rs`, `plan-peredelki-windowchain-2d.txt`, Git history.

**Готово, когда:** старый resize-дефект описан воспроизводимым сценарием и известен набор существующих механизмов, которые его должны предотвращать. Пока это не сделано, не менять lifecycle окон.

### Этап 1. Восстановить целостное Composition-представление

**Цель:** получить корректный renderer всей Floating Composition без переключения Header по флагу.

**Действия:**

1. Сверить `FloatingHost`, `FloatingWindowContent`, `DockCompositionView` и `MainDockView`.
2. Обеспечить один общий путь рендеринга внутренних Columns/Groups/PanelView/Splitters, не копируя расчёты геометрии.
3. Для постоянного Floating Composition Header всегда присутствует. Удалить зависимость композиционного рендера от `hide_floating_header`.
4. Обеспечить Pointer input, GroupGrip, Tab drag, context menu, Escape, Drop overlay и splitter interaction в пределах одного HWND.
5. Не менять пока количество создаваемых окон. На этом этапе проверяется только корректность полно-композиционного рендера в существующей поверхности.

**Готово, когда:** композиция с одной и несколькими Column/Group полностью отображается в одной поверхности, все внутренние controls работают, Header не исчезает самопроизвольно.

### Этап 2. Вернуть один постоянный HWND на Floating Composition

**Цель:** заменить reconcile отдельных Header/Group окон на reconcile целых Floating Composition.

**Действия:**

1. Перенести постоянную идентичность host с набора `Header(NodeId)`/`Group(NodeId)` на `FloatingGroupId`.
2. Установить ровно одну запись постоянного CompositionWindow для каждой живой FloatingGroup.
3. Не использовать PanelId как логическую идентичность CompositionWindow. PanelId может оставаться временным ключом в кэше PanelView, но не должен выбирать нативное окно композиции.
4. При создании FloatingGroup создать/назначить ровно одно окно и подключить целостный Composition renderer.
5. При изменении Layout обновлять содержимое существующего окна, не создавая HWND для каждой Column/Group.
6. При изменении FloatingGroup.bounds синхронизировать размеры и позицию единственного HWND.
7. При удалении/слиянии FloatingGroup закрывать только окно исчезнувшей композиции.
8. Не удалять старые typed host реализации, пока GroupDrag и Main DockArea drag ещё от них зависят.

**Основные зоны:** `floating_manager.rs`, `floating_host.rs`, `composition_host_registry.rs`, `panel_window_registry.rs`, `panel_window_handle.rs`, `floating_part_host.rs`.

**Готово, когда:** композиция с 4 Column и 8 Group создаёт ровно один постоянный HWND; Resize и повторный reconcile не создают дубликаты; после добавления/удаления Group окно остаётся одно.

### Этап 3. Сделать синхронизацию размеров отдельным проверяемым контрактом

**Цель:** не допустить возврата старого Resize-дефекта.

**Действия:**

1. Перевести `NativeResizeSession` на CompositionWindow, идентифицируемый через FloatingGroupId и WindowId, без PanelId-host lookup.
2. Сохранить преобразование native outer/client bounds в Core logical bounds с учётом DPI и frame/client insets.
3. Восстановить двустороннюю синхронизацию: HWND → Core при native Resize и Core → HWND после layout/drop/metrics изменений.
4. Исключить запись устаревших Core bounds в HWND, пока Windows выполняет свой modal resize loop.
5. Учитывать Core minimum size: сравнивать фактический принятый Core bounds, а не только запрошенный OS размер.
6. Разделить внешний resize окна и внутренний resize Splitter.
7. При финализации жеста выполнить единственную каноническую синхронизацию bounds, закрыть history transaction и обновить GPUI viewport.
8. Пересмотреть логику `apply_native_resize_bounds`: сдвиг соседних частей одной композиции больше не нужен; правила перемещения соседних самостоятельных Floating Composition оставить только в WindowGrid, если он сохранён.
9. Проверить сценарии изменения состава Composition: новая/удалённая Column, Float Group, Merge Group, Drop по внешней границе, Undo/Redo.

**Готово, когда:**

- растягивание правого/левого/нижнего края меняет Core bounds и внутренний layout;
- содержимое заполняет клиентскую область, не оставляя пустые полосы;
- внутренние Splitter не меняют размер HWND;
- Core-операции, которые изменяют bounds композиции, меняют и размер её HWND;
- отсутствуют скачки, зацикливание Resize, устаревшие размеры и ошибки на мониторах с разным DPI;
- старый баг из Этапа 0 воспроизводился до исправления и больше не воспроизводится.

### Этап 4. Перевести перенос отдельной Group на GroupDragWindow

**Цель:** сохранить Group drag без постоянных Group HWND.

**Действия:**

1. Использовать один временный DragHost для всей переносимой Group.
2. Подключить один и тот же маршрут для источника Main и Floating.
3. В исходном CompositionWindow оставить корректный placeholder и пересчитать оставшийся Layout.
4. DropZone получать из Core; не создавать отдельные правила или геометрию в GPUI.
5. Для Drop в существующую Composition передавать PanelView её постоянному CompositionWindow и закрывать временное окно только после подтверждённого handoff.
6. Для Drop на свободную область выполнять promotion временного HWND в постоянное CompositionWindow новой FloatingGroup.
7. При promotion атомарно обновлять root view, FloatingGroupId, native bounds и runtime registry. Не монтировать один AnyView одновременно в двух окнах.
8. Для NoOp, отказа и Escape восстанавливать исходное состояние, bounds и PanelView.

**Готово, когда:** Group можно перетаскивать из Main и Floating в Main, в существующую Floating Composition и на свободный рабочий стол; в постоянном состоянии на каждую Floating Composition остаётся один HWND.

### Этап 5. Перевести перенос целой Composition на один HWND

**Цель:** отказаться от создания временных Header/Group окон при drag за Composition Header.

**Действия:**

1. Для Main DockArea Header drag создавать один временный Composition host с полной сеткой и Header.
2. Не использовать `show_main_drag_parts` для создания окна на каждую Column и Group.
3. Для Floating Header drag перемещать существующий CompositionWindow.
4. Сохранять исходный Core placeholder/drag session, DropZone и rollback.
5. После принятого Drop в Floating использовать тот же HWND как постоянное окно новой Floating Composition или передать композицию существующему целевому окну.
6. При возврате в Main/отмене временный host закрывается; Main отображает актуальный Core Layout.
7. Не менять семантику Core-команд и уже работающих DropZone без отдельного подтверждённого дефекта.

**Готово, когда:** Main из 4 Column и 8 Group переносится одним временным окном; Floating Composition перемещается одним существующим HWND; при Drop нет создания окон по числу внутренних элементов.

### Этап 6. Перевести PanelTab drag и завершить handoff

**Цель:** все виды переноса используют согласованную модель двух типов окон.

**Действия:**

1. Внутреннее reorder вкладок оставить локальным там, где это уже работает.
2. Отделение PanelTab продолжает использовать временную поверхность без Composition Header.
3. При Merge вкладка передаётся существующему CompositionWindow-получателю.
4. При самостоятельном Float временная поверхность проходит тот же promotion, что и GroupDragWindow.
5. Устранить специальные пути, которые создавали постоянные Header/Group окна только для завершения PanelTab drag.
6. Сохранить отмену, focus, activation и запрет двойного монтирования PanelView.

**Готово, когда:** PanelTab работает из Main и Floating во всех поддерживаемых направлениях; итоговый состав HWND соответствует количеству Floating Composition.

### Этап 7. Удалить старую оконную модель и упростить WindowGrid

**Цель:** удалить только то, что больше не участвует в целевой архитектуре.

**Действия:**

1. Убедиться, что ни один сценарий не создаёт постоянные окна Header(NodeId) и Group(NodeId).
2. Удалить `FloatingPartHost` как постоянный оконный host. Сохранить нужные Group presentation/input helpers, если они реально используются временным GroupDragWindow.
3. Удалить `DockWindowPart`, `FloatingPartKind`, typed Header/Group window snapshots и registry entries, если после миграции нет оставшихся потребителей.
4. Упростить reconcile до состава FloatingGroupId → CompositionWindow.
5. Если подтверждено сохранение WindowGrid для нескольких самостоятельных Floating Composition:
   - оставить только Composition-level members;
   - восстановить единый member identity на FloatingGroupId;
   - удалить внутренние Header/Group links и соответствующие pruning/migration переходы;
   - сохранить только используемые алгоритмы совместного перемещения, стыковки, DPI, native Resize и Z-order целых Floating HWND.
6. Если совместное движение нескольких Floating Composition больше не требуется, удалить WindowGrid отдельно, после проверки, что ни один Core drop/resize сценарий от неё не зависит.
7. Обновить архитектурную документацию и acceptance criteria. Старые планы отдельных Header/Group HWND пометить как superseded, а не оставлять как действующую спецификацию.

**Готово, когда:** постоянное окно всегда соответствует целой Floating Composition; нет typed Header/Group HWND и их переходной инфраструктуры; WindowGrid либо работает только между целыми Floating Composition, либо полностью удалена по принятому решению.

## 7. Ручная приёмка после перехода

Проверять по порядку. Каждый сценарий выполнять на композициях с одной Column/Group, несколькими Column и несколькими Group.

### 7.1. Количество и состав окон

- [ ] Main с 4 Column и 8 Group остаётся одним Main HWND.
- [ ] Floating Composition с 4 Column и 8 Group создаёт один постоянный HWND.
- [ ] Отдельный Group drag создаёт максимум один временный GroupDragWindow.
- [ ] Whole Composition drag создаёт максимум один временный Composition host.
- [ ] Reconcile, повторный Drop и Undo/Redo не оставляют дубликатов или пустых HWND.

### 7.2. Resize — обязательный блок

- [ ] Увеличить/уменьшить Floating Composition за левую и правую границы.
- [ ] Изменить высоту за нижнюю границу.
- [ ] Изменить размер за угол.
- [ ] Проверить, что все внутренние Column/Group занимают актуальную клиентскую область.
- [ ] Проверить, что internal Splitter меняет только внутренние пропорции.
- [ ] Извлечь Group из середины и с края; убедиться, что source composition и её HWND имеют ожидаемые bounds.
- [ ] Вставить Group сбоку, сверху, снизу и между соседями; проверить синхронизацию bounds целевого окна.
- [ ] Превратить GroupDragWindow в самостоятельную Floating Composition; проверить изменение размера и позиции с учётом появления Header.
- [ ] Повторить Resize на мониторах с различным DPI.
- [ ] Проверить Undo/Redo и отмену во время/после Resize.

### 7.3. Переносы и стыковка

- [ ] Main → Floating: GroupGrip, PanelTab и Composition Header.
- [ ] Floating → Main: GroupGrip и PanelTab.
- [ ] Floating → Floating: GroupGrip, PanelTab и целая Composition.
- [ ] Drop в TabStrip/append, Top/Bottom, Left/Right и FreeArea.
- [ ] Escape, NoOp, неподдерживаемая цель и ошибка handoff возвращают исходное состояние.
- [ ] После любого переноса видимые PanelView не пропадают и не дублируются.

### 7.4. Окна целиком и WindowGrid

- [ ] Перемещать Floating Composition за свободную часть Header.
- [ ] Если WindowGrid сохранена: состыковать две самостоятельные Floating Composition и перемещать их совместно.
- [ ] Если WindowGrid сохранена: Resize одного целого Floating HWND корректно обрабатывает соседей по действующим правилам и не меняет внутреннюю Core-сетку.
- [ ] Закрытие Floating Composition удаляет только её; другие композиции остаются на месте.

## 8. Что не делать во время перехода

- Не откатывать всю историю коммитов до старой версии.
- Не переписывать Core Layout и Core DropZone ради новой оконной модели.
- Не создавать второе дерево Column/Group в GPUI.
- Не сохранять постоянные HWND на каждую Column или Group.
- Не использовать hide/show Header как главный переключатель между разными видами окна.
- Не удалять WindowGrid до решения, нужны ли совместное перемещение и физическая стыковка нескольких Floating Composition.
- Не переписывать Resize наугад до восстановления старого дефекта.
- Не менять одновременно рендеринг, drag lifecycle и sizing в одном этапе.
- Не запускать проверки агентом: локальные сборки и тесты выполняются пользователем после каждого этапа.

## Принцип выполнения

Сначала уточнить и зафиксировать старый Resize-дефект. Затем восстанавливать CompositionWindow, после этого — GroupDragWindow и переносы. Старые Header/Group HWND удалять только после того, как однооконная модель прошла ручную проверку.

Главный критерий перехода: **Core определяет одну Composition, а GPUI показывает её одним постоянным окном. Временное окно без Header существует только ради переноса отдельной Group/Tab.**
