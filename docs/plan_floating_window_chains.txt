# [УСТАРЕЛО] План реализации независимых Floating-окон и цепочек окон

> **СТАТУС: ПРЕДЫДУЩАЯ МОДЕЛЬ, НЕ ТЕКУЩАЯ СПЕЦИФИКАЦИЯ.** Документ исходил из правила «один FloatingGroup = один HWND и одна корневая Column». Оно больше не действует для композиций, содержащих несколько Columns. Текущий контракт: **Main — один HWND; Floating — один HWND на каждую Column**. Оконные связи WindowGrid строятся между реальными Column HWND, а не между абстрактными FloatingGroup. Актуальная архитектура и текущие этапы: [План-перехода-на-модель-одно-окно-на-композицию.md](План-перехода-на-модель-одно-окно-на-композицию.md). Этот файл сохранён как исторический план; его старые этапы нельзя выполнять буквально.

======================================================================
1. ЦЕЛЬ И ИТОГОВАЯ МОДЕЛЬ
======================================================================

Нужно реализовать Photoshop-подобную систему, в которой Floating-композиции
представляют собой отдельные независимые нативные окна Windows. Несколько
таких окон могут быть визуально состыкованы в цепочку, но при этом не
объединяются в одно окно и не сливаются в одну Core-композицию.

Основные правила модели:

1. Main DockArea может содержать несколько колонок. Такая DockArea является
   одной логической Main-композицией.

2. Каждая Floating-композиция содержит ровно одну корневую Column. Внутри
   этой Column могут находиться несколько Groups и Tabs.

3. Каждая Floating-композиция отображается в отдельном нативном окне Windows
   со своим WindowId/HWND и собственным FloatingGroupId.

4. Несколько Floating-композиций могут образовывать Window Chain — визуальную
   цепочку независимых окон, например [A, B, C]. Каждое окно сохраняет свою
   идентичность, Core-поддерево и содержимое.

5. Window Chain — ответственность GPUI/FloatingWindowManager. Это не новая
   основная сущность dock-core. Core продолжает описывать DockArea,
   FloatingGroup, Column, Group и Tabs.

6. Состыковка двух целых Floating-окон не должна выполнять
   DockCommand::DockFloating и переносить Core-поддерево одного окна в другое.
   Она должна связывать два независимых окна в одну Window Chain.

7. Перетаскивание вкладки или группы из любого Floating-окна создаёт для
   извлечённого содержимого отдельную Floating-композицию и отдельное окно.
   Это не то же самое, что перемещение целого окна за шапку.

8. Перетаскивание за шапку любого участника цепочки перемещает всю цепочку.
   Целое окно нельзя отделить от цепочки перетаскиванием его шапки.

9. Изменение размера одного окна меняет размер только этого окна. Окна,
   находящиеся правее него в цепочке, сдвигаются, чтобы сохранить стык.
   Размеры этих соседних окон не меняются.

10. Изменение размера должно выполняться системным механизмом Windows.
    Самодельное Qt-подобное изменение размера внутри client area не
    используется.

2. ЧТО НУЖНО СОХРАНИТЬ И ПЕРЕИСПОЛЬЗОВАТЬ
======================================================================

Перед реализацией не переписывать существующую архитектуру целиком.
Сначала сохранить и переиспользовать уже работающие механизмы:

- PanelWindowRegistry и существующее сопоставление панелей с нативными окнами;
- CompositionHostRegistry и выбор host-панели для FloatingGroup;
- FloatingWindowManager::reconcile() как механизм согласования Layout,
  реестра окон и видимости нативных окон;
- существующее создание WindowKind::Floating;
- существующую передачу/отображение AnyView;
- существующие механизмы определения DropTarget и разрешения перетаскивания;
- floating_root_for_node() и текущие операции извлечения Panel/Tabs/Group,
  где они соответствуют новой модели;
- текущие Core-команды для обычного докинга содержимого.

Особенно важно разделять два разных сценария:

А. Пользователь перетаскивает целое Floating-окно за шапку и стыкует его с
   другим Floating-окном. Это операция Window Chain на уровне менеджера окон.

Б. Пользователь перетаскивает Tab, Group или другой внутренний узел из одного
   окна в другое. Это операция изменения Core Layout через существующие
   механизмы Dock/Float.

Для этих сценариев нельзя использовать одну и ту же семантику команды.

3. ПОЭТАПНЫЙ ПЛАН РАБОТ
======================================================================

ЭТАП 1. АУДИТ ТЕКУЩЕГО СОСТОЯНИЯ И ГРАНИЦ ОТВЕТСТВЕННОСТИ

Цель:
Зафиксировать текущее поведение до изменений и точно определить, где сейчас
происходит слияние Floating-композиций и где отключено системное изменение
размера.

Основные файлы для повторного просмотра:

- crates/dock-gpui/src/floating_manager.rs
- crates/dock-gpui/src/components/floating.rs
- crates/dock-gpui/src/dock_host.rs
- crates/dock-gpui/src/controller_commands.rs
- crates/dock-gpui/src/input_drag.rs
- crates/dock-core/src/layout/floating_operations.rs
- crates/dock-core/src/layout/drop_handling.rs
- crates/dock-core/src/layout/tree_navigation.rs

Что проверить:

- как FloatingGroup сопоставляется с host-панелью и HWND;
- как reconcile() создаёт, показывает, скрывает и синхронизирует окна;
- как определяется цель при перетаскивании целого Floating-окна;
- где cross-floating drop превращается в DockCommand::DockFloating;
- как Main DockAreaHeader формирует операцию Float для многоколоночной
  DockArea;
- как извлекаются Group и Tab и что происходит с пустыми родителями;
- какие части старой нативной реализации Resize были удалены.

Результат этапа:
Краткая карта текущих вызовов и точные точки изменения. На этом этапе
поведение не переписывать и Core-модель не менять.

ЭТАП 2. ВОССТАНОВИТЬ СИСТЕМНОЕ NATIVE RESIZE

Цель:
Вернуть штатное изменение размера нативного Floating-окна средствами Windows.

Ориентир для сравнения:
Коммит 943ee85 — последнее состояние до отключения системного Resize.
Использовать его только как источник нужной реализации Resize, а не как
повод откатывать последующие изменения целиком.

Что сделать:

1. Сравнить текущую реализацию с состоянием 943ee85.
2. Выборочно восстановить системный resizable-режим окна.
3. Восстановить согласование минимальных размеров окна с ограничениями Core.
4. Восстановить отслеживание завершённого нативного Resize и передачу
   полученных размеров в Layout.
5. Проверить, что изменение размера не запускает бесконечный цикл
   reconcile/sync_window_bounds.
6. Удалить или отключить только тот custom-resize код, который дублирует
   системное поведение и мешает нативному Resize.
7. Сохранить более новые изменения, не относящиеся к Resize: перенос окон,
   межоконный drop, стабильность host-панелей, DPI и AnyView.

Ожидаемый результат:
Floating-окно изменяет размер через системную рамку Windows. Минимальные
размеры соблюдаются. Пользователь не должен вручную растягивать окно через
самодельные зоны внутри client area.

ЭТАП 3. ДОБАВИТЬ WINDOW CHAIN В FLOATING_WINDOW_MANAGER

Цель:
Научить менеджер учитывать группы независимых Floating-окон как одну
визуальную цепочку.

Что сделать:

1. Добавить в GPUI-слой структуру/реестр цепочек окон. Точное имя и внутренний
   формат выбрать после проверки текущих типов и идентификаторов.
2. Хранить упорядоченный список участников цепочки. Для идентификации
   использовать существующие FloatingGroupId и/или WindowId — без создания
   дублирующих идентификаторов там, где уже есть подходящий.
3. Сохранять связь каждого участника со своим HWND и собственным
   FloatingGroup.
4. Добавить операции присоединения окна к цепочке, удаления участника,
   получения порядка окон и очистки пустых цепочек.
5. Учитывать создание и уничтожение нативных окон в reconcile(). Повторный
   reconcile() не должен создавать дубликаты связей или менять состав цепи.
6. Не добавлять WindowChain в dock-core как основную сущность.

Ожидаемый результат:
Менеджер знает, что A, B и C образуют цепочку [A, B, C], но Core по-прежнему
видит три независимые Floating-композиции.

ЭТАП 4. ИЗМЕНИТЬ СТЫКОВКУ ЦЕЛЫХ FLOATING-ОКОН

Цель:
Стыковка двух целых окон должна создавать/расширять цепочку, а не объединять
их Core Layout.

Что сделать:

1. Разделить drop целого нативного окна и drop внутреннего содержимого.
2. При отпускании целого Floating-окна у другого Floating-окна определить
   целевое окно и место присоединения в цепочке.
3. Добавить оба окна в одну Window Chain в ожидаемом визуальном порядке.
4. Сохранить отдельные FloatingGroupId, WindowId/HWND и Core-поддеревья.
5. Не вызывать DockCommand::DockFloating для операции соединения целых окон.
6. Оставить DockCommand::DockFloating для реального переноса Group/Column
   внутрь другой DockArea, если это соответствует выбранной DropZone.
7. После изменения цепочки синхронизировать положение окон так, чтобы между
   ними не было разрывов или наложений.

Ожидаемый результат:
После соединения A и B на экране видны два отдельных окна, расположенные рядом.
В Core по-прежнему существуют две отдельные Floating-композиции.

ЭТАП 5. ПЕРЕМЕЩЕНИЕ ВСЕЙ ЦЕПОЧКИ ЗА ШАПКУ ЛЮБОГО ОКНА

Цель:
Перетаскивание за шапку любого участника должно перемещать всю цепочку,
сохраняя взаимное расположение окон.

Что сделать:

1. При начале перемещения определить цепочку, в которой находится окно.
2. Запомнить исходные координаты всех окон и положение курсора относительно
   окна, за шапку которого началось перемещение.
3. Во время движения вычислять смещение относительно исходной позиции.
4. Применять одно и то же смещение ко всем участникам цепочки.
5. Не изменять размеры окон и не менять Core Layout.
6. При отпускании зафиксировать итоговые позиции всех окон.
7. Если окно не входит в цепочку, использовать тот же механизм как цепочку
   из одного участника.

Ожидаемый результат:
Перетаскивание за шапку A, B или C перемещает всю цепочку [A, B, C].
Взаимные расстояния и размеры окон сохраняются.

ЭТАП 6. ПЕРЕТАСКИВАНИЕ ВСЕЙ MAIN DOCKAREA В FLOATING

Цель:
При извлечении многоколоночной Main-композиции каждая её колонка должна
стать отдельной Floating-композицией и отдельным нативным окном.

Пример:
Main DockArea содержит четыре колонки [A, B, C, D]. После перетаскивания
всей DockArea должны появиться четыре отдельных Floating-окна:

    [Floating A] [Floating B] [Floating C] [Floating D]

Они должны быть сразу связаны в одну Window Chain в исходном порядке.

Что сделать:

1. При начале Float всей Main DockArea получить упорядоченный список её
   корневых колонок.
2. Не превращать весь Split(X) в один FloatingGroup с несколькими Column.
3. Реализовать одну атомарную Core-операцию, которая извлекает все колонки
   DockArea и создаёт для каждой отдельный FloatingGroup с одной корневой
   Column.
4. Операция должна выполняться как одна транзакция истории — один Undo,
   а не четыре независимые Float-команды.
5. Сохранить порядок колонок, их ширины, содержимое и относительное
   расположение.
6. После обновления Layout создать/сопоставить отдельное нативное окно
   каждому FloatingGroup.
7. Объединить созданные окна в одну Window Chain в том же порядке.
8. Не затрагивать другую Main DockArea: Left и Right являются отдельными
   композициями. Если извлекается одна DockArea, она образует свою цепочку.

Ожидаемый результат:
Main DockArea из N колонок превращается в N независимых FloatingGroup и N
нативных окон, связанных одной цепочкой. Каждая Floating-композиция имеет
ровно одну корневую Column.

ЭТАП 7. ИЗВЛЕЧЕНИЕ TAB И GROUP ИЗ ЛЮБОГО ОКНА ЦЕПОЧКИ

Цель:
Сохранить возможность извлекать внутреннее содержимое независимо от того,
находится исходное окно отдельно или внутри цепочки.

Что сделать:

1. Для Tab и Group использовать существующие механизмы Float там, где они
   уже корректно формируют отдельную Floating-композицию.
2. Новая Floating-композиция должна содержать одну Column.
3. Создать для неё отдельное нативное окно и добавить его в Window Chain
   как нового независимого участника либо оставить отдельным окном — в
   зависимости от фактической точки извлечения и выбранной геометрии.
4. Не переносить HWND исходного окна на извлечённое содержимое, если это
   разрушает идентичность исходного окна.
5. Если после извлечения в исходной Column остались другие Groups, исходное
   окно и его FloatingGroup должны сохраниться.
6. Если исходная Column/Floating-композиция стала пустой, удалить пустые
   Core-узлы, закрыть/освободить соответствующее нативное окно и убрать его
   из Window Chain.
7. После удаления участника корректно пересчитать порядок/стыковку оставшихся
   окон, не меняя их размеры.
8. Не удалять непустую родительскую композицию только потому, что из неё
   извлечена одна Group или Tab.

Ожидаемый результат:
Tab или Group можно извлечь из любого окна цепочки. Извлечённое содержимое
получает отдельное окно, а исходное окно продолжает работать, если в нём
осталось содержимое.

ЭТАП 8. NATIVE RESIZE С УЧЁТОМ WINDOW CHAIN

Цель:
Изменение размера одного окна должно сдвигать следующие окна, но не менять
их размеры.

Что сделать:

1. Получать фактические новые bounds изменённого окна из системного Resize.
2. Сравнивать новую ширину с предыдущей шириной.
3. Сдвигать окна, расположенные правее изменённого участника, на величину
   изменения ширины, чтобы сохранить стык.
4. Не менять ширину или высоту соседних окон.
5. Не изменять размеры/структуру Core-композиций соседей.
6. Не допускать циклического запуска Resize/Move из-за синхронизации bounds.
7. При изменении размера последнего окна цепочки не перемещать отсутствующих
   последующих участников.
8. Соблюдать минимальные размеры самого изменяемого окна.

Пример:
Цепочка [A, B, C]. Ширина A увеличилась на 40 px. Тогда B и C сдвигаются
вправо на 40 px, а их собственные ширина и высота остаются прежними.

Ожидаемый результат:
Размер меняется только у окна под системным Resize. Соседние окна сохраняют
собственные размеры и только меняют положение для сохранения стыка.

ЭТАП 9. ЖИЗНЕННЫЙ ЦИКЛ, Z-ORDER И СОГЛАСОВАНИЕ ОКОН

Цель:
Сделать поведение цепочки устойчивым при закрытии окон, изменении Layout,
смене активного окна и повторных reconcile().

Что сделать:

1. При закрытии окна удалять его из соответствующей цепочки.
2. Если в цепочке остался один участник, считать его обычным одиночным
   Floating-окном и очищать лишнее состояние цепочки.
3. Если участников не осталось, удалить пустую цепочку.
4. При закрытии/удалении последнего содержимого корректно освободить host,
   HWND и записи реестров.
5. Синхронизировать z-order так, чтобы участники цепочки не теряли ожидаемое
   взаимное расположение по глубине.
6. Сохранить стабильность CompositionHostRegistry и PanelWindowRegistry.
7. Сделать reconcile() идемпотентным: одинаковый Layout и одинаковые связи
   должны приводить к одинаковому состоянию окон без повторного создания.

Ожидаемый результат:
Цепочки не содержат закрытых окон, не оставляют пустых FloatingGroup и не
создают дубликаты нативных окон/связей.

ЭТАП 10. СОХРАНЕНИЕ СОСТОЯНИЯ ЦЕПОЧЕК (ПОЗЖЕ)

Это отдельный последующий этап, не блокирующий базовую реализацию.

В дальнейшем можно сохранять:

- состав и порядок участников Window Chain;
- bounds каждого окна;
- взаимное расположение окон;
- связь окна с FloatingGroup;
- восстановление цепочек при загрузке workspace.

Не включать персистентность в первые этапы, пока не стабилизированы создание,
стыковка, перемещение, извлечение и Resize.

======================================================================
4. КРИТЕРИИ ПРИЁМКИ И РЕГРЕССИОННЫЕ СЦЕНАРИИ
======================================================================

Сценарий 1. Стыковка двух Floating-окон

- Открыть Floating A и Floating B.
- Состыковать B с A.
- На экране остаются два самостоятельных нативных окна.
- У окон разные WindowId/HWND и FloatingGroupId.
- Core-поддеревья не сливаются.

Сценарий 2. Перемещение цепочки

- Сформировать цепочку [A, B, C].
- Потянуть за шапку A: перемещаются A, B и C.
- Повторить перетаскивание за шапку B и затем C.
- Во всех случаях перемещается вся цепочка, взаимное расположение сохраняется.

Сценарий 3. Resize первого окна

- Сформировать цепочку [A, B, C].
- Увеличить ширину A на 40 px.
- B и C сдвигаются вправо на 40 px.
- Размеры B и C не меняются.

Сценарий 4. Resize среднего окна

- Сформировать цепочку [A, B, C].
- Изменить ширину B.
- A остаётся на месте.
- C сдвигается на величину изменения ширины B.
- Размеры A и C не меняются.

Сценарий 5. Извлечение Group из окна цепочки

- Сформировать цепочку из нескольких окон.
- Извлечь одну Group из среднего окна.
- Для Group создаётся отдельное Floating-окно.
- Если в исходном окне остались другие Groups, исходное окно сохраняется.

Сценарий 6. Извлечение последней Group

- Извлечь последнюю Group из одного из окон цепочки.
- Пустая исходная Floating-композиция и её окно корректно удаляются.
- Участник удаляется из Window Chain.
- Оставшиеся окна сохраняют размеры и корректную стыковку.

Сценарий 7. Извлечение всей Main DockArea из четырёх колонок

- В одной Main DockArea создать четыре колонки [A, B, C, D].
- Перетащить всю эту DockArea в Floating.
- Получить четыре отдельных нативных окна.
- Каждое окно содержит отдельный FloatingGroup с одной Column.
- Окна связаны в цепочку [A, B, C, D].
- Порядок, ширины и содержимое колонок сохранены.
- Одно Undo восстанавливает исходную Main DockArea целиком.

Сценарий 8. Независимость Main DockArea

- Если в Main есть отдельные Left и Right DockArea, извлечение одной из них
  не должно случайно включать колонки другой DockArea в ту же цепочку.

Сценарий 9. Внутренний Dock между композициями

- Перетащить Group внутрь другой композиции через соответствующую DropZone.
- Обычная Core-операция Dock должна продолжать работать.
- Логика соединения целых окон не должна перехватывать внутренний Dock.

Сценарий 10. Native Resize и ограничения

- Изменение размера выполняется системной рамкой Windows.
- Минимальные размеры соблюдаются.
- Не возникает двойного Resize, циклов синхронизации или скачков bounds.

Сценарий 11. Повторная синхронизация

- Несколько раз вызвать сценарии обновления Layout/reconcile.
- Не создаются дубликаты окон, цепочек или участников.
- Существующие host-панели продолжают отображать правильный AnyView.

======================================================================
5. ПОРЯДОК ВНЕДРЕНИЯ И КОНТРОЛЬ ИЗМЕНЕНИЙ
======================================================================

Работать небольшими завершёнными этапами. После каждого этапа пользователь
проверяет поведение в своём локальном окружении. Не объединять несколько
крупных этапов в один набор изменений.

Рекомендуемый порядок:

1. Аудит текущей реализации.
2. Восстановление системного Native Resize.
3. Реестр Window Chain.
4. Стыковка целых Floating-окон без слияния Core-композиций.
5. Перемещение всей цепочки за шапку любого окна.
6. Атомарное Float всех колонок одной Main DockArea в отдельные окна.
7. Извлечение Tab/Group и очистка пустых источников.
8. Native Resize с перемещением окон справа.
9. Z-order, закрытие окон и устойчивость reconcile().
10. Сохранение цепочек в workspace — отдельным этапом позднее.

Ограничения реализации:

- Работать в текущей ветке main. Новые ветки самостоятельно не создавать.
- Не делать массовый откат коммитов. Для Native Resize переносить только
  нужную системную реализацию, сохраняя более новые несвязанные изменения.
- Не вводить WindowChain в Core как новую основную сущность.
- Не объединять целые Floating-композиции через DockCommand::DockFloating.
- Не создавать параллельные реализации уже существующего поведения.
- Не переписывать работающие Core-механизмы без доказанной необходимости.
- Не запускать проверки проекта со стороны агента. Проверки выполняет
  пользователь локально после каждого этапа.
- Перед каждым этапом фиксировать список файлов и ожидаемую область изменений.

======================================================================
6. ИТОГОВОЕ СОСТОЯНИЕ, К КОТОРОМУ НУЖНО ПРИЙТИ
======================================================================

Main DockArea:
- может содержать несколько колонок;
- при Float всей DockArea каждая колонка становится отдельной Floating-
  композицией и отдельным нативным окном;
- все полученные окна формируют одну цепочку;
- операция выполняется атомарно и отменяется одним Undo.

Floating:
- каждая Floating-композиция содержит ровно одну корневую Column;
- внутри неё могут быть несколько Groups и Tabs;
- каждая композиция живёт в отдельном HWND;
- несколько таких окон могут быть связаны в Window Chain;
- соединение окон не объединяет их Core Layout.

Window Chain:
- хранится и управляется в GPUI/FloatingWindowManager;
- перемещается целиком за шапку любого участника;
- сохраняет независимость и размеры своих окон;
- при Resize одного окна сдвигает последующие окна без изменения их размеров;
- корректно обновляется при извлечении содержимого и закрытии окон.

Главный архитектурный принцип:
Core отвечает за структуру и операции над DockArea/Column/Group/Tabs и
FloatingGroup. FloatingWindowManager отвечает за реальные нативные окна,
их HWND, host-сопоставление и Window Chain. Стыковка целых окон связывает
окна на уровне менеджера, а внутренний Dock содержимого изменяет Core Layout.
