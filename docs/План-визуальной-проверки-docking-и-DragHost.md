# План визуальной проверки Docking и DragHost

## 1. Назначение документа

Документ предназначен для последовательной ручной проверки уже реализованной системы перетаскивания и стыковки Docking. Это не план разработки и не замена автоматических тестов. Цель — проверить поведение приложения глазами пользователя: начало жеста, отображение DragHost, placeholder, подсветку целей, итоговую структуру, отмену, фокус и поведение постоянных Floating-окон.

План объединяет требования из двух документов:

- [План переделки Docking: перетаскивание и стыковка](План-переделки-docking-перетаскивание-и-стыковка.md) — семантика Panel / Group / Column / DockArea, допустимые стыковки и единые правила Main/Floating.
- [План внедрения DragHost — временного окна переноса](План-внедрения-DragHost-временно-окно-переноса.md) — перенос содержимого во временный DragHost, маршрутизация по HWND, placeholder, отмена, очистка, Undo и фокус.

Проверки выполняются по этапам. Каждый этап можно проходить отдельно. После подтверждения этапа переходим к следующему. Если обнаружена ошибка, фиксируем её и не маскируем результат следующими проверками.

## 2. Что считаем правильным поведением

### 2.1. Три разных роли окон

| Роль | Что должно происходить |
|---|---|
| MainHost | Постоянное главное окно с основным Dock Layout |
| FloatingHost | Постоянное нативное окно со своей Dock-композицией и геометрией |
| DragHost | Временное окно только для визуального переноса содержимого; оно не является Dock-целью и не меняет Layout |

DragHost не должен превращаться в постоянную Floating-композицию во время движения. Постоянное Floating создаётся только после успешного отпускания в свободной области.

### 2.2. Что переносим

| Источник | Что именно должно перемещаться |
|---|---|
| PanelTab | Одна Panel, даже если она неактивна во вкладках |
| GroupGrip | Вся Group с её вкладками и их порядком |
| Column grip | Вся Column со всеми Groups и Panels |
| Main DockArea header | Вся выбранная Main DockArea как единое поддерево |
| FlyoutPanel | Panel, открытая во Flyout; Flyout не должен подменять тип источника |
| Заголовок постоянного FloatingHost | Само нативное окно, а не содержимое через DragHost |

### 2.3. Общие инварианты

Во время drag, до mouse-up:

- исходный Layout не меняется;
- исходный объект остаётся в исходной структуре, а на его месте отображается placeholder;
- placeholder занимает прежнюю геометрию и не сдвигает соседние элементы;
- одна PanelView не отображается одновременно в двух окнах;
- DragHost следует за курсором с сохранением точки захвата;
- DragHost не участвует в выборе целевого HWND и не показывает собственные drop-зоны;
- подсветка соответствует результату Core Resolver целевого MainHost/FloatingHost.

После успешного drop:

- применяется одна конечная структурная операция;
- объект появляется ровно в одном целевом месте;
- placeholder исчезает;
- DragHost закрывается;
- порядок вкладок, групп и колонок остаётся корректным.

После отмены:

- исходная структура остаётся прежней;
- исходное представление возвращается;
- DragHost закрывается;
- Undo/Redo не получают лишних записей.

## 3. Правила проведения проверки

1. Перед каждым этапом подготовить понятное исходное состояние Layout. Не проверять несколько разных операций на одной случайно изменённой структуре.
2. Использовать панели с различимыми названиями, чтобы визуально видеть, какая именно Panel переместилась и в каком порядке.
3. Для проверки Group подготовить группу с одной вкладкой и группу с несколькими вкладками.
4. Для проверки Column подготовить колонку с одной Group и колонку с несколькими Groups. По возможности проверить как развёрнутую, так и свёрнутую/rail-колонку.
5. Для межоконных сценариев открыть минимум два постоянных FloatingHost, чтобы отдельно проверить перенос в конкретное окно, а не только в любое Floating.
6. Перед отпусканием мыши задержать курсор над целью и проверить подсветку. Не ограничиваться проверкой итогового положения после drop.
7. После каждого успешного действия осмотреть исходную и целевую области: не осталось ли пустого места, дубликата, пропавшей панели или лишнего окна.
8. Для сравнения повторить операцию в обратном направлении, если соответствующая комбинация поддерживается.
9. Записывать результат каждого сценария: ПРОЙДЕНО, ОШИБКА, НЕ ПОДДЕРЖИВАЕТСЯ или НЕ ПРОВЕРЕНО.
10. Если для проверки этапа потребовалось исправление кода, сначала исправить только найденную проблему, затем выполнить локальные проверки проекта и повторить этот сценарий. Сборку и тесты запускает пользователь в своём окружении.

### Как проверять один сценарий

- Зафиксировать исходное состояние и запомнить порядок вкладок/групп.
- Начать drag за предназначенную для этого область, а не за кнопку или интерактивный элемент.
- Дождаться визуального перехода в DragHost.
- Проверить placeholder и внешний вид DragHost.
- Навести курсор на конкретную drop-зону и проверить Overlay до отпускания.
- Отпустить мышь.
- Проверить итоговую структуру в обоих окнах.
- Повторить сценарий через Undo, если операция должна быть обратимой.

## 4. Этапы визуальной проверки

---

## Этап 0. Подготовить контрольное рабочее пространство

**Цель:** получить воспроизводимую исходную конфигурацию, чтобы результаты разных этапов можно было сравнивать.

**Подготовить:**

- Main Dock с несколькими колонками, если это доступно в текущем приложении;
- хотя бы одну Group с несколькими вкладками;
- хотя бы одну Group с одной вкладкой;
- колонку с несколькими Groups;
- одну постоянную Floating-композицию;
- для дальнейших этапов — вторую постоянную Floating-композицию;
- различимые Panel, чтобы визуально контролировать их порядок и содержимое.

**Проверить:**

- каждое постоянное Floating — отдельное нативное окно;
- окна можно перемещать независимо друг от друга;
- содержимое Main и каждого Floating отображается без наложений и пустых участков;
- текущие размеры и расположение окон позволяют удобно тестировать drop-зоны;
- начальное состояние записано или сохранено, чтобы к нему можно было вернуться.

**Готово, если:** подготовлено воспроизводимое пространство с Main и несколькими FloatingHost. Если приложение сейчас не позволяет собрать какую-либо структуру через UI, отметить это как ограничение тестовой конфигурации, а не как ошибку drag-механики.

---

## Этап 1. Проверить начало жеста и области захвата

**Цель:** убедиться, что перетаскивание начинается только с предназначенных областей и обычные клики не превращаются в drag.

**Сценарии:**

1. Короткий click по вкладке PanelTab — вкладка активируется, DragHost не появляется.
2. Pointer-down и отпускание до drag-порога — выполняется обычное действие элемента, DragHost не появляется.
3. Перетаскивание PanelTab за пределы исходной drag-зоны — запускается перенос.
4. Перетаскивание Group за GroupGrip — захватывается вся Group.
5. Перетаскивание Column за отдельный Column grip — захватывается вся Column.
6. Перетаскивание Main DockArea за её управляющий header — захватывается вся выбранная область.
7. Перетаскивание Panel из открытого Flyout — захватывается Panel, а не Flyout как отдельная композиция.
8. Перетаскивание вкладки внутри существующего FloatingHost — обычное перемещение вкладки внутри полосы работает; при выходе из неё запускается DragHost.
9. Клики по кнопкам управления колонкой, вкладками и группой не запускают drag вместо действия кнопки.

**Ожидаемый результат:**

- жест определяется по исходному handle и payload;
- тип переносимого объекта не меняется при переходе в DragHost;
- click и drag различаются предсказуемо;
- область заголовка существующего FloatingHost не начинает переносить его содержимое вместо самого окна.

**Готово, если:** каждый тип захвата запускается из своей зоны, а клики/кнопки сохраняют обычное поведение.

---

## Этап 2. Проверить визуальное поведение DragHost и placeholder

**Цель:** проверить, что временное окно корректно представляет переносимое содержимое, не меняя постоянный Layout.

Для каждого источника — Panel, Group, Column и Main DockArea — выполнить начало drag и удерживать мышь, не отпуская её.

**Проверить:**

1. DragHost появляется после начала реального drag, а не при обычном pointer-down.
2. DragHost следует за курсором без заметного отставания и скачков.
3. Точка захвата сохраняется: окно не прыгает относительно курсора.
4. В DragHost нет постоянной шапки/заголовка Floating-композиции, пока идёт перенос.
5. В исходном Host появляется placeholder.
6. Placeholder занимает прямоугольник исходного объекта:
   - Panel — место содержимого панели;
   - Group — место всей группы;
   - Column — вся высота и ширина колонки;
   - DockArea — вся выбранная область.
7. Соседние Groups и Columns не сдвигаются неожиданно, а геометрия исходной области остаётся стабильной.
8. Переносимое содержимое не дублируется между DragHost и исходным Host.
9. Содержимое не исчезает на промежуточном кадре при передаче между окнами.
10. При mouse-up временное окно закрывается, а постоянный FloatingHost появляется только при drop в FreeArea.

**Отдельно проверить:**

- неактивную вкладку PanelTab;
- Group с несколькими вкладками;
- Column с несколькими Groups;
- DockArea с несколькими Columns.

**Готово, если:** DragHost показывает исходное содержимое, placeholder сохраняет геометрию, нет двойного отображения и лишнего постоянного окна во время перетаскивания.

---

## Этап 3. Проверить маршрутизацию окон и drop-overlay

**Цель:** убедиться, что цель определяется по реальному окну под курсором и локальным координатам именно этого окна.

**Сценарии:**

1. Начать drag в Main и провести курсор над Main.
2. Провести курсор над первым FloatingHost.
3. Провести курсор над вторым FloatingHost.
4. Перемещаться между двумя FloatingHost, не отпуская мышь.
5. Переместиться из окна в свободную область рабочего стола.
6. Вернуться из FreeArea поверх другого DockHost.
7. Провести курсор над самим DragHost, когда он перекрывает Main или Floating.

**Проверить:**

- при переходе между окнами подсветка пропадает со старой цели и появляется в актуальном целевом окне;
- Overlay находится в целевом Main/Floating, а не в DragHost;
- DragHost не становится drop-целью, даже когда перекрывает окно назначения;
- при перекрытии нескольких окон выбирается верхнее подходящее постоянное Dock-окно под курсором;
- координаты не смещены относительно клиентской области;
- одинаковая визуальная зона в Main и Floating означает одну и ту же структурную операцию;
- свободная область определяется только тогда, когда под курсором нет подходящего MainHost/FloatingHost.

**Для каждой зоны:**

- задержать курсор над её центром;
- немного переместить мышь внутри зоны;
- пересечь границу соседней зоны;
- проверить, что Overlay переключается в ожидаемый вариант;
- вернуть курсор в предыдущую зону и убедиться, что результат переключается обратно.

**Готово, если:** подсветка всегда относится к реальному целевому окну и соответствует его Core DropZone; нет ложных зон на DragHost и перескоков между геометрическими кэшами разных окон.

## Этап 4. Проверить перенос одной Panel

**Цель:** проверить полный цикл PanelTab через DragHost во всех основных сочетаниях Main/Floating.

**Матрица:**

| Источник | Цель | Ожидаемый результат |
|---|---|---|
| Panel Main | Group Main | Panel добавляется в конец вкладок целевой Group |
| Panel Main | Group Floating | Panel переносится в указанную Group FloatingHost |
| Panel Floating A | Group Main | Panel переносится в Main |
| Panel Floating A | Group Floating B | Panel переносится именно в Group второго FloatingHost |
| Panel Main | FreeArea | После release создаётся отдельный постоянный Floating |
| Panel Floating | FreeArea | После release создаётся новая отдельная Floating-композиция |
| Panel | собственная исходная Group | No-op либо корректное сохранение исходного положения, без дублирования |

**Проверить в каждом применимом сценарии:**

- до отпускания Panel остаётся в исходном Layout под placeholder;
- при наведении на центр Group Overlay показывает добавление вкладки;
- после drop Panel оказывается в конце вкладок целевой Group;
- остальные вкладки сохраняют порядок;
- исходная Group корректно освобождается от Panel;
- перенос в Floating A и Floating B не путает целевые окна;
- при FreeArea постоянный Floating появляется только после отпускания;
- после drop заголовок постоянного Floating отображается обычным образом;
- старый исходный Floating не закрывается и не превращается случайно в окно новой панели.

**Дополнительно:** проверить активную и неактивную вкладки, чтобы убедиться, что перенос не зависит от того, была ли Panel активной.

**Готово, если:** Panel переносится напрямую в выбранный Main/Floating Host, добавляется в конец вкладок, а FreeArea создаёт постоянное Floating только на release.

## Этап 5. Проверить структурные операции Group

**Цель:** убедиться, что переносится именно Group целиком, а не отдельная активная Panel или корневая Floating-композиция.

**Подготовить:** одну Group с одной вкладкой и одну Group с несколькими вкладками.

**Проверить три варианта цели:**

1. **Центр существующей Group.** Drop объединяет вкладки в одну Group. Внутренний порядок вкладок исходной Group сохраняется; целевая Group получает ожидаемый порядок согласно выбранной операции.
2. **Верхняя граница Group.** Drop создаёт отдельную Group сверху.
3. **Нижняя граница Group.** Drop создаёт отдельную Group снизу.

**Матрица источника и цели:**

| Источник | Цель |
|---|---|
| Group Main | Group Main |
| Group Main | Group Floating |
| Group Floating A | Group Main |
| Group Floating A | Group Floating B |
| Group Main/Floating | FreeArea |

**Проверить:**

- placeholder занимает весь исходный прямоугольник Group;
- в DragHost видны все вкладки исходной Group;
- переносится вся Group, включая неактивные вкладки;
- при объединении не теряется ни одна Panel;
- при создании Group сверху/снизу порядок соседних Groups понятен и стабилен;
- исходная Column корректно перестраивается после ухода Group;
- при FreeArea появляется одна постоянная Floating-композиция, а не набор отдельных окон;
- повторный drag из нового места работает.

**Готово, если:** вся Group перемещается одной операцией, вкладки внутри неё сохраняются, а выбранная зона определяет объединение или создание соседней Group.

---

## Этап 6. Проверить перенос Column и горизонтальные стыковки

**Цель:** проверить, что Column переносится как единое поддерево, включая все Groups и Panels.

**Подготовить:**

- Column с одной Group;
- Column с несколькими Groups;
- по возможности свёрнутую/rail-Column;
- Main с несколькими Columns;
- Floating-композицию с одной или несколькими Columns.

**Матрица:**

| Источник | Цель | Ожидаемый результат |
|---|---|---|
| Column Main | допустимый слот Main | Вся Column вставляется в выбранное место |
| Column Main | внешний край Main | Вся Column стыкуется к допустимому краю |
| Column Main | внешний край Floating | Вся Column добавляется к допустимому внешнему краю Floating-композиции |
| Column Floating A | допустимая Column Main | Вся Column переносится в Main |
| Column Floating A | внешний край Floating B | Вся Column переносится в другую Floating-композицию |
| Column Main/Floating | FreeArea | После release создаётся Floating из всей Column |

**Проверить:**

- placeholder охватывает всю Column;
- DragHost показывает все Groups, вкладки и активные PanelView исходной Column;
- Column не распадается на отдельные переносы Groups;
- внутренний порядок Groups и вкладок сохраняется;
- splitters и размеры дочерних областей не теряются без причины;
- при вставке в слот между Columns появляется ожидаемая позиция;
- горизонтальная стыковка целой Column доступна только на разрешённых внешних Left/Right краях;
- для отдельной Panel или Group не появляются ложные горизонтальные зоны, предназначенные для целой Column;
- свёрнутая/rail-Column также захватывается отдельным grip и переносится целиком;
- после ухода единственной Column исходная область корректно обрабатывает пустое состояние;
- FreeArea создаёт одно постоянное Floating-окно только после mouse-up.

**Готово, если:** вся Column переносится единым поддеревом, её порядок и содержимое сохраняются, а горизонтальные зоны соответствуют ограничениям для целых Column-композиций.

## Этап 7. Проверить перенос Panel из Flyout

**Цель:** проверить отдельный путь FlyoutPanel через общий DragHost без преждевременного превращения Panel во Floating.

**Подготовить:** Column в режиме IconsOnly и открыть Flyout для одной Panel.

**Сценарии:**

1. FlyoutPanel → Group Main.
2. FlyoutPanel → существующий FloatingHost.
3. FlyoutPanel → FreeArea.
4. FlyoutPanel → Escape во время drag.
5. FlyoutPanel → исходное место или недопустимая зона.

**Проверить:**

- drag начинается с содержимого Panel во Flyout;
- DragHost получает именно Panel;
- flyout не закрывается в момент пересечения drag-порога;
- до успешного release исходная структура и Layout не меняются;
- при успешном drop Flyout закрывается, а Panel появляется в выбранной цели;
- при Escape Panel возвращается в исходный Flyout, сам Flyout остаётся доступен;
- при ошибке или недопустимом drop содержимое не теряется;
- повторное открытие Flyout и следующий drag работают.

**Готово, если:** FlyoutPanel переносится через DragHost, а закрытие Flyout происходит только после успешного release.

## Этап 8. Проверить перенос Main DockArea

**Цель:** проверить временное представление всей левой или правой Main DockArea через DragHost.

**Подготовить:**

- Left DockArea с одной Column;
- Right DockArea с несколькими Columns;
- хотя бы одну активную Panel в каждой переносимой Column.

**Проверить:**

1. Захват Main DockArea за предназначенную область общего header.
2. Вся выбранная область заменяется одним placeholder.
3. Все её Columns и splitters исчезают из исходного места на время передачи.
4. DragHost показывает всю multi-column-композицию.
5. Активные PanelView всех Columns отображаются только в DragHost.
6. Drop в FreeArea создаёт постоянный Floating из исходного DockArea только после release.
7. Escape закрывает DragHost и возвращает всю DockArea на исходное место.
8. Если в DockArea открыт Flyout, перенос области должен быть заблокирован или не стартовать согласно текущему контракту.

**Известное ограничение текущей реализации:**

Core DropSource пока не содержит самостоятельную цель для прямого переноса целой Main DockArea поверх другой Main/Floating-композиции. Поэтому такой drop нельзя считать поддерживаемой стыковкой. Визуально проверить, что отпускание над Main/Floating не вызывает преждевременный Float, не повреждает исходную область и корректно завершает/отменяет жест. Для положительного результата «DockArea пристыкована к Main/Floating» потребуется отдельное решение и реализация Core-операции; не отмечать этот сценарий как пройденный только потому, что DragHost показал правильную картинку.

**Готово, если:** Main DockArea безопасно переносится целиком в FreeArea, отменяется без изменений и не теряет PanelView. Прямой drop в Main/Floating фиксируется отдельно как неподдерживаемый текущей моделью.

---

## Этап 9. Проверить отмену, недопустимые цели и восстановление

**Цель:** проверить все терминальные пути DragHost, а не только успешные переносы.

**Сценарии отмены:**

1. Escape до появления DragHost.
2. Escape сразу после появления DragHost.
3. Escape, когда курсор над разрешённой drop-зоной.
4. Escape, когда курсор находится в FreeArea.
5. Отпустить мышь над исходным местом.
6. Отпустить мышь вне всех DockHost, если этот сценарий не должен создавать Floating для выбранного типа.
7. Отпустить над недопустимой целью.
8. Повторно нажать Escape после уже завершённой отмены, если обработчик позволяет этот сценарий.
9. После каждой отмены сразу начать новый drag.

**Проверка системной потери фокуса:**

1. Во время drag переключиться между MainHost, FloatingHost и DragHost — сессия должна продолжаться.
2. Во время drag выполнить Alt+Tab или переключиться на внешнее приложение — сессия должна отмениться и восстановить исходное содержимое.
3. Во время drag закрыть целевой FloatingHost, если это безопасно воспроизводится.
4. Повторить после успешного переноса и после Escape.

**Проверить после каждой отмены/ошибки:**

- Layout визуально не изменился;
- исходный объект вернулся в прежнее место;
- placeholder исчез;
- исходная активная вкладка восстановлена;
- DragHost исчез и не остался скрытым/зависшим;
- нет лишнего постоянного FloatingHost;
- не осталось пустой Group/Column из-за незавершённого переноса;
- Undo/Redo не изменились;
- следующий drag запускается нормально.

**Готово, если:** каждый путь отмены возвращает исходное состояние, не оставляет временное окно и не мешает следующему drag.

---

## Этап 10. Проверить Undo/Redo и сохранение состояния PanelView

**Цель:** убедиться, что визуально успешный перенос не пересоздаёт Panel и не ломает пользовательское состояние.

**Проверка истории:**

1. Выполнить один успешный перенос Panel.
2. Выполнить ровно один Undo — Panel должна вернуться в исходную структуру.
3. Выполнить Redo — Panel должна вернуться в целевую структуру.
4. Повторить для Group и Column.
5. Выполнить отменённый drag и проверить, что Undo не отменяет какое-либо предыдущее пользовательское действие.

**Проверка содержимого:**

- ввести текст в TextInput, затем перенести содержащую его Panel Main → Floating;
- проверить ввод после переноса;
- перенести Panel обратно Floating → Main;
- перенести Panel между двумя FloatingHost;
- проверить сохранение текста и локального состояния;
- повторить для неактивной вкладки, если это применимо;
- проверить, что активная вкладка Group остаётся ожидаемой после переноса;
- убедиться, что одна Panel не появилась одновременно в двух местах.

**Проверка порядка:**

- Panel после переноса добавлена в конец вкладок целевой Group;
- при переносе Group сохраняется внутренний порядок её вкладок;
- при переносе Column сохраняется порядок Groups и вкладок;
- после Undo/Redo структура восстанавливается без перестановок.

**Готово, если:** успешный drop создаёт ровно одну логическую запись истории, Undo/Redo возвращает структуру, а cached PanelView сохраняет состояние и остаётся интерактивной.

## Этап 11. Отдельно проверить постоянные FloatingHost

**Цель:** не спутать перенос содержимого через DragHost с перемещением или изменением размера уже существующего нативного окна.

**Сценарии:**

1. Перетащить общий заголовок FloatingHost — перемещается всё нативное окно.
2. Изменить размер FloatingHost за его границу/resize-зону.
3. Переместить окно поверх Main и других FloatingHost.
4. Переместить несколько FloatingHost независимо друг от друга.
5. Перетащить Panel/Group/Column внутри FloatingHost за их собственные drag-зоны — это уже перенос содержимого через DragHost.
6. Если в интерфейсе есть отдельный жест захвата всей Floating-композиции для DockFloating, проверить его отдельно от заголовка окна. Не подменять этот сценарий простым перемещением HWND.

**Ожидаемый результат:**

- заголовок постоянного FloatingHost перемещает только HWND;
- resize меняет размер именно текущего FloatingHost;
- native move/resize не создают DragHost и не оставляют placeholder внутри Dock Layout;
- drag подструктуры из FloatingHost, напротив, запускает DragHost;
- постоянные FloatingHost остаются зарегистрированными окнами;
- DockCommand::DockFloating, если доступна через отдельный жест композиции, стыкует существующую Floating-композицию, а не временный DragHost.

**Готово, если:** перемещение/resize постоянного окна визуально и поведенчески отделены от переноса Panel/Group/Column.

## Этап 12. Проверить геометрию, DPI, несколько мониторов и z-order

**Цель:** проверить реальные экранные условия, которые нельзя надёжно покрыть одной раскладкой на одном мониторе.

**Сценарии:**

1. Переместить DragHost между Main и Floating на одном мониторе.
2. Перетащить содержимое на второй монитор.
3. Начать drag на одном DPI/scale factor и закончить на другом.
4. Проверить положение DragHost относительно курсора после перехода через границу мониторов.
5. Проверить drop возле левого, правого, верхнего и нижнего края экрана.
6. Проверить частично перекрытые Main/Floating окна.
7. Проверить DragHost поверх нескольких перекрывающихся DockHost.
8. Проверить сценарий, когда DragHost визуально закрывает часть целевого окна.

**Проверить:**

- нет постоянного смещения курсора или placeholder;
- Overlay совпадает с фактическими зонами окна;
- правильное окно выбирается с учётом z-order;
- DragHost исключается из hit-test, но реальное целевое окно за ним находится;
- scale factor конкретного целевого окна используется для перевода координат;
- после drop не остаются окна за пределами видимого рабочего стола;
- повторный drag после перехода между мониторами работает.

**Готово, если:** координаты и выбор окна остаются корректными на всех доступных конфигурациях мониторов и DPI.

## Этап 13. Финальный регрессионный проход

**Цель:** пройти ключевые сценарии подряд после завершения отдельных этапов и убедиться, что успешные операции не ломают следующие.

Пройти в указанном порядке:

1. Panel Main → Group Main.
2. Panel Main → Group Floating A.
3. Panel Floating A → Group Main.
4. Panel Floating A → Group Floating B.
5. Panel → FreeArea.
6. Group Main → Group Main (объединение).
7. Group Main → верх/низ другой Group.
8. Group Main → Group Floating.
9. Group Floating → Group Main.
10. Column Main → допустимый слот Main.
11. Column Main → внешний край Floating.
12. Column Floating → Main.
13. Column Floating A → Floating B.
14. Column → FreeArea.
15. FlyoutPanel → Group Main.
16. FlyoutPanel → Floating.
17. FlyoutPanel → FreeArea.
18. Main DockArea → FreeArea.
19. Escape во время активного DragHost.
20. Заголовок постоянного FloatingHost — native move.
21. Граница постоянного FloatingHost — native resize.

Для каждого успешного переноса после release проверить:
- исходное место;
- целевое место;
- количество и порядок вкладок;
- активную вкладку;
- наличие/отсутствие placeholder;
- количество постоянных FloatingHost;
- отсутствие оставшегося DragHost.

Для каждого отменённого переноса проверить:
- исходное состояние без изменений;
- отсутствие лишней записи Undo;
- возможность немедленно начать следующий drag.

**Этап считается завершённым, когда:** все поддерживаемые сценарии пройдены, известные ограничения явно записаны, нет потери/дублирования Panel, а постоянные FloatingHost и временный DragHost работают как разные роли.

## 6. Ограничения текущей проверки

- План проверяет визуальное и интерактивное поведение уже существующей реализации; он сам по себе не добавляет новые Core DropTarget или жесты.
- Прямой drop целой Main DockArea в Main/Floating пока не имеет Core-операции и не должен считаться поддержанным.
- Любая зона должна исходить от Core Resolver. Нельзя считать правильной подсветку только потому, что она выглядит убедительно: после drop результат должен соответствовать показанной операции.
- Свободная область — отдельная цель. Постоянный FloatingHost должен создаваться на release, а не на старте detach.
- Заголовок и resize-зоны постоянного FloatingHost проверяются отдельно от drag его содержимого.
- Ручные проверки на Windows нужны для реального HWND, foreground focus, DPI и межмониторной геометрии. Автоматические тесты не заменяют эту визуальную приёмку.

## 7. Порядок совместной работы

1. Начинаем с Этапа 0 и фиксируем исходное рабочее пространство.
2. Проходим по одному этапу, не перескакивая через обнаруженные ошибки.
3. Для каждого этапа я заранее фиксирую конкретный сценарий проверки и ожидаемый результат.
4. Пользователь выполняет проверку в локальном приложении и присылает результат или снимок экрана.
5. При проблеме сначала разбираем её и исправляем минимальный участок; только после повторной проверки продолжаем.
6. Работаем в текущей ветке main. Новые ветки самостоятельно не создаём.
7. Исходные планы остаются историей реализации и архитектурных решений; этот документ становится отдельным чек-листом визуальной приёмки.
