======================================================================
1. ЦЕЛЬ И ЗАФИКСИРОВАННОЕ ПОВЕДЕНИЕ
======================================================================

Нужно расширить существующую WindowChain с горизонтальной последовательности
окон до двумерной сетки независимых Floating-окон.

Каждое окно остаётся самостоятельным:
- собственный FloatingGroupId;
- собственный HWND / WindowId;
- собственный Core Layout и содержимое;
- собственные bounds;
- собственные ограничения минимального размера;
- собственный расчёт высоты по содержимому.

Общее правило независимости размеров имеет одно явно заданное исключение:
при вертикальной стыковке перетаскиваемое окно принимает ширину целевого окна,
на которое его сбрасывают. Ширина целевого окна при этом не меняется.

Стыковка целых окон не объединяет их Core-композиции. WindowChain/Grid остаётся
ответственностью GPUI/FloatingWindowManager. Dock Core продолжает отвечать за
внутреннюю структуру отдельного FloatingGroup и за обычный Dock содержимого.

Поддерживаемые направления стыковки целых окон:
- слева;
- справа;
- сверху;
- снизу.

Пример целевой сетки:

        ┌──────────┬──────────┐
        │    A     │    B     │
        ├──────────┘          │
        │    C                │
        ├──────────┐          │
        │    D     │    E     │
        └──────────┴──────────┘

Это иллюстрация отношений соседства, а не требование сделать все строки и
колонки одинакового размера. Реальные размеры каждого HWND независимы.

Поведение Resize:

1. При изменении правой границы окна само окно меняет ширину. Окна справа от
   него перемещаются настолько, насколько нужно для сохранения стыка. Их
   ширина и высота не меняются.
2. При изменении нижней границы окно меняет высоту. Окна ниже него перемещаются
   вниз на изменение нижней границы. Их собственные размеры не меняются.
3. Изменение левой или верхней общей границы не должно запускаться со стороны
   окна, у которого слева или сверху есть сосед. Общая граница принадлежит
   правому/нижнему соседу предыдущего окна: resize выполняется через правую
   или нижнюю границу предыдущего окна.
4. При изменении размера последнего окна в соответствующем направлении другие
   окна не сдвигаются.
5. При изменении угла могут одновременно измениться ширина и высота. Сдвиги
   должны объединяться, чтобы один HWND не получил несколько конфликтующих
   наборов bounds.
6. Перетаскивание за шапку любого участника перемещает всю связанную сетку
   одним и тем же физическим смещением. Размеры и взаимное расположение
   сохраняются.

Поведение шапки:

- Шапка композиции остаётся обычной частью каждого Floating-окна.
- Для нижних окон не вводится постоянный флаг скрытия шапки.
- Нижняя шапка физически перекрывается HWND предыдущего окна сверху.
- Шапка верхнего окна остаётся видимой и перемещает всю сетку.
- При извлечении окна из сетки его шапка становится видимой автоматически,
  потому что больше не перекрыта соседним HWND.
- Не пересоздавать окна ради переключения вариантов «с шапкой / без шапки».

Правило ширины при вертикальной стыковке зафиксировано:

- Эталоном является конкретное целевое окно, на которое пользователь сбрасывает
  перетаскиваемое окно.
- Перетаскиваемое окно принимает текущую ширину целевого окна.
- Целевое окно сохраняет свою ширину без изменений.
- Например, если окно 2 сбрасывают на окно 1 сверху или снизу, ширина окна 2
  становится равной ширине окна 1; окно 1 не расширяется и не сужается.
- Не выбирать максимальную ширину среди участников сетки и не расширять всю
  сетку по самому широкому окну.
- Нормализация ширины выполняется как часть операции вертикального Drop до
  окончательной расстановки HWND. После неё шапка нижнего окна должна
  перекрываться верхним окном по всей ширине.

Это правило относится именно к окну, которое сбрасывают, и к конкретному окну,
на которое выполняется Drop. Размеры остальных участников сетки не следует
пересчитывать по принципу максимальной ширины.

2. ЧТО УЖЕ ЕСТЬ В КОДЕ И ЧТО МОЖНО ПЕРЕИСПОЛЬЗОВАТЬ

Анализ выполнен по main на коммите ff39b23. Последние неудачные изменения
автоматического увеличения высоты групп уже отменены. Рабочую логику начального
размера отдельного Floating-окна этот план не меняет.

2.1. Независимые нативные окна уже реализованы

Файл:
crates/dock-gpui/src/floating_manager.rs

Существуют:
- PanelWindowRegistry — сопоставление PanelId с native/GPUI окном;
- CompositionHostRegistry — выбор host-панели для FloatingGroup;
- FloatingWindowManager::reconcile() — согласование Core Layout, HWND,

Это сохраняем. Не переносим WindowChain в dock-core и не меняем владение

2.2. Исходная WindowChain на момент аудита была строго одномерной

Файл:
crates/dock-gpui/src/floating_manager.rs

Текущая модель около строк 532–535:

    WindowChainRegistry {
        chains: HashMap<FloatingGroupId, Vec<FloatingGroupId>>,
        chain_by_group: HashMap<FloatingGroupId, FloatingGroupId>,
    }

То есть цепочка — это упорядоченный Vec окон. В ней нет информации о строках,
столбцах, верхних/нижних соседях или ветвлениях.

На исходной точке аудита методы link_before/link_after/link_at/link_sequence_at
умели только вставлять окна до/после другого участника в одной последовательности.
После этапа 1 эти операции заменены направленными связями WindowGrid; текущая
модель находится в crates/dock-gpui/src/window_chain.rs.

Переиспользовать нужно саму идею реестра, идентификацию через FloatingGroupId,
проверки дубликатов, атомарное изменение через копию состояния и очистку
удалённых участников. Внутренний Vec как единственную модель расположения
нужно заменить.

2.3. Геометрия стыковки тоже только горизонтальная

Файл:
crates/dock-gpui/src/floating_manager.rs

Текущие элементы:

Функция frame_geometries_for_bounds() около строки 1094 уже получает реальные

2.4. Перемещение всей цепочки уже работает как общая операция

Файл:
crates/dock-gpui/src/floating_manager.rs

- begin_existing_window_move_with_header() собирает NativeMoveWindow для всех
  участников текущей цепочки;
- tick_native_move() применяет одинаковое смещение dx/dy ко всем HWND;
- finish_native_move() получает конечные bounds всех окон;
- finish_floating_window_chain_move() пересчитывает стыковку и фиксирует
  bounds участников одной операцией истории.

После перехода на сетку нужно заменить только получение участников и
перерасчёт их bounds. Сам механизм общего перемещения и одной истории Undo
переиспользовать.

2.5. Native Resize уже реализован, но распространение изменения только по X

Файл:
crates/dock-gpui/src/floating_manager.rs

- observe_native_resize()/sync_native_resize_bounds() отслеживают системный
  Windows resize;
- NativeResizeSession хранит окно и начальные bounds;
- apply_native_resize_bounds() синхронизирует полученный размер с Core;
- native_resize_right_edge_delta() вычисляет физическое изменение правой
  границы;
- shift_window_chain_after_resize() сдвигает только участников после
  изменённого окна в линейном Vec;
- соседние сдвиги выполняются в той же native-resize history transaction.

Сохраняем системный Resize, NativeResizeSession, синхронизацию bounds и
транзакцию истории. Расширяем расчёт смещений на правую и нижнюю границы и
заменяем линейный список соседей на направленные связи сетки.

2.6. Политика доступных границ Resize сейчас привязана к первому элементу Vec

Файл:
crates/dock-gpui/src/floating_manager.rs
Функция sync_native_resize_edge_policy() около строки 3783:
- левый resize включён только у первого участника линейной цепочки;
- верхний resize выключается у любого участника многоконной цепочки.

Для сетки нужно проверять фактических соседей:
- выключать левую границу, если слева есть сосед;
- выключать верхнюю границу, если сверху есть сосед;
- сохранять доступность правой и нижней внешних границ.

В platform уже существуют set_left_resize_enabled() и set_top_resize_enabled().
Отдельное управление правой/нижней границей сейчас не требуется, поскольку
они остаются доступными. Не добавлять новые native API без подтверждённой
необходимости.

2.7. Z-order уже учитывает наложение соседних окон, но только для горизонтали

Файлы:
- crates/dock-gpui/src/floating_manager.rs;
- crates/platform/src/lib.rs.

floating_groups_in_native_z_order() разворачивает линейную цепочку, чтобы
левое окно оказалось выше правого. synchronize_native_z_order() передаёт
порядок в NativeWindowOps::set_window_chain_z_order(). Windows-реализация
поднимает окна в порядке, который оставляет левое окно сверху.

Эту систему нужно обобщить: окно сверху и окно слева должны получать
приоритет перекрытия относительно окна снизу/справа. Это необходимо не
только при первом соединении, но и после активации любого окна, reconcile(),
перемещения и изменения размера.

2.8. DragHost уже разделяет перенос содержимого и перенос целого окна

Файлы:
- crates/dock-gpui/src/drag_host_manager.rs;
- crates/dock-gpui/src/floating_manager.rs.

floating_window_chain_target() сейчас переводит PanelTab/GroupGrip/
DockAreaHeader drop на Left/Right стороны Floating в операцию присоединения
WindowChain. DragHost сначала создаёт отдельный FloatingGroup через FreeArea,
затем join_created_groups_to_chain() добавляет новое окно в цепочку.

Для целого Floating окна NativeMoveTarget::FloatingChain также создаётся

======================================================================
3. ЦЕЛЕВАЯ МОДЕЛЬ WINDOWCHAIN GRID
======================================================================

Не рекомендуется делать WindowChain как Vec<Vec<FloatingGroupId>> с общей
высотой строк и общей шириной столбцов. У окон независимые размеры; обычная
матрица заставит соседние окна делить высоту/ширину по строкам и столбцам и
может вернуть ту же проблему, от которой мы уходим.

Предлагаемая модель — разреженная двумерная сетка смежности:

    WindowGrid
      members: FloatingGroupId -> WindowGridNode
      links: связи между соседними окнами

    WindowGridLink
      first: FloatingGroupId
      second: FloatingGroupId
      direction: Right | Below

Направление хранится канонически:
- Right: second расположен справа от first;
- Below: second расположен ниже first.

Обратные направления Left/Above выводятся из той же связи. Если сценарии
потребуют нескольких окон вдоль одной стороны (например, два маленьких окна
под одним широким), модель связей должна поддерживать несколько связей на
одной стороне, а не жёстко ограничивать узел одним соседом.

Зачем сетка смежности, а не фиксированная матрица:
- каждое окно сохраняет собственные width/height;
- можно строить неполные строки, столбцы и Т-образные соединения;
- можно вставлять новое окно в выбранную сторону существующего;
- нет общего row height/column width;
- можно находить только восточную или южную область, которую нужно переместить
  при Resize конкретной границы.

Инварианты модели:
1. FloatingGroupId встречается в одной сетке не более одного раза.
2. Участник сетки всегда существует в Core Layout и имеет активный HWND host.
3. Связь всегда двусторонне согласована: если B справа от A, обратная связь
   говорит, что A слева от B.
4. Нельзя создавать дублирующие связи, связь окна с самим собой или соединение
   двух уже связанных областей, которое создаёт конфликт геометрии.
5. Вставка целой сетки в сторону окна сохраняет внутренние связи исходной сетки.
6. Удаление участника не должно оставлять висячие ссылки. Соседи соединяются
   напрямую либо остаются раздельными, если такое соединение конфликтует с
   геометрией. Это правило отдельно покрывается тестами.
7. Сетка не определяет размеры окон. Она определяет отношения, порядок
   перемещения, порядок Z и правила сохранения соприкосновения.

До написания production-кода нужно отдельно утвердить поведение вставки в
уже занятую сторону и поведение разных ширин при вертикальной стыковке.
Нельзя решать эти случаи случайным изменением bounds.

======================================================================
4. ГЕОМЕТРИЯ И ПЕРЕКРЫТИЕ ШАПОК
======================================================================

4.1. Горизонтальная стыковка

Сохранить уже работающий принцип: видимые DWM-границы соседних HWND должны
соприкасаться с учётом невидимых resize borders. Использовать существующие
window_rect(), visible_frame_rect(), scale_factor() и NativeFrameGeometry.

4.2. Вертикальная стыковка

Нижнее окно должно заходить под верхнее ровно на высоту composition header.
Шапка нижнего окна остаётся отрисованной, но перекрыта HWND верхнего окна.

При расчёте вертикального положения недостаточно использовать только
outerHeight или просто вычесть число из origin.y. FloatingGroup.bounds хранит
физический origin внешнего окна и логический размер client area. Поэтому
нужно учитывать реальное начало client area относительно outer HWND.

Геометрический принцип:

    clientTop(B) = clientBottom(A) - headerOverlap

    outerTop(B) = clientTop(B) - clientTopInset(B)

Где:
- clientBottom(A) — фактическая нижняя граница клиентской области A в
  физических пикселях;
- clientTopInset(B) — расстояние от внешнего верха HWND B до начала его
  клиентской области;
- headerOverlap — физический размер шапки, полученный из общей метрики и DPI.

Для расчёта следует использовать существующие NativeWindowOps:
window_rect(), client_origin(), client_size(), scale_factor(). DWM visible
frame продолжает использоваться для соприкосновения внешних видимых границ.
Не смешивать физические координаты HWND с логическими размерами Core.

При трёх окнах:
- B размещается относительно нижней клиентской границы A с перекрытием шапки;
- C размещается относительно нижней клиентской границы B с таким же
  перекрытием;
- размеры B и C не изменяются.

4.3. Z-order — обязательная часть геометрии

Положение окон само по себе не скрывает нижнюю шапку. Верхнее окно должно
быть выше нижнего в native Z-order. Порядок должен восстанавливаться:
- после соединения;
- после активации любого участника;
- после перемещения всей сетки;
- после Resize;
- после reconcile/пересоздания host.

Приоритет наложения: верхнее/левое окно над нижним/правым. Для сетки нужен
детерминированный порядок обхода узлов, который не зависит от порядка обхода
HashMap.

  управления левым/верхним общим resize edge недостаточно.

Реализованные требования:
1. Системный Windows resize и NativeResizeSession сохранены.
2. Оставить native_resize_right_edge_delta(); добавить аналогичный расчёт
   изменения нижней границы.
3. Для правой границы найти восточную область сетки, которую нужно сдвинуть.
4. Для нижней границы найти южную область сетки, которую нужно сдвинуть.
5. Все смещения рассчитывать относительно фактических физических границ,
   используя scale factor и client/native bounds.
6. Соседние окна получают только новые origin; их Size остаётся прежним.
7. Если изменён угол, объединить смещения X/Y в один конечный bounds на HWND.
8. Не отправлять одному FloatingGroup несколько противоречивых команд.
9. Primary resize и все зависимые Move/ResizeFloatingBounds должны оставаться
   внутри одной native resize history transaction и одного согласованного flush.
10. Сохранять действующие Core minimum size для изменяемого FloatingGroup.
    Минимумы соседних FloatingGroup не суммировать.
11. Для общего левого ребра отключать левую границу окна справа; для общего
    верхнего ребра отключать верхнюю границу окна снизу.
12. Правая и нижняя внешние границы остаются доступными для Resize.
13. При resize последнего участника по направлению соседей нет — никого не
    перемещать.
14. При ограничении минимальным размером сдвигать соседей на фактическую
    принятую Core-границу, а не на сырое значение, предложенное HWND.

Приёмка после локальной сборки и тестов:
- resize A справа двигает только окна справа;
- resize A снизу двигает только окна ниже;
- размеры соседей не меняются;
- resize среднего окна не двигает окна до него;
- нижняя шапка остаётся перекрытой после изменения высоты верхнего окна;
- угловой resize не создаёт двойного смещения;
- отсутствуют циклы синхронизации HWND/Core.

Реализация, проверки и ручные критерии приёмки этапа перечислены в разделе
«Текущий прогресс реализации» выше. Локальная сборка и ручные проверки

ЭТАП 8. РЕГРЕССИОННЫЕ СЦЕНАРИИ И ПОЛИРОВКА

Основные unit-тесты чистых модулей:
- связь во всех четырёх направлениях;
- соединение двух сеток с сохранением внутренних связей;
- вставка между существующими соседями;
- удаление углового, среднего и связующего окна;
- корректная декомпозиция сетки после удаления соединителя;
- горизонтальная и вертикальная формулы с DWM inset/client offset;
- fractional DPI;
- направленный Resize с сохранением размеров соседей;
- угловой Resize;
- стабильный порядок Z;
- повторный layout/reconcile не меняет рассчитанные bounds;
- неверная связь/цикл/дублирующий участник отклоняются без частичного изменения.

Ручная проверка пользователем:
1. Два окна: A слева B и A справа B.
2. Два окна: A сверху B и A снизу B.
3. Три окна вертикально: A/B/C; шапки B и C перекрыты.
4. Три окна горизонтально: A/B/C; прежнее поведение не сломано.
5. Сетка 2x2 и Т-образная сетка с независимыми размерами.
6. Перетаскивание всей сетки за шапку каждого участника.
7. Resize правой и нижней границ первого/среднего/последнего окна.
8. Угловой Resize.
9. Активация каждого окна по очереди; Z-order не инвертируется.
10. Разные ширины при вертикальном Drop:
    - перетаскиваемое окно шире целевого — перетаскиваемое сужается до ширины
      целевого, целевое не меняется;
    - перетаскиваемое окно уже целевого — перетаскиваемое расширяется до ширины
      целевого, целевое не меняется;
    - в обоих случаях нижняя шапка полностью перекрывается; максимальная ширина
      всей сетки не вычисляется.
11. Разные DPI/мониторы.
12. Извлечение Tab/Group и закрытие окна из середины сетки.
13. Undo/Redo, Escape/cancel и повторный reconcile.
14. Обычный внутренний Dock Group/Tab между композициями по-прежнему работает.

ЭТАП 9. МЕТРИКИ И ФОРМУЛЫ — ТОЛЬКО ПОСЛЕ СТАБИЛЬНОЙ РАБОТЫ СЕТКИ

Сейчас не менять DockMetrics/ThemeMetrics и не затевать рефакторинг формул.
Вернуться к ним после того, как четыре направления, Resize и Z-order работают.

В финальном этапе:
1. Определить единый источник высоты composition header в ThemeMetrics.
2. На границе GPUI преобразовывать ThemeMetrics в DockMetrics. Не добавлять
   зависимость dock-core от ui crate.
3. Удалить дублирующие значения высоты шапки из других конфигураций.
4. Все места отрисовки, hit-test, минимумов и WindowGrid geometry должны
   использовать один и тот же metric.
5. Формула вертикального перекрытия и resize reflow не должны содержать
   собственные числа 28/32 или отдельные поправки.
6. Добавить контролируемый путь обновления DockMetrics в DockController,
   увеличить metrics_revision, сбросить rect caches и пересчитать bounds/Z-order
   существующих WindowGrid после изменения высоты шапки.
7. Повторить тесты стыковки на нескольких значениях header height, в том числе
   меньше текущего временного значения. Не должно появляться зазоров.
8. Убедиться, что обычные высоты Column header, Group header и Tab strip —
   разные сущности и не смешиваются в одну настройку.

Критерий готовности: изменение одной настройки высоты шапки меняет её
отрисовку, hit-zone и перекрытие уже существующих и новых окон без зазоров.

7. ЧЕГО НЕ ДЕЛАТЬ
======================================================================

- Не объединять разные FloatingGroup в один Core DockArea ради вертикальной
  стыковки.
- Не складывать минимальные высоты разных Floating-окон.
- Не менять размеры соседних окон при Resize другого окна.
- Не делить размеры окон на общие row height/column width.
- Не выбирать максимальную ширину участников при вертикальной стыковке:
  перетаскиваемое окно принимает ширину конкретного целевого окна, а цель
  сохраняет свою ширину.
- Не возвращать предыдущую попытку автоматического роста групп через
  FloatingColumnSizingSnapshot.
- Не вводить флаг hide_header для каждого нижнего окна.
- Не пересоздавать HWND/GPUI Window ради появления/скрытия шапки.
- Не переписывать уже работающий horizontal WindowChain заново; сначала
  сохранить его тестами и затем обобщить его операции.
- Не смешивать целое окно и внутренний Panel/Group drop.
- Не менять Core sizing и ThemeMetrics одновременно с начальной реализацией
  двумерных связей.
- Не расширять platform API заранее, если текущие set_left_resize_enabled()
  и set_top_resize_enabled() уже решают управление общими границами.
- Не запускать cargo build/test/clippy от агента. Проверки выполняет пользователь
  локально после каждого завершённого этапа.
- Не создавать или переключать GitHub-ветки без прямой просьбы пользователя.

8. ПОРЯДОК РЕАЛИЗАЦИИ И ПРИЁМКА
======================================================================

Работать строго по одному этапу за раз:

1. Подготовить модель WindowGrid и чистые тесты.
2. Получить от пользователя подтверждение сборки/тестов.
3. Подключить четыре направления Drop.
4. Получить подтверждение.
5. Подключить геометрию и перекрытие шапок.
6. Получить подтверждение визуальной стыковки.
7. Подключить Z-order и движение всей сетки.
8. Получить подтверждение.
9. Подключить вертикальный Resize и распространение смещений.
10. Получить подтверждение всех сценариев Resize.
11. Закрытие/извлечение/reconcile и регрессионная проверка.
12. Только затем централизовать ThemeMetrics/DockMetrics и формулы.

После каждого этапа указывать:
- что переиспользовано;
- что обобщено;
- какие модули/типы созданы и зачем;
- какие локальные проверки должен выполнить пользователь.

ИТОГОВЫЙ ПРИНЦИП:
FloatingGroup владеет собственным содержимым и размером окна.
WindowGrid знает, какие окна находятся слева/справа/сверху/снизу, как
перемещать их вместе, как сохранять стыки при Resize и как перекрывать
нижние/правые шапки правильным Z-order. Core Layout не превращается в сетку
нативных окон. Метрики шапки централизуются только после стабилизации
геометрии и взаимодействий.
