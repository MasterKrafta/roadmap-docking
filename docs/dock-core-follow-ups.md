# Отложенные пункты аудита docking

Этот файл фиксирует задачи, к которым нужно вернуться после завершения текущей интеграции drag-and-drop. Пункты ниже **не считаются подтверждёнными функциональными дефектами**. Не менять рабочую реализацию только ради устранения замечания статического аудита.

## Порядок работы

1. Сначала завершить интеграцию drag-and-drop в `dock-gpui`.
2. После этого прогнать проверки проекта и проверить реальные сценарии перетаскивания.
3. Только затем вернуться к оптимизациям `dock-core`: сначала измерения, потом изменение реализации.

## 1. Интеграция drag-and-drop в GPUI

**Статус:** следующий пункт в работе.  
**Область:** преимущественно `crates/dock-gpui`.

В `dock-core` уже существуют `DragSession`, `prepare_drop_resolver()` и `DropZoneResolver::resolve()`. GPUI-адаптер ещё не подключает полный путь обработки drag-and-drop: запуск сессии, разрешение цели при движении указателя и завершение перетаскивания.

Что нужно сделать:

- Подключить существующий API `DragSession` и `DropZoneResolver` к контроллеру и обработчикам указателя в GPUI.
- Повторно разрешать целевую drop-позицию при движении указателя, используя подготовленный resolver без пересоздания зон на каждом движении.
- Обновлять `DragOverlay` и активную подсветку зоны.
- При отпускании указателя применить итоговую команду; поддержать отмену жеста.
- Пересоздавать resolver при изменении layout, геометрии или метрик, чтобы не использовать устаревший снимок.

**Важно:** не переписывать `dock-core` заранее. Менять ядро только при обнаружении конкретной недостающей возможности API.

**Критерии завершения:** проверить успешный drop, отсутствие допустимой цели, отмену, отпускание указателя над актуальной целью и отсутствие устаревшего preview.

## 2. Линейный поиск родителя узла

**Статус:** отложено до завершения GPUI drag-and-drop и появления измерений.  
**Область:** `crates/dock-core`.

`Layout::find_parent` перебирает узлы модели и проверяет их дочерние узлы, поэтому поиск имеет линейную стоимость. Постоянный parent-index не добавлен: кэш только по `Layout::version` может устаревать, поскольку внутри транзакции структура `candidate Layout` меняется до фиксации новой версии.

Что нужно сделать при возвращении к пункту:

- Оценить, насколько часто `find_parent` вызывается в горячих путях и насколько ощутима его стоимость на больших раскладках.
- Если измерения оправдывают оптимизацию, выбрать индекс с чётким временем жизни и механизмом актуализации при структурных изменениях.
- Гарантировать корректность при перемещении, удалении и замене узлов, а также при неудачной транзакции и откате.

**Не делать:** вводить долгоживущий индекс или кэш только по revision без доказанной согласованности с деревом. Помнить, что уже имеющийся временный индекс для расчёта drop-зон не равнозначен постоянному индексу для всех вызовов `find_parent`.

**Критерии завершения:** тесты согласованности индекса после структурных операций и транзакционных ошибок; бенчмарк до/после на типичной и большой раскладке.

## 3. Линейная стоимость транзакции Layout

**Статус:** отложено до профилирования.  
**Область:** `crates/dock-core`.

`Layout::apply` клонирует модель-кандидат для транзакционного выполнения команды. Нормализация выполняет предварительную валидацию состояния, изменяет структуру, а затем проводит итоговую полную валидацию. Стоимость этих проходов растёт вместе с размером модели (как минимум линейно по числу узлов для соответствующих обходов).

Сейчас это известная стоимость выбранной стратегии, а не подтверждённый функциональный дефект.

Что нужно сделать при возвращении к пункту:

- Измерить время `Layout::apply` на типичных и искусственно больших раскладках, включая разные классы команд.
- Определить, какая часть затрат существенна: клонирование, предварительная валидация, нормализация или итоговая валидация.
- Рассматривать оптимизацию только при подтверждённом узком месте и после формулировки контракта корректности.

**Не делать:** убирать клонирование или защитные проходы без замеров, тестов и отдельного контракта корректности.

**Обязательные гарантии:** атомарность команды, отсутствие частично применённых изменений при ошибке, корректная нормализация, полная проверка итогового состояния и сохранение существующего поведения команд.

**Критерии завершения:** воспроизводимый baseline и сравнение до/после; тесты успешных команд, отказов и сохранения состояния при ошибке; все стандартные проверки проекта проходят.

## Проверки перед закрытием любого пункта

После каждого изменения выполнить локально из корня workspace:

```powershell
cargo fmt --all -- --check
cargo check --workspace --all-targets --all-features --locked
cargo test --workspace --all-features --locked
cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
```

Не отмечать пункт завершённым, пока нет фактического вывода успешных проверок. Оптимизации закрывать только при наличии измерений и подтверждения эквивалентности поведения.
