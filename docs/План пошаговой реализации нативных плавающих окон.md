# Пошаговый план реализации нативных плавающих окон (tear-off)

**Дата:** 1 ноября 2026  
**Ветка:** `main`  
**Назначение:** рабочая последовательность внедрения. Подробные требования и ограничения остаются в [основном ТЗ](./ТЗ%20перевод%20dock-gpui%20на%20нативные%20плавающие%20окна%20(tear-off).md). Этот документ отвечает на другой вопрос: **в каком порядке выполнять работу, что проверять после каждого шага и когда переходить дальше**.

---

## 1. Что уже проверено и что ещё не проверено

### Подтверждено экспериментами

Эксперимент находится в [`tearoff/any_view_transfer.rs`](../tearoff/any_view_transfer.rs).

1. Для каждой панели создаётся один `Entity` и один `AnyView`. В логах при переносах сохраняются исходные `EntityId`.
2. Одна и та же панель поочерёдно отображается в разных нативных окнах GPUI.
3. Неактивная вкладка может оставаться в реестре представлений, не отображаясь в данный момент, а затем снова монтироваться.
4. Созданы главное окно и два самостоятельных floating-окна A и B.
5. Проверено присоединение панели из одного floating-окна к другому: исходное окно скрывается, целевое показывает общую группу вкладок.
6. Проверено обратное извлечение панели в ранее освобождённое floating-окно.
7. Пользователь подтвердил, что операции через экспериментальные кнопки выполняются быстро, без заметных задержек; текст, счётчики и `EntityId` сохраняются.

### Пока не проверено

- Реальное перетаскивание мышью вместо экспериментальных кнопок.
- Выполнение тех же операций через настоящий `DockCore::Layout` и его команды. Текущая модель двух floating-групп в эксперименте упрощённая и не заменяет Core.
- Попадание курсора в drop-зоны разных окон, подсветка цели и корректное преобразование координат.
- Отмена перетаскивания через Escape и единая транзакция Undo.
- Перемещение между мониторами с разным DPI, нативный resize и восстановление workspace.
- Полный startup/close lifecycle рабочего приложения с произвольным количеством сохранённых floating-композиций.

**Вывод:** доказана техническая возможность переносить один и тот же GPUI-view между двумя native floating-окнами. Это не означает, что основной docking pipeline уже реализован.

## 2. Целевая модель, которую не меняем по ходу этапов

1. **Один `DockController` и один `Layout` на рабочее пространство.** Все окна показывают разные части одной модели. Нельзя создавать отдельный Core/Layout для каждого floating-окна.
2. **Главное окно остаётся отдельным.** В нём находятся основная рабочая область, canvas и пристыкованные к главному окну композиции.
3. **Одна floating-композиция — одно нативное окно.** Если в композиции лежат две панели как вкладки, это одно floating-окно с двумя вкладками, а не два окна.
4. **Одна открытая панель — один `Entity` и один `AnyView`.** Представление удерживается в реестре, даже если вкладка неактивна. В один момент один и тот же view может быть смонтирован только в одном окне.
5. **Стыковка не закрывает панель.** При объединении двух floating-композиций их узлы объединяются в Core; окно-источник скрывается/освобождается, а его панель продолжает жить в общем реестре.
6. **Извлечение панели из группы создаёт отдельную floating-композицию в Core.** Для неё менеджер показывает отдельное нативное окно и переносит туда прежний `AnyView`.
7. **Меню — каталог доступных типов панелей, а не список готовых окон.** Панели и окна создаются только для тех экземпляров, которые реально открыты в текущем workspace. Не создавать 100 окон из-за 100 пунктов меню.
8. **Не вводить пул окон заранее.** Сначала создавать/переиспользовать окно по фактической операции. К предварительной подготовке и пулу возвращаться только при измеренной задержке.

## 3. Последовательность реализации

Каждый этап выполнять отдельно. После изменения — остановиться, передать результат на локальную проверку и не начинать следующий этап, пока текущий не подтверждён.

### Этап 0. Зафиксировать проверенный прототип

**Цель:** сохранить рабочий пример как контроль поведения GPUI.

- [ ] Не смешивать код `tearoff/any_view_transfer.rs` с production-кодом `dock-gpui`.
- [ ] Сохранить в эксперименте две отдельные панели A/B, два floating-host и главное окно.
- [ ] Сохранить логирование `EntityId` и места отображения панели.
- [ ] После будущих изменений сверять поведение production с этим экспериментом.

**Готово, когда:** эксперимент остаётся воспроизводимым и служит эталоном переноса GPUI-view между окнами. Новые возможности в эксперимент добавлять только при необходимости проверить конкретный риск.

### Этап 1. Подготовить Core для независимой геометрии окон

**Цель:** перестать считать floating-группы частью viewport главного окна.

Основные файлы:
- `crates/dock-core/src/compute_rects.rs`
- `crates/dock-core/src/compute_rects/`
- `crates/dock-core/src/layout.rs`
- `crates/dock-core/src/layout_rects.rs`
- тесты геометрии в `crates/dock-core/src/`

Задачи:
- [ ] Разделить расчёт главной области и геометрии отдельной floating-группы.
- [ ] Добавить расчёт геометрии одной floating-группы в локальных координатах её окна: начало координат (0, 0).
- [ ] Не ограничивать размер/позицию floating-группы viewport главного окна.
- [ ] Убедиться, что hit-test и drop-зоны получают снимок геометрии именно того окна, в котором выполняется взаимодействие.
- [ ] Не допускать, чтобы ошибка геометрии одной floating-группы ломала расчёт главного окна или других floating-групп.

**Проверка:** unit-тесты на floating-группу за пределами главного viewport, на размер больше главного окна и на независимые локальные координаты двух floating-групп.

**Готово, когда:** Core способен выдать отдельный корректный `LayoutRects` для главного окна и для каждой floating-композиции без взаимного влияния.

### Этап 2. Подготовить Core-команды и drag-семантику

**Цель:** обеспечить однозначные операции отрыва, стыковки и извлечения.

Основные файлы:
- `crates/dock-core/src/dock_command.rs`
- `crates/dock-core/src/command_value.rs`
- `crates/dock-core/src/command_application.rs`
- `crates/dock-core/src/drag_drop_resolution.rs`
- `crates/dock-core/src/drag_session.rs`
- соответствующие Core-тесты

Задачи:
- [ ] Сделать так, чтобы результат команды `Float` позволял адаптеру получить ID только что созданной `FloatingGroup`.
- [ ] Зафиксировать семантику перетаскивания floating-группы через `FloatingCapture`: отсутствие drop-цели означает «оставить окно плавающим», а не потерять состояние или ошибочно отменить успешный отрыв.
- [ ] Поддержать drop одной floating-группы в другую: центр — вкладка, стороны — разделение согласно существующим правилам Core.
- [ ] Поддержать извлечение отдельной панели/вкладки из floating-композиции в новую floating-группу.
- [ ] Сохранить одну транзакцию истории на весь жест: начало drag → отрыв/перенос → drop; Escape откатывает весь жест.
- [ ] Не добавлять новые команды, если нужное поведение можно корректно выразить существующими командами.

**Проверка:** unit-тесты без GPUI: Float возвращает ID; floating A объединяется с B; отдельная вкладка извлекается; пустой drop оставляет окно плавающим; Escape отменяет операцию; Undo возвращает прежнее дерево.

**Готово, когда:** все требуемые операции можно выполнить на Core-модели без окон и UI.

### Этап 3. Подключить реестр представлений панелей

**Цель:** перенести подтверждённую в эксперименте схему в production-адаптер.

Основной файл:
- `crates/dock-gpui/src/controller.rs`
- при необходимости `crates/dock-gpui/src/registry.rs`
- создание и отображение панелей в `crates/dock-gpui/src/dock_host.rs`

Текущее состояние: в `DockController` уже объявлено поле `panel_views: HashMap<PanelId, AnyView>`, но на текущем состоянии репозитория оно только инициализируется пустой картой. Жизненный цикл реестра ещё предстоит подключить.

Задачи:
- [ ] Реализовать явную регистрацию view при создании экземпляра панели.
- [ ] Хранить один `Entity`/`AnyView` на каждый открытый `PanelId`.
- [ ] Не удалять view при переключении вкладки, стыковке, отстыковке или переносе между окнами.
- [ ] Удалять view только при настоящем закрытии экземпляра панели.
- [ ] При рендере выбирать один host для каждого view: главное окно либо конкретный floating-host.
- [ ] Не монтировать один `AnyView` одновременно в двух окнах.
- [ ] Проверить восстановление ввода, курсора, выделения и фокуса после повторного монтирования.

**Проверка:** сначала на двух панелях A/B: открыть обе, переключать вкладки, объединять их, извлекать неактивную вкладку и возвращать обратно. Сверять `EntityId`, текст и внутреннее состояние.

**Готово, когда:** production-адаптер сохраняет те же свойства, которые уже показал `any_view_transfer.rs`.

### Этап 4. Подготовить платформенные операции Windows

**Цель:** изолировать Win32 и не допустить `unsafe` в `dock-gpui`.

Использовать существующий:
- `crates/platform/Cargo.toml`
- `crates/platform/src/lib.rs`

Сейчас `crates/platform` — практически пустой каркас: он не подключён как зависимость `dock-gpui` и не указан в корневом списке workspace. Поэтому сначала подключить существующий crate, а не создавать рядом ещё один `dock-native`.

Задачи:
- [ ] Подключить `crates/platform` к workspace и к GPUI-адаптеру.
- [ ] Ввести небольшой контракт native-операций, не протаскивая HWND в Core.
- [ ] Реализовать получение native handle, owner, show/hide, activate, move и resize окна.
- [ ] Добавить получение позиции курсора, состояния кнопок и Escape.
- [ ] Добавить определение окна под курсором, DPI и рабочих областей мониторов.
- [ ] Добавить минимальный размер окна, если закреплённый GPUI API не обеспечивает его динамически.
- [ ] Оставить безопасную заглушку для не-Windows платформ.
- [ ] Сохранить `#![forbid(unsafe_code)]` в `dock-gpui`; все Win32 `unsafe` держать внутри платформенного crate с пояснениями безопасности.

**Проверка:** небольшая проверка каждого native-вызова на окнах, созданных GPUI. Пока не подключать drag-механику.

**Готово, когда:** GPUI-слой может управлять native-окнами через узкий API, а Core ничего не знает о Win32.

### Этап 5. Создать `FloatingHost` для одной композиции

Задачи:
- [ ] Превратить текущий внутренний `FloatingWindowView` в корневой `FloatingHost: Render` для native-окна.
- [ ] Передавать в host ID floating-группы и её собственную геометрию.
- [ ] Рендерить дерево группы в локальных координатах окна с origin (0, 0).
- [ ] Переиспользовать существующие `ColumnView`, `GroupView`, `PanelHost`, `SplitterView` и tab-компоненты.
- [ ] Не создавать внутри host копию Layout или контроллера.

**Проверка:** открыть один отдельный PopUp и отобразить в нём одну floating-группу из общего Layout. Затем — две панели как вкладки одной группы.

**Готово, когда:** floating-композиция полноценно рендерится в отдельном native-окне, а её модель остаётся в общем Core.

### Этап 6. Создать `FloatingWindowManager` и реестр окон

**Цель:** связать реальные floating-группы Core с native-окнами.

Новый файл:
- `crates/dock-gpui/src/floating_manager.rs`

Изменения:
- `crates/dock-gpui/src/lib.rs`
- `crates/dock-gpui/src/controller.rs`
- `crates/dock-gpui/src/dock_host.rs`
- `crates/dock-gpui/Cargo.toml` и workspace — только если понадобятся согласованные зависимости

Задачи:
- [ ] Ввести `WindowRegistry`: `FloatingGroupId → WindowHandle + native handle`.
- [ ] Связать открытые панели с текущей группой/окном отображения.
- [ ] Реализовать `reconcile()`: сравнивать актуальные `Layout.floating_groups` с реестром окон.
- [ ] Создавать окно для новой floating-группы; скрывать и повторно использовать освободившееся окно после объединения групп.
- [ ] При удалении floating-группы закрывать/освобождать лишнее окно по согласованной политике.
- [ ] Подписать manager на изменения Layout и не создавать отдельную копию состояния.
- [ ] Сначала проверить ручное создание двух окон A/B и объединение, затем подключать автоматическое создание по Core-событиям.

**Startup для production:** не опираться на удалённый `crates/dock-experiment`. Сверить поведение с закреплённой ревизией GPUI и текущим прототипом:
1. восстановить Layout workspace;
2. создать скрытое главное окно;
3. создать скрытые floating-окна только для реально сохранённых floating-композиций;
4. дождаться первичного draw каждого root view (в закреплённом GPUI `App::open_window` выполняет draw до возврата);
5. назначить owner и скорректировать Z-order;
6. показать главное окно и подготовленные floating-окна.

**Проверка:** workspace с двумя floating-группами создаёт два native-окна; объединение групп скрывает одно; извлечение снова показывает освобождённый host. Пункты меню, которые не открыты в Layout, не создают ни view, ни окно.

**Готово, когда:** количество и видимость native-окон всегда соответствуют floating-композициям общего Layout.

- [ ] Удалить построение и рисование floating-слоя внутри главного viewport.
- [ ] Передавать `FloatingHost` только данные своей floating-группы.
- [ ] Сделать геометрию/кэш независимыми для каждого окна (идентификатор окна в ключе кэша).
- [ ] Обеспечить независимые локальные hit-test и drop-zone resolver для главного и каждого floating-окна.

**Проверка:** главное окно не рисует содержимое floating-групп; каждая группа видна только в собственном native-окне. Перемещение или resize одного окна не меняет геометрию другого.

**Готово, когда:** старый in-window floating-слой больше не участвует в production-рендере.

### Этап 8. Реализовать реальный tear-off и перемещение native-окна

**Цель:** заменить экспериментальные кнопки перетаскиванием мышью.

Основные файлы:
- `crates/dock-gpui/src/input/pointer.rs`
- `crates/dock-gpui/src/input/drag.rs`
- `crates/dock-gpui/src/controller.rs`
- `crates/dock-gpui/src/floating_manager.rs`
- native-операции в `crates/platform`

Задачи:
- [ ] Ввести кандидата на drag по заголовку/вкладке/группе.
- [ ] Запускать отрыв после согласованного порога движения.
- [ ] После Core-команды `Float` продолжать тот же жест уже для созданной floating-группы.
- [ ] Перемещать нативное окно средствами OS, не перерисовывая его как абсолютный слой внутри главного окна.
- [ ] На всём протяжении движения проверять окно под курсором, включая другое floating-окно и главное окно.
- [ ] Переводить screen coordinates в локальные логические координаты конкретного окна-цели.
- [ ] Не отменять drag только потому, что фокус перешёл из одного окна GPUI в другое.
- [ ] Escape должен вернуть исходную структуру и положение.

**Проверка по очереди:**
1. оторвать панель из главного дока и переместить её за пределы главного окна;
2. отпустить на пустом месте — она остаётся floating;
3. вернуть её в главный док;
4. перенести floating-окно на другое floating-окно;
5. прервать жест Escape.

**Готово, когда:** реальные мышиные операции проходят без кнопок-помощников, без потери фокуса и с правильной транзакцией Undo.

### Этап 9. Реализовать объединение и извлечение групп между floating-окнами

**Цель:** довести до production проверенный эксперимент с A/B.

Затрагиваемые области:
- Core: `DockFloating`, `Float`, операции с `Tabs`/группами.
- GPUI: `FloatingWindowManager`, `FloatingHost`, `panel_views`, drop overlay и drag pipeline.

Задачи:
- [ ] Drop в центр другой floating-группы объединяет панели в одну tab-группу.
- [ ] Drop на сторону создаёт split согласно правилам Core.
- [ ] После объединения source floating-группа исчезает из Layout, её native-окно скрывается/освобождается, target-окно продолжает показывать объединённое дерево.
- [ ] Извлечение отдельной вкладки создаёт новую floating-группу и показывает её в другом окне.
- [ ] Если в исходной группе остались вкладки, окно остаётся на месте и показывает оставшуюся группу.
- [ ] При извлечении последнего узла/закрытии группы manager корректно обрабатывает пустую композицию.
- [ ] Перенос A ↔ B работает симметрично.
- [ ] Состояние неактивных и активных панелей сохраняется; ни один `Entity`/`AnyView` не создаётся заново из-за стыковки.

**Проверка:** A в окне 1 и B в окне 2 → объединить в окне 1 → получить A/B в одном окне → извлечь B в окно 2 → повторить в обратном направлении. Затем повторить через настоящий drag.

**Готово, когда:** операции между floating-окнами используют настоящий Core Layout, а результат совпадает с моделью, проверенной экспериментом.

### Этап 10. Resize, DPI и несколько мониторов

**Цель:** обеспечить нативное изменение размера и корректную геометрию на разных мониторах.

Основные области:
- `crates/platform`
- `crates/dock-gpui/src/floating_manager.rs`
- `crates/dock-gpui/src/controller.rs`
- `crates/dock-gpui/src/input/resize.rs`
- `crates/dock-core/src/floating_group.rs`

Задачи:
- [ ] Включить native resize-рамку и минимальный размер по ограничениям содержимого.
- [ ] Синхронизировать bounds native-окна с Core.
- [ ] Объединить непрерывный resize в один шаг Undo.
- [ ] Обрабатывать смену DPI при переходе между мониторами.
- [ ] Проверить, что окно не пропадает и не урезается до viewport главного окна.
- [ ] Проверить, нужна ли принудительная перерисовка во время модального resize-цикла; добавлять timer только при воспроизводимой проблеме и гарантировать его остановку.

**Проверка:** resize за все края/углы, минимальный размер, перенос между мониторами с разным масштабом, отсутствие скачков и обрезания.

**Готово, когда:** native bounds и Core bounds синхронны, а содержимое остаётся корректным при изменении DPI и размера.

### Этап 11. Persistence и восстановление workspace

**Цель:** сохранять фактическую структуру дока и позиции native-окон.

Основные файлы:
- `crates/dock-gpui/src/persistence.rs`
- `crates/dock-core/src/workspace_file.rs`
- `crates/dock-core/src/workspace_types.rs`
- `crates/dock-gpui/src/floating_manager.rs`

Задачи:
- [ ] Сохранять состав floating-композиций, их bounds и порядок/состояние вкладок.
- [ ] Зафиксировать единую систему координат и единицы для сохранения bounds (экранные физические координаты и логический размер нельзя смешивать неявно).
- [ ] При загрузке не clamp-ить floating-окна к viewport главного окна.
- [ ] Проверять, что сохранённое окно попадает в рабочую область существующего монитора; если нет — безопасно переместить его в доступную рабочую область.
- [ ] После восстановления Layout выполнить `FloatingWindowManager::reconcile()`.
- [ ] Создавать при запуске окна только для реальных floating-композиций восстановленного workspace.

**Проверка:** сохранить workspace с несколькими floating-группами, вкладками и разными bounds; перезапустить; проверить восстановление структуры и положения. Отдельно проверить отключённый монитор.

**Готово, когда:** сохранённый workspace восстанавливается без потери панелей и без привязки floating bounds к размеру главного окна.

### Этап 12. Закрытие, фокус и полировка

**Цель:** привести поведение окон к ожидаемому поведению приложения.

Задачи:
- [ ] Закрытие отдельной панели выполняет Core-команду и удаляет её view из реестра только после успешного закрытия.
- [ ] Закрытие последней панели в floating-композиции корректно закрывает/освобождает её native host.
- [ ] Закрытие главного окна завершает или закрывает дочерние floating-окна согласованно; minimize главного окна обрабатывает owner-цепочку.
- [ ] Проверить фокус, клавиатуру, clipboard, текстовый ввод, выделение и прокрутку при переносах.
- [ ] Проверить context menu и flyout в floating-окнах.
- [ ] Удалить старый in-window floating-код и устаревшие тесты только после того, как новые сценарии проходят.
- [ ] Обновить публичные exports и документацию слоёв.

**Готово, когда:** закрытие, minimize, focus и ввод не оставляют «висячих» окон, view или записей менеджера.

## 4. Приёмка всей реализации

Всю систему считать готовой только после проверки полного набора сценариев:

- [ ] Старт workspace с главным окном и несколькими сохранёнными floating-композициями.
- [ ] Создание панели из меню: появляется только выбранный экземпляр; остальные пункты меню не создают окна.
- [ ] Отрыв панели из главного дока мышью.
- [ ] Возврат панели в главный док.
- [ ] Перенос floating-композиции в другую floating-композицию: вкладкой и split.
- [ ] Извлечение неактивной вкладки из floating-группы в отдельное окно.
- [ ] Обратное встраивание этой панели в группу.
- [ ] Симметричные операции A → B и B → A.
- [ ] Escape, drop на пустое место, Undo/Redo.
- [ ] Сохранение Entity state, текста, курсора, выделения, прокрутки и фокуса.
- [ ] Resize, minimum size, два монитора с разным DPI.
- [ ] Сохранение/восстановление workspace и поведение при исчезнувшем мониторе.
- [ ] Minimize/close главного окна и закрытие последней панели.

## 5. Правила выполнения работ

1. **Один этап — один небольшой набор изменений.** Не переписывать одновременно Core, рендер, окна и ввод.
2. **После каждого этапа — локальная проверка пользователем.** Следующий этап начинается только после результата проверки и исправления обнаруженных ошибок.
3. **Core тестируется отдельно от GPUI.** Сначала подтверждаем модель и команды, затем подключаем окна и ввод.
4. **Прототип не превращать в production-архитектуру копированием.** Из него переносим подтверждённые принципы, но не упрощённую модель групп и обработчики-кнопки.
5. **Не добавлять оптимизации без измерений.** Pool/pre-warm окон и дополнительные таймеры — только после подтверждённого узкого места.
6. **Не создавать новые ветки.** Работать небольшими коммитами в текущей ветке `main`.
7. **Не менять публичный API GPUI без необходимости.** Сначала использовать возможности закреплённой ревизии `9cd14daad768fbfaeeac8789f515f9a5f67669a6`.
8. **После каждого изменения фиксировать:** что поменялось, какие сценарии проверены, что осталось открытым.

## 6. Что делать первым

Первый production-шаг после этого плана — **Этап 1: независимая геометрия floating-группы в `dock-core`**. Он не затрагивает GPUI-окна, поэтому его проще проверить изолированно. Перед ним не нужно переписывать `DockHost` или создавать `FloatingWindowManager`.
