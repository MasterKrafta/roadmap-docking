# План переделки Docking: перетаскивание и стыковка
## Цель
Привести механику перетаскивания и стыковки к единой и предсказуемой модели, в которой панель, группа, колонка или целая DockArea могут переноситься между Main Dock и настоящими Floating-окнами.
Должны одинаково работать все сочетания источника и цели:
- Main → Main;
- Main → Floating;
- Floating → Main;
- Floating → Floating.
Различие между Main и Floating должно определять только то, **в каком реальном окне находится цель и в каких локальных координатах рассчитываются её drop-зоны**. Семантика стыковки при этом должна оставаться общей.
## Основные правила архитектуры
1. **Core остаётся единственным владельцем Layout.** GPUI не создаёт параллельное дерево компоновки и не принимает самостоятельных решений о структуре Dock.
2. **Floating — настоящее нативное окно.** У каждого Floating-окна собственные HWND, WindowId, клиентская область и локальные координаты. Это не визуальная панель поверх общего Canvas.
3. **Источник перетаскивания и временное окно переноса — разные понятия.** Например, вкладка остаётся `Panel`, даже если во время tear-off временно отображается в отдельном Floating-окне.
4. **Один набор правил DropTarget для Main и Floating.** Геометрия рассчитывается отдельно для каждого целевого окна, но смысл зон и результат команд должны совпадать.
5. **Не добавлять новые первичные сущности без необходимости.** Сохранять существующую модель `DockArea → Column → Group → Tabs / Panel`. Не вводить `Composition` как новую основную сущность Core.
6. **DropOverlay только отображает результат Core.** UI не должен самостоятельно вычислять или придумывать зоны стыковки.
7. **Не менять уже работающие механизмы вне текущего шага.** Каждый этап выполняется отдельно, с ограниченным набором файлов и понятным результатом.

## Этап 1. Разделить логический источник перетаскивания и временное Floating-окно
**Задача:** устранить потерю исходной сущности во время tear-off.
Сейчас временное Floating-окно в некоторых сценариях начинает выступать как источник перетаскивания. Из-за этого исходная сущность может определяться по форме корня Floating-композиции: например, `FloatingGroup` трактуется как `Group` или `Column`. Такое преобразование теряет исходный смысл операции.
Нужно обеспечить следующее:
- вкладка, которую начали перетаскивать, остаётся `DragPayload::Panel`;
- захват группы остаётся `DragPayload::Group`;
- захват колонки остаётся `DragPayload::Column`;
- перенос всей Main DockArea сохраняет семантику переноса целой DockArea;
- `FloatingGroupId` используется для идентификации временного/текущего Floating-хоста и окна, но не подменяет исходную сущность;
- при маршрутизации к целевому HWND источник не выводится заново из формы корня Floating Layout.
**Основные файлы:**
- `crates/dock-core/src/drag_types.rs`;
- `crates/dock-core/src/drop_types.rs` — только если для сохранения типа источника действительно потребуется корректировка типов;
- `crates/dock-gpui/src/controller.rs`;
- `crates/dock-gpui/src/input_drag.rs`;
- `crates/dock-gpui/src/floating_manager.rs`.
**Критерий готовности:** во всех сценариях можно однозначно определить, что именно перетаскивается, независимо от того, находится ли источник сейчас в Main или уже отображается во временном Floating-окне.
**Не делать на этом этапе:** не перестраивать генерацию drop-зон и не менять правила структурного объединения. Сначала исправить идентичность источника.

## Этап 2. Унифицировать и уточнить иерархию DropTarget
**Задача:** определить полный и непротиворечивый набор целей для стыковки.
Проверить, что цели выражают структурную операцию, а не привязаны к тому, находится ли окно в Main или Floating.
Нужны однозначные варианты для следующих операций:
- добавить панель в конец полосы вкладок существующей группы;
- добавить группу к вкладкам другой группы;
- создать группу выше или ниже существующей группы;
- вставить группу или колонку в свободный слот между колонками;
- пристыковать композицию к краям DockArea;
- оставить перетаскиваемую композицию отдельным Floating-окном.
Отдельно проверить `ColumnSlot`: сейчас его валидация ориентирована на колонку Main Dock. Нужно определить, как тот же структурный слот должен работать для колонки внутри Floating-композиции.
Также нужно проверить, что `DropSource` не теряет различия между переносом Panel, Group и Column.
**Основные файлы:**
- `crates/dock-core/src/drop_types.rs`;
- `crates/dock-core/src/layout/drop_handling.rs`;
- `crates/dock-core/src/layout/command_target_operations.rs`;
- `crates/dock-core/src/layout/group_operations.rs`;
- `crates/dock-core/src/layout/floating_operations.rs`.
**Критерий готовности:** каждая допустимая структурная операция имеет отдельную понятную цель; одна и та же цель применима в Main и Floating, если структура обеих областей это допускает.

## Этап 3. Исправить семантику структурного переноса
**Задача:** гарантировать корректное изменение Layout при переносе объектов разного уровня.
Проверить переносы:
- одной Panel;
- Group с одной вкладкой;
- Group с несколькими вкладками;
- Column с одной Group;
- Column с несколькими Group;
- целой DockArea с одной Column;
- целой DockArea с несколькими Column.
Для каждого случая определить, что именно перемещается целиком, а что можно вложить в существующую структуру.
Обязательные условия:
- порядок вкладок сохраняется;
- порядок групп сохраняется;
- порядок колонок сохраняется;
- при переносе не теряются панели;
- исходная область корректно освобождается;
- недопустимые операции отклоняются до изменения Layout;
- перенос одной Panel не превращается случайно в перенос всей Floating-композиции.
**Основные файлы:** Core-команды и операции в `crates/dock-core/src/layout/`, в первую очередь:
- `drop_handling.rs`;
- `floating_operations.rs`;
- `group_operations.rs`;
- `command_target_operations.rs`.
**Критерий готовности:** для каждого типа источника Core выполняет ровно ту структурную операцию, которую описывает DropTarget.
---
## Этап 4. Пересобрать drop-зоны Main Dock
**Задача:** сделать генерацию зон Main Dock простой, однозначной и согласованной с правилами стыковки.
Ожидаемое поведение:
- **Panel:** добавляется в конец полосы вкладок целевой Group; произвольная вставка между вкладками не нужна, если отдельно не будет принято такое решение;
- **Group:** может объединяться с вкладками целевой Group или создавать соседнюю Group сверху/снизу;
- **Column:** переносится как целая Column в слот между колонками или к внешнему краю Main Dock;
- **DockArea:** переносится как целая композиция, если это предусмотрено текущим сценарием;
- свободная область Main Dock создаёт Floating, а не неявную вставку в случайное место.
Особое внимание уделить общим границам соседних групп: одна координата не должна одновременно давать две конкурирующие цели. Приоритет и порядок генерации зон должны приводить к стабильному результату.
**Основные файлы:**
- `crates/dock-core/src/compute_drop_zones.rs`;
- `crates/dock-core/src/compute_drop_zones/drop_zone_main.rs`;
- `crates/dock-core/src/compute_drop_zones/drop_zone_tree.rs`.
**Критерий готовности:** для каждой точки Main Dock выбирается одна ожидаемая зона; соседние границы не дают случайного результата.
---
## Этап 5. Пересобрать drop-зоны Floating-окна
**Задача:** обеспечить во Floating те же правила, что и в Main Dock, с учётом локальной геометрии конкретного нативного окна.
Проверить:
- добавление Panel в конец вкладок Group внутри Floating;
- объединение Group с другой Group;
- создание Group сверху/снизу;
- вставку Column в допустимый слот Floating-композиции;
- стыковку к допустимым краям Floating;
- корректный свободный drop, при котором окно остаётся Floating.
Генератор должен использовать геометрию целевого Floating Layout, а не координаты Main Dock и не прямоугольник другого Floating-окна.
Нужно отдельно проверить ограничения Photoshop-профиля: например, запрет горизонтального разделения Floating-композиции, если это ограничение действует для выбранного типа структуры.
**Основные файлы:**
- `crates/dock-core/src/compute_drop_zones/drop_zone_floating.rs`;
- `crates/dock-gpui/src/controller_layout_cache.rs`;
- `crates/dock-gpui/src/floating_manager.rs`.
**Критерий готовности:** Floating-окно предлагает те же структурные варианты стыковки, что и Main Dock, в пределах разрешённых ограничений; расчёт выполняется в локальных координатах именно этого окна.
---
## Этап 6. Проверить маршрутизацию между реальными HWND
**Задача:** убедиться, что при перетаскивании событие и drop-зоны принадлежат тому нативному окну, над которым находится курсор.
Маршрут должен работать так:
1. Получить экранную позицию курсора.
2. Определить реальный HWND под курсором среди Main и известных Floating-окон.
3. Исключить HWND исходного окна, когда это необходимо.
4. Преобразовать экранные координаты в локальные координаты найденного окна.
5. Получить DropZoneResolver для Layout именно этого окна.
6. Передать в resolver исходную логическую сущность без потери её типа.
7. При отпускании применить выбранную Core-команду.
Проверить все сочетания:
- Main → Main;
- Main → Floating;
- Floating → Main;
- Floating → Floating.
Также проверить перенос между двумя разными Floating-окнами, чтобы кэш геометрии одного окна не использовался для другого.
**Основные файлы:**
- `crates/dock-gpui/src/floating_manager.rs`;
- `crates/dock-gpui/src/controller_layout_cache.rs`;
- `crates/dock-gpui/src/input_drag.rs`;
- `crates/dock-gpui/src/controller.rs`.
**Критерий готовности:** целевое окно определяется по HWND под курсором, а все вычисления drop-зон выполняются в координатах его клиентской области.
---
## Этап 7. Привести визуальную обратную связь к Core DropZone
**Задача:** отображать только ту зону, которую действительно выбрал Core Resolver.
Проверить отображение:
- добавления Panel в полосу вкладок;
- объединения групп;
- разделения группы сверху/снизу;
- вставки колонки;
- пристыковки к краям;
- свободной Floating-области.
Overlay Main и Overlay Floating могут визуально различаться из-за размеров и расположения окон, но не должны иметь независимые правила выбора цели.
Не восстанавливать отдельную логику remote overlay, которая самостоятельно вычисляет зоны на другой поверхности. Сначала использовать уже существующую маршрутизацию по реальным окнам и resolver целевого окна.
**Основные файлы:**
- `crates/dock-gpui/src/components/drop_overlay.rs`;
- `crates/dock-gpui/src/dock_host.rs`;
- `crates/dock-gpui/src/components/floating.rs`.
**Критерий готовности:** подсветка точно соответствует выбранному Core DropZone и не показывает ложную цель в исходном окне.

## Этап 8. Проверить временное освобождение источника и откат операции
**Задача:** проверить весь жизненный цикл tear-off и не допустить потери исходной структуры при отмене или неудачном drop.
Проверить сценарии:
- начало drag и превышение порога detach;
- создание/показ временного Floating-окна;
- перенос содержимого в окно-хост;
- движение над разрешённой целью;
- успешный drop;
- отпускание вне допустимой цели;
- отмена drag;
- ошибка Core-команды;
- закрытие временного окна во время незавершённой операции, если такой сценарий возможен.
Важно определить, когда исходный узел временно удаляется из прежнего места и кто отвечает за восстановление при неуспехе. Не должно оставаться пустых или потерянных узлов, зависших ссылок на WindowId/FloatingGroupId или двух активных хостов одной Panel.
**Основные файлы:**
- `crates/dock-gpui/src/controller.rs`;
- `crates/dock-gpui/src/input_drag.rs`;
- `crates/dock-gpui/src/drag_session.rs`;
- связанные команды/операции Core, если обнаружится ошибка на уровне Layout.
**Критерий готовности:** успешный drop завершает перенос ровно один раз; отмена или ошибка не повреждает исходный Layout и не оставляет временные окна/хосты в неконсистентном состоянии.

## Этап 9. Финальная проверка и удаление устаревшей логики
**Задача:** после завершения предыдущих этапов проверить сценарии целиком и удалить только доказанно ненужные обходные механизмы.
### Матрица сценариев
| Источник | Цель | Ожидаемый результат |
|---|---|---|
| Panel в Main | Tabs в Main | Panel добавляется в конец вкладок целевой Group |
| Panel в Main | Tabs во Floating | Panel переносится в целевую Floating Group |
| Panel во Floating | Tabs в Main | Panel переносится в Main Group |
| Panel во Floating | Tabs в другом Floating | Panel переносится в Group другого Floating-окна |
| Group в Main | Group в Main | Группы объединяются или разделяются согласно выбранной зоне |
| Group в Main | Group во Floating | Группа переносится в целевую Floating-композицию |
| Group во Floating | Group в Main | Группа переносится в Main Dock |
| Group во Floating | Group в другом Floating | Группа переносится в другое Floating-окно |
| Column в Main | Main Dock | Column вставляется в допустимый слот или к краю |
| Column во Floating | Main Dock | Column переносится как целая структура, если операция разрешена |
| Column в Main | Floating | Column переносится в допустимый слот Floating-композиции |
| Column во Floating | Floating | Column переносится в допустимый слот другого Floating-окна |
| DockArea | Main / Floating | Вся композиция переносится целиком согласно поддерживаемым операциям |
| Любой источник | Свободная область | Источник остаётся отдельным Floating-окном |
### Проверки целостности
- все Panel присутствуют ровно по одному разу;
- порядок Panel внутри Group сохранён;
- порядок Group внутри Column сохранён;
- порядок Column сохранён;
- нет пустых структур, запрещённых правилами Layout;
- у каждой Floating-композиции правильное окно-хост;
- геометрия Main и каждого Floating-окна кешируется раздельно;
- повторный drag после успешного переноса работает;
- отмена и ошибка не оставляют повреждённый Layout.
**Важно:** сборку и тесты запускает пользователь в своём локальном окружении. После каждого этапа пользователь присылает результат проверки, и только затем переходим к следующему этапу.

## Порядок нашей совместной работы
Каждый этап делаем отдельно:
1. Пользователь присылает текущий шаг или просит начать следующий.
2. Перед изменениями фиксируем короткий план: какие файлы затрагиваем и что именно меняем.
3. Изучаем только необходимые участки текущего кода.
4. Вносим минимальные изменения в текущую ветку `main`.
5. Не запускаем сборку и тесты вместо пользователя.
6. Пользователь проверяет результат локально и присылает ошибки или подтверждение.
7. После подтверждения переходим к следующему этапу.
### Ограничения на изменения
- Не создавать и не переключать Git-ветки.
- Не менять Core без необходимости для текущего этапа.
- Не дублировать Layout в GPUI.
- Не возвращать ранее отменённую remote-overlay-логику без отдельного согласования.
- Не смешивать несколько этапов в один большой рефакторинг.
- Не удалять старую реализацию до проверки, что её заменил рабочий механизм.
## Текущая точка старта
Начинать с **Этапа 1 — разделения логического источника перетаскивания и временного Floating-окна**. Следующие этапы не выполнять заранее: их объём уточняется по фактическому результату предыдущего шага.
