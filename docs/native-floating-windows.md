# Настоящие плавающие окна: архитектура и этапы

## Зачем

Цель — поведение плавающих панелей как в Photoshop: floating-группа может жить в отдельном системном окне, перемещаться независимо от главного окна, возвращаться в dock и сохранять положение после перезапуска.

Сейчас floating-группы **не являются отдельными окнами ОС**. `layers/floating.rs` рисует их поверх `DockSurface`, а `MainWindow` содержит один `DockController`, одну историю undo/redo и один механизм сохранения workspace. Поэтому косметическая правка заголовка не решит задачу: сначала необходимо определить единственного владельца layout, а затем отделить представление группы от поверхности главного окна.

## Архитектурные инварианты

1. **Один источник истины.** Layout, undo/redo и команды dock принадлежат одному workspace. Не создавать отдельную копию layout на каждое floating-окно: иначе окна начнут расходиться по состоянию, а Undo/Redo будет непредсказуемым.
2. **Окна — представления, а не владельцы layout.** Каждое плавающее окно знает свой `FloatingGroupId` и отображает соответствующую область дерева. Команды из него отправляются владельцу workspace.
3. **Идентификатор — не индекс.** Жизненный цикл окна связывается с `FloatingGroupId`; порядок групп в layout не должен использоваться как постоянная идентичность.
4. **Не закрывать окно до фиксации команды.** При возврате группы в dock сначала успешно применить команду к layout, затем закрывать native window. При ошибке оставить текущее окно и состояние неизменными.
5. **Отдельная геометрия каждой поверхности.** Главная поверхность и floating-окно имеют собственные viewport, scroll handles и временные UI-состояния. Для дочернего дерева нужно переводить координаты в локальную систему окна, а не переиспользовать абсолютные координаты главной поверхности без преобразования.
6. **Сохранение идёт из единого layout.** Автосохранение не должно запускаться независимо каждым floating-окном. Все изменения layout проходят через владельца workspace и используют существующий механизм сериализации.

## План реализации — по одному проверяемому этапу

### Этап 1. Отделить рендер одной floating-группы

Файлы:
- `crates/dock-gpui/src/layers/floating.rs` — выделить рендер одной группы из цикла рендеринга всех плавающих групп; существующий рендер должен сохранить прежний вид.
- `crates/dock-gpui/src/surface.rs` и при необходимости `crates/dock-gpui/src/frame.rs` — подготовить узкий интерфейс, позволяющий построить поверхность одного floating-дерева в локальном viewport.
- тесты геометрии — проверить локальный origin, размеры и отсутствие элементов соседних floating-групп.

Результат этапа: одна floating-группа может быть отрисована независимо от остальных, но native windows ещё не создаются.

### Этап 2. Представление native floating-окна

Новый файл `crates/dock-gpui/src/floating_window.rs`:
- GPUI view одной группы, привязанный к `FloatingGroupId`;
- собственные размеры/viewport и локальные hit-зоны;
- получение актуального состояния и отправка команд через владельца workspace;
- закрытие/перестройка view при исчезновении группы из layout.

`crates/dock-gpui/src/main_window.rs` остаётся владельцем команд, истории и автосохранения. Floating view не получает отдельную независимую историю и не сериализует layout самостоятельно.

### Этап 3. Жизненный цикл окон

Новый `crates/dock-gpui/src/floating_window_manager.rs`:
- сопоставление `FloatingGroupId` с созданным native window;
- сверка набора окон с floating-группами в layout;
- создание окна при detach, закрытие после успешного dock/close, безопасная обработка повторных событий;
- синхронизация положения и размеров окна с моделью.

`crates/dock-gpui/src/entry.rs` остаётся местом запуска приложения; управление отдельными floating-окнами не должно разрастаться в стартовом коде.

### Этап 4. Перетаскивание между окнами

`main_window.rs`, `floating_window.rs` и drag-подсистема должны согласовать один жест между разными viewport:
- источник начинает drag с идентификатором панели/группы;
- координаты переводятся в систему целевой поверхности;
- target вычисляется по актуальной геометрии, а не по кадру, который мог устареть после перемещения окна;
- drop фиксируется один раз в общем layout;
- отмена drag не меняет layout и гарантированно убирает overlay.

Отдельно проверить поведение при отпускании мыши вне любого dock-окна, закрытии окна во время drag и изменении размера viewport.

### Этап 5. Workspace и регрессии

- восстановление положения floating-окон при старте;
- сохранение после перемещения/resize и закрытия приложения;
- поддержка нескольких floating-групп и перекрывающихся окон;
- Undo/Redo для dock-команд без ложных checkpoints от обычного перемещения native окна;
- тесты на идемпотентный жизненный цикл окон, drop между поверхностями и сохранение/восстановление.

## Правило внесения изменений

Каждый этап — отдельный небольшой commit непосредственно в `main`. После каждого этапа запускаются локальные проверки проекта; к следующему этапу переходим только после результата пользователя. Нельзя заявлять о работающих native floating-окнах, пока проверено только прежнее overlay-поведение.
