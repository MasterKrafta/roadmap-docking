# План проверки и исправления замечаний по roadmap-docking

**Дата ревизии:** 2026-10-27  
**Основа:** статический просмотр текущей ветки `main`. Это рабочий список для последовательного исправления, а не утверждение, что каждый пункт является багом.

## Как работаем

- Исправляем по одному пункту, начиная с **P1-01**.
- Для поведенческих исправлений сначала добавляем тест, который воспроизводит проблему, затем меняем код.
- После каждого изменения проверку запускает пользователь в локальном окружении. Не считаем сборку или тесты пройденными без фактического результата.
- Статусы: **Открыт** — требуется работа; **Проверить** — нужно подтвердить воспроизводимость или принять продуктовое решение; **Закрыт** — замечание проверено и не считается дефектом.
- Приоритеты: **P1** — риск потери данных или невозможности восстановить сохранённое состояние; **P2** — устойчивость, корректность или существенный технический долг; **P3** — архитектура, удобство, доступность и оптимизация без доказанной текущей поломки.

## P1 — сохранность пользовательского workspace

### P1-01. Не перезаписывать workspace после неудачной загрузки

**Статус:** Закрыт — исправление внесено, пользователь подтвердил успешный локальный запуск тестов.  
**Уверенность:** исходный дефект воспроизведён регрессионным тестом.

**Где смотреть:**
- `crates/dock-gpui/src/dock/workspace.rs` — `load_layout`
- `crates/dock-gpui/src/main_window.rs` — `new_with_workspace`, `save_workspace_now`
- `crates/dock-gpui/src/entry.rs` — обработчик закрытия окна

**Исходный дефект:** если файл не читался или отклонялся парсером/валидатором, приложение запускало начальный layout, после чего автосохранение могло заменить исходный workspace начальными настройками.

**Решение:** `load_layout` теперь различает отсутствие файла и ошибку (`Result<Option<Layout>, WorkspaceError>`). При ошибке загрузки окно использует резервный начальный layout, но автоматическое сохранение отключено; при обычном первом запуске без файла сохранение остаётся доступным. Добавлены регрессионные тесты на сохранность workspace с неизвестной версией и на создание workspace при первом запуске.

**Критерии готовности:**
- Повреждённый JSON остаётся неизменным после запуска и закрытия приложения.
- Файл с неизвестной версией схемы остаётся неизменным.
- Отсутствующий файл по-прежнему позволяет выполнить первый запуск и создать workspace.
- Успешно загруженный workspace продолжает сохраняться после изменений.

### P1-02. Согласовать лимит глубины workspace с ограничениями JSON-парсера

**Статус:** Закрыт — граничные тесты прошли локально по подтверждению пользователя.  
**Уверенность:** ошибка подтверждена тестом на закреплённой версии `serde_json 1.0.154`.

**Где смотреть:**
- `crates/dock-core/src/workspace_file.rs` — `MAX_WORKSPACE_TREE_DEPTH`, `from_json_with_diagnostics`, экспорт дерева
- `crates/dock-core/src/workspace_file_tests.rs` — граничные round-trip тесты

**Проблема:** старый лимит в 256 уровней позволял экспортировать JSON, который затем не мог разобрать `serde_json::from_str` из-за лимита рекурсии. Важно: глубина — это число узлов на одном пути от корня до листа, а не число панелей во всём workspace.

**Изменение:** установлен максимум в 62 уровня. В худшем случае дерево такой глубины занимает 127 вложенных JSON-контейнеров вместе с оболочкой файла; закреплённый парсер отклоняет 128-й. Добавлены проверки сериализации и загрузки на максимальной глубине, отказа на следующем уровне и согласованности экспорта runtime-layout. Пользователь подтвердил успешное прохождение локальных тестов.

**Критерии готовности:** workspace предельной допустимой глубины сериализуется и загружается; следующий уровень отклоняется; экспорт runtime-layout и импорт JSON используют один и тот же лимит.

### P1-03. Не вызывать глобальные обработчики GPUI из фазы render

**Статус:** Запуск окна подтверждён пользователем; горячие клавиши и остальные обработчики ещё требуют проверки.  
**Уверенность:** причина подтверждена пользовательским backtrace.

**Где смотреть:** `crates/dock-gpui/src/main_window.rs` — `Render::render`, регистрации `Window::on_key_event` и `Window::on_mouse_event`.

**Проблема:** приложение завершалось при первом рендере с panic `this method can only be called during paint`. Глобальные обработчики клавиатуры и мыши регистрировались прямо из `Render::render`, а закреплённая версия GPUI разрешает эти вызовы только из paint-фазы.

**Изменение:** регистрации перенесены в paint callback полноразмерного прозрачного `canvas`-элемента. Сами обработчики и фазы Capture/Bubble сохранены.

**Критерии готовности:** приложение больше не падает при запуске; Escape, глобальные горячие клавиши, отслеживание drag/resize за пределами поверхности, закрытие меню, автоскрытие flyout и поднятие floating-групп работают как прежде.

## P2 — корректность и устойчивость

### P2-01. Не отмечать workspace сохранённым до успешной записи

**Статус:** Закрыт — пользователь подтвердил успешный локальный запуск тестов.  
**Уверенность:** дефект подтверждён статическим анализом; добавлен регрессионный тест состояния повторной попытки.

**Где смотреть:** `crates/dock-gpui/src/main_window.rs` — `schedule_workspace_save`, `save_workspace_now`.

**Проблема:** прежний `workspace_snapshot` обновлялся при планировании debounce, до фактической записи. Если запись завершалась ошибкой, планировщик видел совпадающий снимок и не планировал повтор.

**Изменение:** в `MainWindow` добавлено отдельное состояние `WorkspaceSaveState`: последний успешно сохранённый снимок, ожидающий снимок и поколение debounce. Успешная запись обновляет сохранённый снимок; ошибка очищает ожидающую попытку, но не меняет сохранённый снимок. Это позволяет запланировать повтор для того же содержимого при следующем событии. Повторный таймер для уже ожидающего неизменного снимка не сбрасывается, а устаревшие таймеры отменяются по поколению.

**Критерии готовности:** после ошибки записи сохранение того же состояния можно запланировать повторно; успешно сохранённый снимок не вызывает лишних записей; более старый debounce не перезаписывает новое состояние.

### P2-02. Убрать классификацию ошибок по текстовым сообщениям

**Статус:** Закрыт — пользователь подтвердил успешное прохождение локальных тестов и форматирования.  
**Уверенность:** технический долг подтверждён; непосредственная поломка не обнаружена.

**Где смотреть:** `crates/dock-core/src/layout/helpers.rs` — `ratio_issues`, `is_normalizable_validation_error`; `crates/dock-core/src/validation_error.rs`; `crates/dock-core/src/layout/validation.rs`.

**Проблема:** восстановление распознаёт часть ошибок сравнением строк `reason`. Изменение текста сообщения в валидаторе может незаметно изменить поведение нормализации.

**Изменение:** причины ошибок Split/Tabs/Column представлены enum `ValidationReason`; нормализация классифицирует их по вариантам enum вместо сравнения строк. Отображаемые тексты ошибок оставлены прежними.

**Критерии готовности:** тесты нормализации проверяют тип/код причины, а не совпадение формулировок текста.

### P2-03. Уточнить контракт постобработки геометрии в GPUI-адаптере

**Статус:** Закрыт — пользователь подтвердил успешное прохождение локальных тестов и форматирования.  
**Уверенность:** архитектурный риск подтверждён; самостоятельный текущий баг не доказан.

**Где смотреть:**
- `crates/dock-gpui/src/chrome_geometry.rs` — `normalize_docked_group_geometry`
- `crates/dock-gpui/src/frame.rs` — `FrameGeometry::compute`

**Проблема:** адаптер мутирует `LayoutRects` после расчёта геометрии в Core. Повторный вызов на уже нормализованном снимке сдвигает геометрию повторно. Результат используется рендерингом и определением drop-зон.

**Изменение:** тест закрепляет, что `FrameGeometry::compute` выдаёт результат одного применения нормализации к свежему Core-снимку; интеграционный тест продолжает проверять совпадение drop-зон с этим снимком. Документация функции теперь явно запрещает подавать ей результат `FrameGeometry`. Публичный экспорт пока сохранён, чтобы не менять API без отдельного решения; поэтому для внешних вызовов корректность входного снимка остаётся контрактом вызывающей стороны.

**Критерии готовности:** основной путь приложения нормализует свежую геометрию ровно один раз; рендеринг, hit testing и drop-зоны используют один и тот же снимок. Возможное ограничение публичного API — отдельное решение, а не скрытый breaking change.

### P2-04. Удалять устаревшие scroll handles

**Статус:** Закрыт по подтверждению пользователя: проверки и все тесты прошли.
**Уверенность:** отсутствие очистки видно в просмотренном коде; последствия для undo/redo не доказаны.

**Где смотреть:** `crates/dock-gpui/src/main_window.rs` — добавление handles для vertical overflow; `crates/dock-gpui/src/dock/controller.rs` — `scroll_handles`.

**Проблема:** handles добавляются в map по мере появления overflow. В просмотренном коде не найдено очистки для исчезнувших узлов. Это может оставлять лишние записи, а после изменений структуры дерева состояние прокрутки может расходиться с актуальными узлами.

**Изменение:** в `DockController::frame` handles очищаются по актуальным узлам `Node::Column` после успешного расчёта геометрии кадра и обновления границ canvas. Handles существующих колонок сохраняются, даже если текущий viewport не создаёт overflow. В `crates/dock-gpui/src/dock/controller_tests.rs` добавлены регрессионные тесты на удаление устаревших handles и сохранение handles живых колонок без текущего overflow.

**Критерии готовности:** после многократного добавления/удаления узлов карта не накапливает неактуальные handles; прокрутка существующих узлов сохраняется корректно.

### P2-05. Усилить автоматические тесты для workspace и жестов

**Статус:** Закрыт по подтверждению пользователя: property-тест с основными и плавающими раскладками прошёл.
**Уверенность:** пробелы в покрытии частично подтверждены; в проекте уже есть unit-тесты workspace, поэтому утверждение об отсутствии такого тестирования неверно.

**Где смотреть:**
- `crates/dock-core/src/command_sequence_tests.rs` — stateful property-тест настроен на 48 случаев
- `crates/dock-core/src/workspace_file_tests.rs` — тесты схемы, миграции, глубины и round-trip
- `crates/dock-gpui/tests/workspace_roundtrip.rs`
- `crates/dock-gpui/src/main_window.rs` — debounce и сохранение
- `crates/dock-gpui/src/layers/` и `crates/dock-gpui/src/components/`

**Первый шаг:** в `crates/dock-core/src/workspace_file_tests.rs` добавлен property-тест, генерирующий валидные layout с разным количеством колонок, групп и панелей. Его базовый вариант прошёл у пользователя. Следующим изменением генератор расширен на случайное количество floating groups с собственными колонками, группами и панелями; это расширение ожидает локальной проверки.

**Что сделать:**
1. Проверить property-тест случайных допустимых layout: сериализация → загрузка → проверка структуры.
2. Добавить сценарии повреждённого файла и неудачной записи для P1-01/P2-01.
3. Проверить undo/redo после последовательностей команд и работу на небольших viewport.
4. Выбрать критичные пользовательские пути рендеринга и добавить тесты геометрии/взаимодействия, где это возможно.

**Критерии готовности:** основные сценарии потери данных и восстановления воспроизводятся автоматическими тестами; тесты не зависят от реального времени или внешней сети.

### P2-06. Убрать дублирование констант и смешивание цветов в компонентах

**Статус:** Закрыт по подтверждению пользователя: тесты после удаления RGB-дублирования и централизации высоты строки popup-menu прошли.
**Уверенность:** дублирование подтверждено статически; визуальная поломка не доказана.

**Где смотреть:**
- `crates/dock-gpui/src/color.rs`
- `crates/dock-gpui/src/components/drop_zone.rs`
- `crates/dock-gpui/src/layers/drop_overlay.rs`
- `crates/dock-gpui/src/components/popup_menu.rs`
- `crates/dock-gpui/src/menus/mod.rs`

**Проблема:** функция смешивания RGB была реализована в нескольких местах; теперь оба потребителя используют `crate::color::blend_rgb`. Высота строки popup-меню централизована в `components/popup_menu.rs` и используется как при расчёте границ, так и при отрисовке. Ширина задаётся только расчётом границ, а отступ используется только в рендеринге, поэтому текущего дублирования этих значений нет. Изменение одной копии может рассогласовать геометрию и отображение.

**Что сделать:** централизовать общее смешивание цветов и общие размеры, используемые одновременно измерением и рендерингом. Не создавать дополнительный общий модуль, если достаточно существующих тематических модулей.

**Критерии готовности:** расчёт границ и отрисовка меню используют одни и те же параметры; тест фиксирует совпадение размеров строки.

### P2-07. Проверить валидность темы и её влияние на layout

**Статус:** Закрыт по подтверждению пользователя: тесты `ui` и `dock-gpui` прошли.
**Уверенность:** отсутствие отдельного Theme::validate подтверждено; реальное влияние отдельных некорректных полей требует проверки.

**Где смотреть:** `crates/ui/src/theme/theme.rs`, `theme_metrics.rs`, `theme_colors.rs`; `crates/dock-gpui/src/metrics.rs`; `crates/dock-gpui/src/dock/rail_policy.rs`.

**Исходная проблема:** поля темы публичные. До добавления `Theme::validate` не все значения, применяемые напрямую в UI, проходили одинаковую проверку; некорректные rail-пороги могли незаметно отключить автоматические переходы.

**Изменение:** в `crates/ui/src/theme/theme_metrics.rs`, `theme_typography.rs` и `theme.rs` добавлена валидация конечных и положительных размеров, отношений метрик, rail hysteresis, split ratio, RGB-диапазона и типографики. `DockController::new_initial` и `new_with_layout` отклоняют невалидную тему с диагностируемой ошибкой вместо молчаливого отключения rail-политики. Регрессионный тест в `crates/dock-gpui/src/dock/controller_tests.rs` воспроизвёл исходную проблему до исправления; теперь нужно проверить исправление локально.

**Следующая проверка:** подтвердить локальными тестами инварианты метрик, типографики, RGB-цветов и отказ при создании как начального, так и восстановленного layout. После успешного прогона сверить оставшиеся UI-метрики с реальным использованием и отдельно решить, какие незадействованные поля темы относятся к P3-01.

**Критерии готовности:** некорректные параметры темы обрабатываются предсказуемо; не возникает отрицательной/непредставимой геометрии или скрыто отключённого поведения без диагностики.

## P3 — архитектура, интерфейс и сопровождаемость

### P3-01. Разделить тему: объявленные поля и реальное применение

**Статус:** Закрыт — пользователь подтвердил локальное прохождение `cargo fmt --all -- --check`, `cargo test -p ui` и `cargo test -p dock-gpui`. Неиспользуемые публичные метрики явно помечены как reserved/legacy, а поддерживаемые метрики подключены к UI.  
**Уверенность:** статический просмотр подтвердил неиспользование нескольких полей; применение остальных метрик требует отдельного разбора.

**Где смотреть:** `crates/ui/src/theme/theme_typography.rs`, `theme_metrics.rs`, `theme_colors.rs`; `crates/dock-gpui/src/components/`; `crates/dock-gpui/src/layers/`.

**Проблема:** первичный аудит выявил неиспользуемые поля типографики и метрик темы. `ThemeTypography` и hover-палитра уже подключены; `default_column_split_ratio`, `group_control_button_width`, `content_padding`, `button_size` и `button_gap` влияют на layout/отрисовку. Три поля не управляют текущим UI и теперь явно помечены как reserved/legacy: `edge_drop_zone_width` (вместо него геометрия использует `drop_edge_zone`), `tab_drag_zone_width` (будущая drag-зона) и `column_tab_width` (legacy simple-column UI; текущие вкладки распределяются по доступной ширине).

**Закрыто:** `ThemeTypography` и `ThemeColors::hover` подключены в `IconButton`, `PanelTab`, `RailEntry`, `PopupMenu` и `FloatingTitle`; пользователь подтвердил прохождение локальных тестов. `drop_indicator_thickness` управляет обводкой `DropZone`, а `drop_outline_thickness` — обводкой drag-preview.

**Сделано:** `build_initial_layout` применяет `ThemeMetrics::default_column_split_ratio` к начальному столбцу с двумя группами; пользователь подтвердил прохождение тестов. `group_control_button_width` протянут в `DockMetrics` и адаптер темы; теперь им пользуются и `normalize_docked_group_geometry`, и отрисовка кнопок в `tree_tabs.rs`, вместо отдельной константы `28 px`. Пользователь подтвердил прохождение тестов.

**Закрыто:** `content_padding` применяется в `PanelSurface` как равномерный внутренний отступ вокруг содержимого панели; пользователь подтвердил успешное прохождение `cargo test -p ui` и `cargo test -p dock-gpui`.

**Закрыто:** `button_size` задаёт максимальную ширину кнопок в заголовке плавающего окна; добавлены unit-тесты на применение размера и ограничение доступной геометрией. Пользователь подтвердил успешное прохождение `cargo test -p ui` и `cargo test -p dock-gpui`.

**Закрыто:** `button_gap` управляет промежутком между кнопками в заголовке плавающего окна; добавлен unit-тест на учёт промежутков. Пользователь подтвердил успешное прохождение `cargo test -p ui` и `cargo test -p dock-gpui`.

**Уточнено:** `edge_drop_zone_width` сохранён как legacy-поле для совместимости. В runtime используется `drop_edge_zone`, который передаётся в `DockMetrics`; старое поле не удаляется, чтобы не ломать возможных внешних потребителей структуры.

**Закрыто:** `tab_drag_zone_width` документирован как резерв под будущую drag-зону, а `column_tab_width` — как legacy-метрика старого simple-column UI. Текущая геометрия вкладок не использует эти поля; публичные поля сохранены для совместимости.

**Критерии готовности:** изменение поддерживаемого параметра темы действительно меняет интерфейс; в публичной теме не остаются поля, которые создают ложное ожидание настройки.

### P3-02. Зафиксировать app-first направление вместо проектирования универсального embed API

**Статус:** Закрыт — принято продуктовое решение пользователя.  
**Уверенность:** решение определяет текущий этап продукта, а не финальный долгосрочный контракт API.

**Где смотреть:** `crates/dock-gpui/src/entry.rs`, `crates/dock-gpui/src/lib.rs`, `crates/dock-gpui/src/host.rs`.

**Решение:** сейчас строим docking-интерфейс как основу большой программы, а не самостоятельную универсальную библиотеку. Текущий `run()` остаётся входом приложения; не добавляем настройки темы и реестра панелей только ради гипотетического внешнего встраивания.

**Практические границы:** сохраняем внутреннее разделение Core/UI/host и уже существующие полезные публичные типы, но не расширяем публичный API без конкретной потребности основного приложения. Когда появится реальный сценарий встраивания или отдельный потребитель, контракт библиотеки можно пересмотреть отдельной задачей.

**Критерии готовности:** направление зафиксировано; новые API-решения принимаются исходя из потребностей приложения и его docking-интерфейса, без преждевременного проектирования универсальной библиотеки.

### P3-03. Сохранить намеренную семантику гистерезиса при resize

**Статус:** Закрыт — пользователь подтвердил успешное локальное прохождение форматирования и всех тестов `dock-gpui`.  
**Уверенность:** поведение закреплено регрессионным тестом, алгоритм не менялся.

**Где смотреть:** `crates/dock-gpui/src/dock/rail_policy.rs`; `crates/dock-gpui/src/dock/controller.rs` — `update_resize`, `commit_resize`.

**Решение:** выбор rail/expanded намеренно учитывает режим предыдущего preview. Порог схлопывания и порог раскрытия разделены, чтобы колонка не мерцала при движении внутри промежутка.

**Сделано:** тест проверяет последовательность ширин 219 → 230 → 241 → 230 → 220 px: колонка входит в rail ниже порога 220, остаётся в rail внутри промежутка, раскрывается выше порога 240, сохраняет expanded-режим внутри промежутка и возвращается в rail на нижнем пороге. Комментарий `commit_resize` объясняет сохранение режима при отпускании мыши внутри промежутка.

### P3-05. Уточнить поддержку платформ

**Статус:** Отложен до этапа реального портирования на дополнительные ОС. Наличие подготовленных каталогов не означает, что поддержка платформ уже реализована; сейчас не менять запуск приложения ради преждевременной мультиплатформенности.  
**Уверенность:** подтверждено статически.

**Где смотреть:** `crates/dock-gpui/src/entry.rs`.

**Проблема:** `run()` запускает приложение только на Windows; на других платформах пишет ошибку в tracing. При этом функция определения пути workspace содержит ветви для macOS и Linux.

**Когда вернуться:** когда начнётся фактическое портирование на вторую ОС. Тогда проверить требования GPUI и сборки, а также согласовать `run()` и пути workspace с реальной матрицей поддерживаемых платформ. До этого не заявлять поддержку ОС и не тратить время на преждевременную реализацию.

**Критерии готовности:** заявленная поддержка платформ соответствует реальному поведению приложения.

### P3-06. Улучшить доступность управления с клавиатуры

**Статус:** В работе; первый подшаг реализован и ожидает локальной проверки. Перестановка и resize с клавиатуры остаются открытыми.  
**Уверенность:** ограниченность клавиатурного управления отмечена статическим обзором, но полноценный accessibility-аудит не проводился.

**Проблема:** ключевые операции drag, resize и переупорядочивания ориентированы на мышь. Одного focus ring недостаточно для полноценного клавиатурного управления.

**Минимальный набор:** перевод фокуса на panel tabs и rail entries; активация Enter/Space; затем клавиатурное перемещение/переупорядочивание, изменение размера и понятная индикация фокуса. На первом подшаге `PanelTab` активирует выбранную вкладку, а `RailEntry` открывает соответствующий flyout с Enter/Space. Добавлены тесты на распознавание клавиш активации; доступность других действий остаётся отдельной работой.

### P3-07. Разделить пользовательский контент и демонстрационные заглушки

**Статус:** Проверить — зависит от назначения приложения.  
**Уверенность:** подтверждено текущей реализацией.

**Где смотреть:** `crates/dock-gpui/src/dock/host_impl.rs`, `crates/dock-gpui/src/host.rs`, `crates/dock-gpui/src/panels/content.rs`.

**Проблема:** WindowHost делегирует отображение содержимого в NoopHost/реестр встроенных панелей, где сейчас показаны заглушки вроде «Контент: …». При этом обработчики команд, drag и resize у WindowHost реализованы — называть весь host неработающим неправильно.

**Что сделать:** если проект остаётся демо, явно оставить и описать заглушки. Если это библиотека, определить API, через который приложение передаёт рендереры панелей.

### P3-08. Централизовать тексты и мелкие параметры UI

**Статус:** Открыт; низкий приоритет.

**Где смотреть:** `crates/dock-gpui/src/panels/content.rs`, `components/popup_menu.rs`, `menus/mod.rs`, тема UI.

**Проблема:** пользовательские строки смешивают русский и английский; ряд размеров меню и отступов зашит в компонентах. Это затрудняет локализацию и единообразную настройку.

**Что сделать:** выделить минимальную стратегию локализации (либо пока официально закрепить один язык) и вынести только повторно используемые/настраиваемые параметры. Не вводить инфраструктуру локализации, если она не нужна текущему продукту.

### P3-09. Проверить накладные расходы копирования Layout и истории

**Статус:** Проверить измерениями; не оптимизировать предположительно.

**Где смотреть:** `crates/dock-core/src/undo_redo_history.rs`; resize preview в `crates/dock-gpui/src/dock/controller.rs`.

**Проблема:** команды используют копии Layout, а resize preview строит кандидата на базе baseline; история хранит ограниченное число полных снимков. Это упрощает транзакционность и undo, но стоимость может расти с размером layout.

**Что сделать:** сначала измерить реальные сценарии и размер layout. Рассматривать Arc/persistent-структуры или структурное разделение данных только при подтверждённом узком месте.

### P3-10. Учесть, что версия Layout не является идентификатором содержимого

**Статус:** Открыт как архитектурное ограничение; текущая ошибка не доказана.

**Где смотреть:** `crates/dock-gpui/src/dock/resize_session.rs`; `crates/dock-gpui/src/dock/controller.rs`; `crates/dock-gpui/src/frame.rs`.

**Проблема:** разные варианты preview могут быть построены из одного baseline и иметь одинаковую ревизию, хотя геометрия различается. Поэтому будущий кэш нельзя безопасно индексировать только по version, если он должен различать превью.

**Что сделать:** документировать область применимости version. Если появится кэш состояния preview, добавить отдельный generation/id либо использовать полноценный ключ входных параметров.

### P3-11. Проверить требования к потокобезопасности Layout

**Статус:** Проверить только при необходимости межпоточного использования.

**Где смотреть:** `crates/dock-core/src/layout.rs` — `ValidationCache(Cell<...>)`.

**Проблема:** использование Cell влияет на то, может ли Layout реализовать Sync. Само по себе это не баг, если модель предназначена для одного потока.

**Что сделать:** не менять реализацию ради формального Sync. Сначала решить, является ли межпоточное разделение Layout частью требований API; при необходимости выбрать подходящий способ кэширования.
