# План переделки Dock: панели по запросу и постоянные окна панелей
> Обновлённая целевая модель: обычный запуск открывает только главное окно; панели открываются через меню и сразу появляются отдельными плавающими окнами.
## 1. Цель переделки
Перестроить запуск и управление панелями так, чтобы пользователь сам выбирал, какие панели открывать, а каждая открытая панель имела собственное постоянное нативное окно.
**Обычный запуск:**
- открывается главное окно с Canvas и пустыми областями Dock;
- панели автоматически не создаются и не открываются;
- нужную панель пользователь включает через меню `Панели` с галочками;
- новая панель сразу создаётся как самостоятельная плавающая композиция и показывается в собственном окне;
- новая панель не помещается автоматически в левую/правую область главного Dock.
Собственное окно панели связано с её `PanelId` на протяжении жизни экземпляра. Если панель A вложить в композицию B, окно A скрывается, но не уничтожается. Содержимое A отображается в host-окне композиции B. При извлечении A снова показывается её собственное окно.
`dock-core` не требуется переписывать с нуля. Существующие деревья, `PanelId`, `Tabs`, `Column`, команды перемещения, drop-зоны и Undo/Redo сохраняются там, где соответствуют этой модели.

## 2. Целевая модель
### 2.1. Каталог типов и открытые экземпляры — разные сущности
| Сущность | Ответственность |
|---|---|
| `PanelRegistry` | Каталог доступных типов панелей: ключ, заголовок, иконка, ограничения и фабрика представления |
| `PanelId` | Идентификатор конкретного открытого экземпляра панели |
| `PanelViewCache<AnyView>` | Единственное представление конкретного `PanelId` и его состояние |
| `PanelWindow` | Постоянное нативное окно, закреплённое за конкретным `PanelId` |
| `Layout` | Текущее расположение открытых панелей, групп и композиций |
| `FloatingGroupId` | Идентификатор плавающей композиции в Core; это не идентификатор нативного окна панели |
| Host отображения | Окно, которое сейчас выводит композицию: главное окно либо выбранное окно одной из панелей этой композиции |
Наличие типа в `PanelRegistry` **не означает**, что экземпляр панели уже создан. Нативное окно и `Entity` создаются только при явном открытии экземпляра.
Для первой версии меню с галочками предполагается **один открытый экземпляр каждого типа панели**. Это соответствует двоичному состоянию «открыта/закрыта». Возможность нескольких экземпляров одного типа можно добавить отдельно, заменив одну галочку на список экземпляров.
### 2.2. Обычный запуск
```text
Application
└── MainWindow
    ├── Main menu
    │   └── Панели [галочки]
    └── DockHost
        └── Canvas
            └── пустые области Dock
Открытые PanelId: нет
PanelWindow: нет
FloatingGroup: нет
```
Важное требование: обычный запуск не должен сначала создавать стартовые панели в главном Dock, а затем переносить или скрывать их. Их вообще не нужно создавать до выбора пользователя.
### 2.3. Открытие панели через меню
```text
Пользователь включает [x] Layers
        │
        ▼
Создаётся PanelInstance и PanelId
        │
        ▼
Core сразу помещает панель в отдельную Floating-композицию
        │
        ▼
Создаётся PanelView (Entity / AnyView)
        │
        ▼
Создаётся собственное окно PanelWindow(Layers)
        │
        ▼
Окно показывается как самостоятельное floating-окно
MainWindow и его Canvas не изменяются.
```
Операция открытия должна сразу создавать плавающую композицию. Не использовать обычный `OpenPanel { target: None }` без изменения его семантики: в текущем Core `None` разрешается через последнее запомненное место панели или профильное место по умолчанию. Это может поместить новую панель в главный Dock.
Нужен однозначный путь открытия именно в floating-состоянии: отдельная команда (например, `OpenPanelFloating`) либо явный destination у существующей команды. Создание панели и её Floating-композиции должно быть атомарным с точки зрения Layout — не должно быть промежуточного кадра, в котором панель появляется в главном Dock.
### 2.4. Панели в одной плавающей композиции
```text
PanelWindowRegistry
├── Panel A → Window A (существует, скрыто)
└── Panel B → Window B (существует, показано)
Window B отображает композицию:
├── Panel B
└── Panel A
```
При вложении A в B:
- окно A скрывается;
- запись A, HWND A, `PanelId` A и `AnyView` A сохраняются;
- окно B остаётся host-окном целевой композиции;
- содержимое A выводится внутри композиции B;
- при извлечении A показывается прежнее окно A.
Если в одну композицию объединяются две плавающие композиции, host-окном по умолчанию остаётся окно целевой композиции. Окно исходной композиции скрывается, но не переиспользуется для другого `PanelId`.
### 2.5. Стыковка с главным Dock
```text
MainWindow (host)
├── Canvas
└── Main Dock
    └── композиция A/B
PanelWindow A → существует, скрыто
PanelWindow B → существует, скрыто
```
При стыковке композиции слева или справа:
- Layout переносит композицию в соответствующую область главного Dock;
- интерфейс начинает отображаться внутри `MainWindow`;
- собственные окна панелей остаются существовать, но скрываются;
- при последующем извлечении панель/композиция снова получает подходящее собственное окно.
### 2.6. Снятие галочки и закрытие панели
Галочка означает, что экземпляр панели открыт в рабочем пространстве. Она **не означает**, что его собственное окно сейчас видно.
- Галочка включена — `PanelId` существует в Layout, экземпляр панели открыт.
- Галочка выключена — экземпляр панели закрыт, удалён из Layout и его собственное окно освобождено.
- Панель вложена в другую панель — галочка остаётся включённой, даже если её окно скрыто.
- Панель пристыкована к главному Dock — галочка остаётся включённой, даже если её окно скрыто.
Особый случай: если закрывается панель, чьё окно сейчас служит host для композиции с другими открытыми панелями, сначала нужно назначить host-ом окно одной из оставшихся панелей (или `MainWindow`, если композиция пристыкована к главному Dock), переключить отображение и только после этого уничтожить окно закрываемой панели.
### 2.7. Не смешивать четыре независимых свойства
1. **Положение в Layout:** floating-композиция, главный Dock, вкладка внутри другой композиции.
2. **Host отображения:** какое окно сейчас рисует интерфейс композиции.
3. **Видимость собственного PanelWindow:** показано или скрыто.
4. **Нативный Windows owner (`GWLP_HWNDPARENT`):** системная связь окон для поведения Windows.
`FloatingGroup.z_order` остаётся настоящим порядком плавающих композиций. Не использовать его как флаг стыковки.
Отдельное floating-окно при открытии не становится членом `Main Dock`. **Системная политика Windows зафиксирована: HWND главного окна является постоянным native owner каждого `PanelWindow` на всём протяжении жизни панели.** Поэтому сворачивание главного окна скрывает все принадлежащие ему panel popups, а закрытие главного окна завершает их жизненный цикл. Эта связь не зависит от положения панели в Layout и не меняется при docking, extraction, смене композиции или host. Если главный HWND недоступен либо `set_owner` завершается ошибкой, такое native `PanelWindow` не регистрируется и создание повторяется на следующем `reconcile()`. Не использовать `set_owner` как замену операции стыковки.

### 3.1. Что нельзя делать в начале
- Не начинать с удаления `FloatingWindowManager` или полного переписывания `dock-core`.
- Не создавать все окна при старте «на будущее».
- Не помещать новую панель сначала в Main Dock, а затем отдельной командой отрывать её в floating.
- Не вызывать `OpenPanel { target: None }` для меню, если эта команда продолжает разрешать последнее/профильное место.
- Не использовать `FloatingGroupId` как постоянную идентичность окна панели.
- Не пересоздавать `Entity`/`AnyView` при переносе панели.
- Не считать скрытое окно закрытой панелью.
- Не связывать `z_order`, Dock membership и Windows owner в одно поле.

## 4. Последовательность реализации
Выполнять строго по одному этапу. Перед каждым этапом перечислять файлы и ожидаемые изменения. После этапа останавливаться и передавать результат на локальную проверку пользователя; к следующему этапу переходить только после подтверждения.
### Этап 0. Зафиксировать новую целевую модель
**Цель:** исключить неоднозначность до изменения кода.
Зафиксировать правила:
1. Обычный новый workspace пустой: только MainWindow, Canvas и меню.
2. Никакие PanelInstance, PanelView или PanelWindow не создаются автоматически при обычном запуске.
3. Меню `Панели` показывает доступные типы из `PanelRegistry`.
4. Включение пункта создаёт один экземпляр типа и сразу отдельную Floating-композицию с собственным окном.
5. Новая панель не помещается в Main Dock и не получает Main Dock как destination по умолчанию.
6. Для первой версии один открытый экземпляр каждого типа панели.
7. Закрытие по галочке удаляет экземпляр; стыковка и скрытие окна не удаляют его.
9. Окно закреплено за `PanelId`; host композиции может меняться.
10. Все окна используют один `DockController` и один `Layout`.
**Готово, когда:** правила обычного запуска, открытия, стыковки, вложения, извлечения и закрытия зафиксированы и больше не меняются в ходе этапов без отдельного решения.
### Этап 1. Сделать пустой обычный запуск
**Цель:** при старте показывать только главное окно и Canvas.
Основные файлы:
- `crates/dock-gpui/src/lib.rs`
- `crates/dock-core/src/layout.rs`
Задачи:
1. Создавать пустой `Layout` без `PanelInstance`, Main Dock-композиций и Floating-композиций.
2. Не вызывать `create_initial_layout()` как default для обычного запуска: она создаёт профильную стартовую раскладку.
3. Регистрировать доступные типы панелей в `PanelRegistry`, не создавая их экземпляры.
4. Не создавать `PanelView` и `PanelWindow` для типов, присутствующих только в каталоге.
**Проверка:** обычный запуск показывает главное окно и Canvas без панелей; включение пункта меню создаёт только выбранную панель.
**Готово, когда:** после обычного запуска в Layout нет открытых панелей и не создаются лишние окна.
### Этап 2. Добавить явное открытие панели сразу в Floating и закрытие
**Цель:** сделать модельные операции, на которые затем сможет опираться меню и менеджер окон.
Основные файлы:
- `crates/dock-core/src/dock_command.rs`
- `crates/dock-core/src/layout/command_panels.rs`
- `crates/dock-core/src/command_application.rs`
- `crates/dock-core/src/command_value.rs`
- соответствующие Core-тесты
Текущее состояние: `OpenPanel` и `ClosePanel` уже существуют. Но `OpenPanel { target: None }` разрешает место через сохранённую позицию или профильный default, а это не гарантирует Floating.
Задачи:
1. Добавить явную семантику «открыть новый экземпляр как самостоятельную Floating-композицию» — отдельной командой либо явным destination у `OpenPanel`.
2. В одной Core-операции создать `PanelInstance`, `Panel` node, `Tabs`/корень композиции, `DockArea::Floating` и `FloatingGroup` с начальными bounds.
3. Не допускать промежуточного состояния, когда новая панель сначала попадает в Main Dock.
4. Возвращать адаптеру достаточную информацию о созданном экземпляре (как минимум `PanelId`; при необходимости также `FloatingGroupId`).
5. Сделать открытие/повторное включение согласованным с правилом одного экземпляра на тип панели.
6. Использовать существующий `ClosePanel` для снятия галочки; проверить, что удаление последнего элемента корректно удаляет пустую композицию и FloatingGroup.
7. Определить inverse/Undo для открытия и закрытия, не ломая существующую историю.
8. Сохранить возможность явного открытия в Main Dock для отдельных команд приложения; меню обычного открытия такую цель не использует.
**Проверка:** Core-тесты: открытие из пустого Layout создаёт FloatingGroup; Main Dock остаётся пустым; второй Open для singleton не дублирует панель; Close удаляет экземпляр; Undo/Redo восстанавливает корректную структуру.
**Готово, когда:** Core способен открыть панель исключительно в floating-состоянии без участия GPUI.
### Этап 3. Подключить меню `Панели` с галочками
**Цель:** дать пользователю управление жизненным циклом экземпляров.
Основные места:
- `crates/dock-gpui/src/lib.rs`
- `crates/dock-gpui/src/registry.rs`
- новый компонент/оболочка меню на уровне приложения, вне `DockHost`
- `crates/dock-gpui/src/actions.rs`
- `crates/dock-gpui/src/controller.rs`
Задачи:
1. Создать меню `Панели` на уровне оболочки главного окна. `DockHost` оставить host-ом Canvas и Dock, не делать его владельцем каталога типов.
2. Формировать пункты меню из зарегистрированных `PanelDescriptor`.
3. Состояние галочки вычислять из текущего `Layout`: есть ли открытый runtime `PanelId` данного ключа.
4. Не хранить вторую независимую копию состояния галочек в локальном UI state.
5. При включении отправлять явную команду открытия сразу в Floating.
6. При выключении отправлять `ClosePanel` для соответствующего `PanelId`.
7. После любой операции Dock (перемещение, вкладка, стыковка, скрытие окна) галочка остаётся включённой, пока `PanelId` есть в Layout.
8. Для первой версии установить singleton-семантику на типы, которым соответствует один checkbox.
**Проверка:** включить/выключить каждый тип; убедиться, что галочка синхронна с Layout; переместить панель в другую композицию и проверить, что галочка не снимается; закрыть панель из Dock UI и проверить, что галочка снимается.
**Готово, когда:** меню управляет Core-моделью и отражает реальное наличие открытых экземпляров, не управляя HWND напрямую.

- `crates/dock-gpui/src/dock_host.rs`

2. Хранить один экземпляр представления на один открытый `PanelId`.
3. Не создавать View только потому, что тип есть в каталоге.
4. Не удалять View при перемещении, объединении, стыковке или смене активной вкладки.

### Этап 5. Подготовить и использовать платформенные операции
**Цель:** обеспечить создание/показ/скрытие/перемещение окон без Win32-кода в GPUI-слое.

- `crates/platform/src/lib.rs`

Задачи:
1. Сверить контракт `NativeWindowOps` с новой моделью постоянного `PanelWindow`.
2. Добавить только недостающие операции: например, получение foreground/active HWND, проверку существования окна или необходимые события активации, если текущего API недостаточно.

**Проверка:** изолированно проверить недостающие нативные операции на GPUI-окнах. Drag pipeline пока не менять.
**Готово, когда:** платформа предоставляет минимальный законченный контракт для PanelWindow и host-переключений.
### Этап 6. Переделать `FloatingWindowManager` и реестр окон
**Цель:** закрепить одно нативное окно за каждым открытым `PanelId` и отдельно учитывать host каждой композиции.
Основной файл:
- `crates/dock-gpui/src/floating_manager.rs`
Текущее состояние: `PanelWindowRegistry` закрепляет постоянное окно за `PanelId`, а `CompositionHostRegistry` отдельно хранит host каждой композиции. Старый `reusable`-пул и зависимость идентичности окна от `FloatingGroupId` уже отсутствуют.
Целевая схема:
```text
PanelWindowRegistry
├── Panel A → WindowHandle A + WindowId A + HWND A + visibility
├── Panel B → WindowHandle B + WindowId B + HWND B + visibility
└── Panel C → WindowHandle C + WindowId C + HWND C + visibility
CompositionHostRegistry
├── FloatingGroup X → host Panel B
├── FloatingGroup Y → host Panel C
└── Main Dock       → MainWindow
```
Задачи:
1. Ввести постоянную запись `PanelId → PanelWindow`.
2. Не перепривязывать окно A к другому `PanelId`.
3. Хранить WindowHandle/WindowId/HWND, bounds, scale, native min size, состояние resize и видимость собственного окна.
4. Вести отдельную карту host: какая поверхность отображает каждую композицию.
5. При открытии панели сразу создавать её индивидуальное окно и показывать его как host её отдельной Floating-композиции.
6. При вложении панели A в композицию B оставлять host B, скрывать окно A и сохранять запись A.
7. При стыковке композиции в Main Dock назначать host-ом MainWindow и скрывать окна панелей этой композиции.
8. При извлечении панели назначать host-ом её собственное окно и показывать его.
9. При закрытии панели, являющейся текущим host, сначала безопасно передать отображение другому host, затем освободить её окно.
10. Обновлять карты после каждого изменения Layout и закрытия панели.
12. `FloatingGroupId` использовать только для адресации композиции/её host mapping, но не для постоянной идентичности нативного окна панели.
**Готово, когда:** окно A сохраняет свой HWND при циклах A → B → A и никогда не становится окном другой панели.
### Этап 7. Подключить создание и отображение окон при открытии панелей
**Цель:** получить единый lifecycle для открываемых PanelWindow.
Основные файлы:
- `crates/dock-gpui/src/lib.rs`
- `crates/dock-gpui/src/floating_manager.rs`
- `crates/dock-gpui/src/components/floating.rs`
- `crates/dock-gpui/src/controller.rs`
Задачи:
1. При включении checkbox создать Core-экземпляр сразу в отдельной Floating-композиции.
2. Создать `PanelView` для нового `PanelId`.
3. Открыть GPUI `WindowKind::PopUp` для его `PanelWindow` и выполнить первичный render.
4. Получить HWND, применить необходимые native style и resize-ограничения и только после этого показать окно.
5. На обычном запуске не выполнять эти операции ни для одного типа панели заранее.
6. Создавать panel windows только для `PanelId`, реально присутствующих в текущем Layout.
7. Не создавать duplicate окна при повторном `reconcile()`.
8. Не создавать скрытые native windows для всего каталога `PanelRegistry`.
**Проверка:**
- новый запуск: только MainWindow;
- включение одной галочки: одно новое floating-окно;
- включение второй: второе собственное окно;
- вложение панели в другую композицию: окно вложенной панели скрывается, host остаётся видимым;
- стыковка композиции в Main Dock: содержимое рисуется MainWindow, собственные окна скрыты.
**Готово, когда:** PanelWindow создаются только для открытых экземпляров, а повторный `reconcile()` не создаёт дубликаты.

### Этап 9. Реализовать drag, docking, tear-off и извлечение
Основные файлы:
- `crates/dock-gpui/src/floating_manager.rs`
- `crates/dock-gpui/src/input/pointer.rs`
- `crates/dock-gpui/src/input/drag.rs`
- `crates/dock-gpui/src/controller.rs`
- `crates/dock-core/src/drag_session.rs`
- `crates/dock-core/src/drag_drop_resolution.rs`
Использовать поведенческие приёмы `tearoff/main.rs`:
- опрос курсора во время нативного перемещения;
- проверка состояния ЛКМ;
- порог отрыва;
- сохранение точки захвата относительно окна;
- перемещение реального HWND;
- подсветка drop target;
- завершение/отмена жеста при отпускании или Escape.
Но все изменения Layout выполнять существующими/доработанными Core-командами, а не отдельной упрощённой моделью.
Правила drop:
| Цель | Результат |
|---|---|
| Левая сторона главного окна | Пристыковать композицию слева; MainWindow становится host |
| Правая сторона главного окна | Пристыковать композицию справа; MainWindow становится host |
| Центр группы панели | Вложить как вкладку |
| Верх/низ группы | Создать соседнюю группу |
| Левая/правая сторона композиции панели | Создать соседнюю колонку |
| Пустое место | Оставить композицию самостоятельной floating |
Различать жесты:
1. Перемещение всей floating-композиции — двигается её текущее host-окно.
2. Перенос floating-композиции в Main Dock — композиция меняет host на MainWindow; индивидуальные PanelWindow сохраняются и скрываются.
3. Извлечение отдельной панели A из композиции B — A отделяется в новую Floating-композицию и показывается в своём Window A.
4. Перенос панели из Main Dock в floating — Layout создаёт Floating-композицию, а её host выбирается из постоянных окон участвующих панелей.
**Проверка:** A ↔ B, A/B ↔ Main Dock слева/справа, drop на пустом месте, Escape, Undo/Redo; ни один HWND не переназначается другой панели.
**Готово, когда:** все перемещения работают через реальные окна и единый Layout без потери состояния панели.

10. Проверить, что все PanelWindow сворачиваются и закрываются вместе с главным окном; Windows owner остаётся главным HWND при любых перемещениях и сменах host. Не использовать owner как Dock-флаг.
**Готово, когда:** переходы фокуса, отпускание, Escape, закрытие и minimize не оставляют висячих окон, view или history transactions.

## 7. Критерии итоговой приёмки
### Обычный запуск и меню
- При обычном запуске открывается только главное окно с Canvas.
- Ни одна панель не создаётся автоматически.
- Каталог доступных типов панелей доступен в меню `Панели`.
- Включение галочки создаёт ровно один экземпляр выбранного типа.
- Новая панель сразу появляется в собственном отдельном floating-окне.
- Новая панель не появляется сначала в левой/правой области главного Dock.
- Снятие галочки закрывает соответствующий экземпляр и освобождает его окно.
- Галочка остаётся включённой, пока PanelId существует, даже если собственное окно скрыто из-за стыковки/вложения.
### Постоянные окна и переносы
- У каждой открытой панели есть собственный PanelWindow, закреплённый за её PanelId.
- Вложение A в B скрывает окно A, но сохраняет его HWND и EntityId.
- Извлечение A показывает прежнее окно A.
- Объединение композиций не переназначает HWND одной панели другой.
- При стыковке композиции с главным окном её содержимое рисуется MainWindow, а индивидуальные panel windows скрыты, но сохранены.
- Закрытие host-панели безопасно передаёт отображение оставшейся панели до уничтожения закрываемого окна.
- Один и тот же AnyView никогда не рендерится одновременно в двух окнах.
- Неактивные вкладки сохраняют состояние и могут быть извлечены.
### Фокус, геометрия и жизненный цикл
- Переключение фокуса между окнами приложения не прерывает штатный drag.
- Отпускание ЛКМ завершает drag; Escape отменяет его и восстанавливает исходную структуру.
- Resize и DPI работают на нескольких мониторах.
- Minimize/close главного окна не оставляет окон, которые должны были завершить свой lifecycle вместе с приложением.
- Нет висячих WindowHandle, HWND, PanelView и незавершённых history transactions.
