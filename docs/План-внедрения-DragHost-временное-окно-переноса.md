# План внедрения DragHost — временного окна переноса

## 1. Цель

Перестроить механизм tear-off так, чтобы во время перетаскивания Panel, Group, Column или Main DockArea использовалось отдельное временное нативное окно **DragHost**, а постоянные Dock-области не меняли свою структуру до отпускания мыши.

Новая схема должна разделять три роли окон:

| Роль | Назначение | Связь с Core Layout |
|---|---|---|
| **MainHost** | Постоянное главное окно приложения | Отображает Main Dock |
| **FloatingHost** | Постоянное плавающее окно композиции | Связано с конкретной Floating-композицией |
| **DragHost** | Временное окно визуального переноса | Не имеет собственной DockArea и не входит в Layout |

DragHost — это **роль окна на уровне GPUI-адаптера**, а не третья разновидность DockArea и не новая сущность Core.

Для создания временной нативной поверхности можно использовать доступный GPUI-механизм открытия обычного верхнеуровневого окна (в том числе underlying `WindowKind::Floating`, если это требуется API GPUI). Нельзя предполагать, что в GPUI существует отдельный `WindowKind::Dragging`, и нельзя добавлять такой вариант в сторонний тип GPUI.

## 2. Архитектурные правила

1. **Core остаётся единственным владельцем Layout.** В GPUI не создаётся второе дерево Dock-композиции.
2. **DragHost не меняет Layout.** Пересечение drag-порога только запускает временную презентацию исходного объекта в другом окне.
3. **Исходный объект сохраняет свою идентичность.** Panel остаётся Panel, Group остаётся Group, Column остаётся Column. Временное окно не становится источником логической операции.
4. **DragHost не является Floating-композицией.** У него нет `FloatingGroupId`, собственного DockArea, сериализуемого состояния, истории или сохранённой геометрии.
5. **Одна сущность PanelView не должна одновременно монтироваться в двух окнах.** При переносе представление передаётся DragHost, а на исходном месте показывается временная заглушка.
6. **Один drop — одна структурная Core-команда.** Не должно быть цепочки `Float → DockFloating` только ради транспортировки объекта во время drag.
7. **Отмена не требует отката Layout.** До mouse-up структура не меняется; Escape или ошибка закрывают DragHost и возвращают представление на исходное место.
8. **Постоянное Floating-окно остаётся самостоятельным.** Перетаскивание его заголовка/рамки продолжает перемещать само нативное окно и не превращается в DragHost-сессию.
9. **Существующий UI переиспользуется.** DragHost использует те же PanelView и существующие представления Panel/Group/Column, а не создаёт копии содержимого или параллельные реализации компонентов.
10. Все изменения выполняются поэтапно. Устаревший механизм не удаляется, пока новая реализация не прошла сценарии, которые он обслуживал.

## 3. Жизненный цикл перетаскивания

### 3.1. Начало жеста

1. Pointer-down создаёт обычную drag-сессию с исходными `DragPayload`, `DragHandle`, координатой нажатия и исходным Host.
2. До пересечения порога drag остаётся обычным нажатием. DragHost не создаётся.
3. После пересечения порога адаптер фиксирует исходный объект, его Host, прямоугольник, точку захвата и исходное состояние представления.
4. Layout пока остаётся без изменений.

### 3.2. Переход в DragHost

1. Адаптер временно исключает исходное содержимое из отрисовки исходного Host.
2. На месте содержимого остаётся placeholder с тем же логическим прямоугольником. Он не должен сдвигать соседние группы/колонки и менять геометрию Core.
3. Та же самая PanelView/AnyView-сущность передаётся в DragHost. Не создаётся новый экземпляр Panel через factory.
4. DragHost открывается без постоянной Dock-шапки и без собственной Dock-структуры.
5. Нативное окно позиционируется относительно курсора с сохранением точки захвата.
6. DragHost следует за курсором до mouse-up или Escape.

### 3.3. Поиск цели

1. По экранной координате курсора определяется целевой HWND среди MainHost и зарегистрированных FloatingHost.
2. HWND самого DragHost обязательно исключается из поиска цели. Иначе визуальное окно перетаскивания может закрыть от hit-test реальное окно назначения.
3. Экранная координата переводится в локальную систему координат найденного целевого окна.
4. Core Resolver вызывается для Layout и геометрии именно этого целевого окна.
5. DragHost показывает обратную связь по результату Resolver. UI не вычисляет зоны самостоятельно.
6. Если курсор находится вне Main/Floating-окон, целевая зона считается свободной областью.

### 3.4. Завершение

При mouse-up выполняется ровно один из вариантов:

- **Drop в MainHost:** исходный объект напрямую перемещается в выбранную цель Main.
- **Drop в FloatingHost:** исходный объект напрямую перемещается в выбранную цель Floating.
- **Drop в свободной области:** Core-команда `Float` создаёт постоянную Floating-композицию из исходного объекта.
- **Drop в недопустимую цель:** операция отменяется либо обрабатывается как свободный drop согласно согласованным правилам. Недопустимое состояние не должно частично менять Layout.
- **Escape / системная отмена:** Layout остаётся прежним, PanelView возвращается в исходный Host.

После завершения DragHost закрывается, runtime-сессия очищается, а представление монтируется ровно в одном конечном Host.

## 4. Границы между DragHost и существующим FloatingHost

DragHost нужен для переноса **содержимого** из одного DockHost в другой: Panel, Group, Column и Main DockArea, если жест начат на её управляющей области.

Не следует переводить в DragHost операции, которые уже являются перемещением целого постоянного Floating-окна:

- перетаскивание заголовка FloatingHost;
- перемещение всей Floating-композиции как одного нативного окна;
- изменение положения/размера существующего FloatingHost.

Эти операции продолжают использовать текущий native move/resize механизм.

Если пользователь начинает переносить Panel/Group/Column, находящуюся внутри FloatingHost, это уже перенос подструктуры. Для такого жеста применяется DragHost, а исходный FloatingHost остаётся на месте с placeholder.

## 5. Runtime-модель адаптера

Названия ниже предварительные. Точные структуры фиксируются на первом этапе после сверки текущих типов и API GPUI.

### 5.1. Роль окна

В GPUI-адаптере вводится собственное различие ролей, например:

- `Main`;
- `Floating { group: FloatingGroupId }`;
- `Dragging { id: DragHostId }`.

Это описание назначения окна, а не замена Core-модели. Для Dragging используется отдельный временный идентификатор `DragHostId`, который не сохраняется в workspace и не попадает в Core Layout.

### 5.2. DragHostManager

Предпочтительно отделить управление временными DragHost от `FloatingWindowManager`:

- `FloatingWindowManager` продолжает владеть постоянными FloatingHost;
- новый `DragHostManager` отвечает за создание, показ, позиционирование и закрытие временных DragHost;
- единая маршрутизация окон знает MainHost, FloatingHost и временные DragHost, но при поиске drop-цели исключает DragHost.

**Решение по владению:** `DockHost` владеет `DragHostManager` как отдельной GPUI-сущностью, на одном уровне с `FloatingWindowManager`. Оба менеджера получают одну и ту же `Entity<DockController>`. DragHostManager не вкладывается в FloatingWindowManager, не владеет Layout, PanelRegistry или отдельными экземплярами PanelView и не создаёт параллельную модель.

### 5.3. Данные DragHost-сессии

Runtime-сессия должна хранить как минимум:

- исходный `DragPayload` и `DragHandle`;
- исходный Host и его WindowId;
- исходный прямоугольник и точку захвата;
- текущую экранную позицию курсора;
- DragHostId, WindowId и native HWND временного окна;
- состояние передачи представления;
- текущую цель/drop-зону;
- признак активной/завершающейся/отменённой сессии.

Не нужно дублировать в этой структуре дерево Layout или данные, которые можно безопасно получить из единого DockController.

### 5.4. Состояния сессии

Предлагаемая последовательность:

`Idle → Pressed → PreparingDragHost → Dragging → ResolvingDrop → Committing → Finished`

Ветка отмены:

`PreparingDragHost / Dragging / ResolvingDrop → Cancelling → Restored`

Каждый переход должен быть идемпотентным: повторный mouse-up, Escape или закрытие окна не должны дважды применить команду или вернуть одну PanelView одновременно в два места.

## 6. План внедрения по этапам

Каждый этап выполняется отдельно. После него пользователь запускает локальные проверки и присылает результат. К следующему этапу переходим только после подтверждения.

## Этап 2. Создать и закрывать пустое временное нативное окно

**Цель:** изолированно проверить жизненный цикл DragHost до переноса реального содержимого.

Основная область:

- `drag_host_manager.rs`;
- `drag_host.rs`;
- `lib.rs`;
- при необходимости отдельная небольшая точка интеграции в `app_shell.rs` или `dock_host.rs`.

Реализовать:

1. Создание временного верхнеуровневого окна без Core Layout.
2. Скрытое создание и позиционирование до первого показа, чтобы избежать мерцания.
3. Показ без нежелательной активации/перехвата фокуса, если это допускает текущий native backend.
4. Перемещение окна по экранным координатам с сохранением точки захвата.
5. Закрытие и освобождение native ресурсов.
6. Защиту от повторного создания второй DragHost в одной активной drag-сессии.
7. Обработку ошибок создания, позиционирования, показа и закрытия.

Особое требование: при поиске окна под курсором DragHost не должен считаться целью. Нужно проверить реальный Win32 hit-test на фоне MainHost и нескольких FloatingHost. Если стандартный поиск возвращает DragHost, маршрутизация должна искать следующее подходящее зарегистрированное окно, а не отправлять drop в DragHost.

**Не делать:** пока не переносить PanelView и не менять Core.

**Фактически внедрено:**

- Добавлен отдельный `drag_host_manager.rs`. Менеджер создаёт не более одного временного окна за раз и не обращается к Core Layout.
- DragHost создаётся скрытым через GPUI `WindowKind::Floating`, получает MainHost как native owner, скрывается из панели задач, позиционируется и изменяет размер до первого показа.
- Первое позиционирование и точка захвата пересчитываются с учётом DPI монитора, на котором оказался HWND. Показ выполняется через `show_no_activate`.
- Добавлены операции `open_at_cursor`, `move_with_cursor`, `close`, получение роли по GPUI `WindowId` и внутреннее получение HWND активного DragHost для передачи в native hit-test как исключаемого окна.
- `DockHost` владеет менеджером как отдельной GPUI-сущностью рядом с `FloatingWindowManager`; оба получают один `DockController`.
- Новый менеджер и его ошибка экспортированы из `dock-gpui`.
- В `platform::NativeWindowOps::window_from_point` уже есть параметр `exclude`: Win32 реализация пропускает исключённый HWND и продолжает обход видимых верхнеуровневых окон по Z-order. Добавлен тест перекрытия DragHost над двумя FloatingHost и MainHost: после исключения DragHost выбирается верхний зарегистрированный DockHost под ним.

**Пока не подключено:** новый pointer/drop pipeline ещё не передаёт HWND активного DragHost в `window_from_point`. Для этого сначала нужно ввести отдельную DragSession и транспорт содержимого; подключение маршрутизации и проверка реального hit-test с открытыми Main/Floating окнами остаются в соответствующих последующих этапах. Старый `begin_native_tearoff`, `DockCommand::Float` и существующий drop lifecycle не менялись.

**Проверка:** пользователь подтвердил успешное прохождение локальных проверок этапа 2. Интерактивная проверка реального Win32 hit-test остаётся на этапе 6, когда DragHost будет подключён к drop routing.

## Этап 3. Описать единый runtime DragSession с исходным Host и транспортным Host

**Цель:** хранить логический источник отдельно от окна, которое его временно показывает.

Основная область:

- `input_drag.rs`;
- `controller.rs`;
- новый `drag_host.rs`;
- новый `drag_host_manager.rs).

Сделать:

1. Сохранить исходные `DragPayload` и `DragHandle` на всю сессию.
2. Отдельно сохранить исходный Host и временный DragHost.
3. Не восстанавливать тип источника по корню временной поверхности.
4. Разделить жесты:
   - содержимое Panel/Group/Column/DockArea — потенциальный DragHost;
   - заголовок существующего FloatingHost — перемещение этого окна;
   - resize существующего FloatingHost — текущая resize-сессия.
5. Ввести явные операции начала, завершения и отмены DragHost-сессии.
6. До завершения этапа оставить старый маршрут tear-off рабочим и включать новые состояния только в изолированном прототипе.

**Фактически внедрено:**

- В `drag_host.rs` добавлены `DragSourceHost` и `DragHostSession`. Сессия хранит исходные `DragPayload` и `DragHandle` отдельно от источника (`Main` или `Floating { group }`) и транспортного `DragHostId`.
- `DragController` хранит runtime-контекст рядом с Core `DragSession`, но не меняет Core-модель.
- Main-host content drag создаёт сессию с источником `Main`; floating tab drag — с источником конкретной `FloatingGroupId`.
- `DragHostManager` привязывает активный `DragHostId` как транспортный Host при открытии окна и снимает ссылку при закрытии.
- `continue_tearoff_drag` перезапускает только Core DragSession и сохраняет исходный runtime-контекст. Обычный FloatingTitle move и resize не создают content-drag session.
- Завершение drop, native tear-off и отмена явно очищают runtime-сессию. Legacy `begin_native_tearoff` и `DockCommand::Float` остаются рабочим маршрутом; новая передача содержимого ещё не включена.

**Критерий готовности:** runtime-модель хранит исходный объект и Host независимо от временного окна; старый drag lifecycle продолжает работать.

## Этап 4. Передать PanelView в DragHost и показать placeholder в источнике

**Цель:** доказать безопасное перемещение существующего UI между окнами без мутации Layout.

Начать только с одной Panel.

Основная область:

- `controller.rs` и существующий `PanelViewCache<AnyView>`;
- `dock_host.rs`;
- `floating_manager.rs` — только для согласования доступа к общему кешу, не для владения DragHost;
- `drag_host.rs` и `drag_host_manager.rs`;
- `dock-components/panel_content.rs` и `dock-components/tab.rs`, если понадобится точка представления.

Последовательность передачи:

1. Исходный Host получает состояние «Panel временно переносится».
2. Исходная PanelView перестаёт добавляться в обычное дерево отрисовки.
3. На прежнем месте появляется placeholder с прежним прямоугольником и размерами.
4. Только после исключения из исходной отрисовки та же AnyView/Entity передаётся в DragHost.
5. DragHost показывает содержимое без постоянной ColumnHeader/Floating-шапки.
6. На возврате выполняется обратная последовательность: сначала DragHost прекращает показывать PanelView, затем целевой Host получает её и placeholder убирается.

Не запускать factory повторно. Не создавать вторую PanelView для drag-preview. Не менять `PanelId`, `NodeId` или Core Layout.

Проверить на реальной панели с состоянием: текстовый ввод, локальное состояние Entity, фокус и повторное перемещение между окнами.

**Критерий готовности:** одна PanelView визуально переезжает в DragHost и обратно; на исходном месте нет дублирующего содержимого; Layout и его версия не изменяются от начала drag до drop.

## Этап 5. Добавить атомарный Core-перенос исходного узла в цель Main/Floating

**Цель:** заменить промежуточную последовательность `Float → DockFloating` одной структурной операцией в момент mouse-up.

Это отдельный Core-этап, который можно тестировать без GPUI DragHost.

Сначала изучить текущие `DockCommand`, `resolve_drag_drop`, `apply_dock_floating_command`, `dock_floating_group`, detach/insert операции и модель владельцев DockArea.

Требование к новой операции:

- принимает исходный логический узел (или однозначный Panel/Node source) и целевую DropTarget;
- умеет переместить исходный узел из Main в Main;
- умеет переместить исходный узел из Main во Floating;
- умеет переместить исходный узел из Floating в Main;
- умеет переместить исходный узел из одного Floating в другой Floating;
- сохраняет внутреннюю структуру переносимого поддерева;
- удаляет опустевшие исходные структуры по существующим правилам Core;
- валидирует источник, цель, ограничения профиля и допустимость операции до мутации;
- при ошибке не оставляет Layout частично изменённым;
- создаёт одну корректную undo-операцию.

Название команды не фиксировать заранее. Возможные направления — обобщённая команда перемещения узла в DropTarget либо отдельная операция DockNodeToTarget. Выбрать минимальное решение, соответствующее существующим Core-абстракциям.

Для свободной области остаётся отдельная команда `Float`, но вызывать её нужно только при финальном отпускании мыши.

Не подменять перенос узла операцией `DockFloating`: эта команда предназначена для уже существующей Floating-композиции. Также не вводить новую Core-сущность DragHost.

**Тестовые случаи Core:**

- Panel Main → Group Main/Floating;
- Panel Floating → Group Main/другого Floating;
- Group Main/Floating → Group Main/Floating;
- Column Main/Floating → допустимая Column-композиция Main/Floating;
- перенос с удалением исходной пустой Group/Column;
- перенос с сохранением порядка Tabs/Groups/Columns;
- отклонение запрещённой цели без изменения Layout;
- undo возвращает исходную структуру.

**Критерий готовности:** один прямой Core-вызов выполняет перенос между любыми допустимыми DockArea; промежуточный FloatingGroup не требуется.

## Этап 6. Реализовать маршрутизацию drop-целей во время работы DragHost

**Цель:** DragHost следует за курсором, но drop вычисляется относительно реального целевого MainHost/FloatingHost.

Основная область:

- `drag_host_manager.rs`;
- `floating_manager.rs`;
- `input_drag.rs`;
- `controller_layout_cache.rs`;
- `controller.rs);
- `dock_host.rs).

Реализовать:

1. Получать экранную позицию курсора.
2. Находить целевое окно среди Main/Floating, исключая DragHost и исходное окно в тех случаях, когда оно не должно быть целью.
3. Преобразовывать координаты экрана в локальные координаты целевого окна с учётом scale factor.
4. Получать геометрию и resolver именно целевого окна.
5. Передавать исходный DropSource без реконструкции по временному Host.
6. Обновлять выбранную DropTarget во время движения.
7. Сохранять независимые cache/geometry snapshots для каждого целевого окна.
8. При выходе за все окна определять FreeArea и вычислять экранные bounds будущего FloatingHost.

DragHost только показывает визуальный preview. Он не является целью стыковки.

**Критерий готовности:** при движении поверх нескольких окон подсветка соответствует реальному Main/Floating окну под курсором; координаты и resolver не путаются между окнами.

## Этап 7. Подключить DragHost для перетаскивания одной Panel

**Цель:** закончить полный жизненный цикл на самом простом типе источника.

Подключить новую схему сначала к Main-host tab drag, затем к tab drag из FloatingHost.

Основная область:

- `input_drag.rs`;
- `dock_host.rs`;
- `floating_manager.rs) — только для определения исходного FloatingHost;
- `dock-components/tab.rs);
- `controller.rs);
- Core-команда из этапа 5.

Сценарии:

1. Panel Main → другая Group Main.
2. Panel Main → Group Floating.
3. Panel Main → FreeArea (создаётся постоянный FloatingHost только на отпускании).
4. Panel Floating → Group Main.
5. Panel Floating → Group другого Floating.
6. Panel Floating → FreeArea (новая отдельная Floating-композиция на отпускании).
7. Panel → собственная исходная Group: no-op либо корректное сохранение исходного положения.
8. Escape до отпускания: PanelView возвращается в источник без изменения Layout.

Старая ветка `begin_floating_tab_tearoff` больше не должна создавать FloatingGroup на пороге для этих сценариев. Удалять её разрешено только после подтверждения всех перечисленных вариантов.

**Критерий готовности:** Panel переносится через DragHost между всеми четырьмя сочетаниями Main/Floating; свободный drop создаёт FloatingHost только в конце; состояние и фокус PanelView сохраняются.

---

## Этап 8. Расширить DragHost на Group, Column и Main DockArea

**Цель:** подключить остальные структурные источники без изменения общей механики.

Выполнять внутри этапа последовательно, не все типы сразу.

### 8.1. Group

- источник — `DragPayload::Group`, `DragHandle::GroupGrip`;
- placeholder сохраняет геометрию всей Group;
- DragHost показывает все вкладки/PanelView группы;
- drop сохраняет порядок Tabs;
- проверить Main → Main, Main → Floating, Floating → Main, Floating → Floating и FreeArea.

### 8.2. Column

- источник — `DragPayload::Column), `DragHandle::ColumnHeader`;
- placeholder сохраняет полную высоту/ширину Column;
- DragHost показывает все группы и панели Column;
- drop переносит Column как единое поддерево;
- проверить Photoshop-ограничения для горизонтального объединения целых Column-композиций;
- не превращать перенос Column в набор независимых переносов Group.

### 8.3. Main DockArea

- источник — `DragPayload::DockArea), `DragHandle::DockAreaHeader`;
- placeholder занимает прежнюю область;
- DragHost показывает всю переносимую композицию;
- FreeArea создаёт Floating из корня DockArea только на release;
- стыковка в Main/Floating выполняется одной структурной командой, если текущая Core-модель разрешает такую операцию.

Весь этап должен переиспользовать общую сессию и DragHostManager. Для каждого типа источника не создавать отдельный менеджер или отдельный механизм native move.

**Критерий готовности:** Panel, Group, Column и Main DockArea используют один жизненный цикл DragHost; каждый тип сохраняет свою идентичность и переносится как ожидаемая структурная единица.

---

## Этап 9. Обработать отмену, ошибки, undo и передачу фокуса

**Цель:** сделать сессию безопасной при любом прерывании.

Проверить:

- Escape до создания DragHost;
- Escape сразу после его создания;
- Escape во время движения между окнами;
- mouse-up над исходным местом;
- mouse-up вне всех окон;
- mouse-up над недопустимой зоной;
- ошибка создания или показа DragHost;
- ошибка передачи AnyView;
- ошибка resolver;
- ошибка финальной Core-команды;
- закрытие исходного или целевого окна во время сессии;
- повторный mouse-up или повторное событие отмены;
- потеря фокуса приложения/отпускание кнопки мыши за пределами окна.

Обязательные гарантии:

1. До финальной команды Layout не меняется.
2. При отмене возвращается та же PanelView/Entity.
3. Одна PanelView никогда не отображается в двух Host одновременно.
4. DragHost всегда закрывается при завершении/отмене.
5. Runtime-регистры не содержат ссылок на уже закрытые WindowId/HWND.
6. Успешный drop создаёт одну undo-запись; отмена не создаёт undo-запись.
7. После ошибки исходное содержимое остаётся доступным.

**Критерий готовности:** все пути завершения сессии приводят к одному консистентному состоянию; нет потерянных панелей, зависших окон и двойных применений Core-команд.

---

## Этап 10. Удалить старый tear-off через временный Floating и завершить матрицу

**Цель:** удалить только ту старую логику, которая действительно заменена DragHost.

После прохождения этапов 0–9 пересмотреть и по одному удалить/упростить:

- вызов `DockCommand::Float` при пересечении drag-порога в `begin_native_tearoff`;
- промежуточную tear-off transaction, если она больше не нужна для нового жизненного цикла;
- `begin_tearoff_move` и `begin_floating_tab_tearoff_move) в части транспортировки содержимого;
- ветки, которые трактуют временный FloatingGroup как транспортный Host;
- специальные обходы, добавленные только из-за того, что источник уже был временно преобразован в Floating.

Не удалять автоматически:

- `DockCommand::Float` как финальную операцию создания постоянного Floating;
- `DockCommand::DockFloating` для стыковки уже существующей Floating-композиции;
- native move/resize текущих FloatingHost;
- `FloatingWindowManager` и его реестр постоянных окон;
- общие механизмы resolver, geometry cache и DropOverlay.

### Итоговая матрица

| Источник | Цель | Ожидаемый результат |
|---|---|---|
| Panel Main | Group Main | Прямой перенос Panel |
| Panel Main | Group Floating | Прямой перенос Panel |
| Panel Floating | Group Main | Прямой перенос Panel |
| Panel Floating | Group другого Floating | Прямой перенос Panel |
| Group Main/Floating | Group Main/Floating | Перенос Group целиком |
| Column Main/Floating | допустимая Column Main/Floating | Перенос Column целиком |
| Main DockArea | Main/Floating или FreeArea | Перенос всей композиции |
| Любой поддерживаемый подузел | FreeArea | Один Float на release |
| Любой поддерживаемый подузел | Escape | Возврат в исходный Host, Layout без изменений |
| Заголовок существующего FloatingHost | Любая позиция | Перемещение самого HWND без DragHost |

Дополнительно проверить:

- повторный drag после каждого успешного переноса;
- сохранение активной вкладки и состояния PanelView;
- фокус и работу TextInput после перемещения;
- отсутствие мерцания при создании/закрытии окон;
- отсутствие ложных drop-зон на DragHost;
- корректную работу на нескольких мониторах и при разном scale factor;
- отсутствие незакрытых временных окон после закрытия приложения.

**Критерий готовности:** все поддерживаемые сценарии проходят локальную проверку, а старый механизм временного Float больше не участвует в транспортировке подузлов.

Не нужно заранее создавать все перечисленные файлы или переносить код между ними. Сначала подтверждаем границы ответственности, затем меняем только файлы текущего этапа.

## 8. Что не меняем

- Core не получает третью разновидность DockArea.
- DragHost не сериализуется и не сохраняется в workspace.
- Не вводится второе дерево Layout на стороне GPUI.
- Не создаётся новая PanelView через registry factory ради drag.
- Не меняется логика перемещения заголовка уже существующего FloatingHost.
- Не переписывается вся система DropTarget или DropOverlay без необходимости.
- Не меняются правила Photoshop для допустимых структурных стыковок вне требований прямого переноса.
- Не удаляется текущая рабочая реализация до прохождения соответствующего этапа новой.
- Не запускаются сборки и тесты вместо пользователя.

## 9. Порядок совместной работы

1. Начинаем с Этапа 0 и фиксируем только карту текущего кода.
2. Перед каждым этапом я сначала указываю конкретные файлы и минимальный объём изменений.
3. Не объединяем несколько этапов в один большой рефакторинг.
4. Работаем в текущей ветке `main`; новые ветки самостоятельно не создаём.
5. После изменений пользователь выполняет локальные проверки и присылает результат.
6. Следующий этап начинаем после подтверждения предыдущего.
7. Если в ходе этапа выясняется, что архитектурное предположение неверно, сначала корректируем план этого этапа, а не маскируем проблему дополнительными временными командами.

Документ `docs/План-переделки-docking-перетаскивание-и-стыковка.md` описывает прежний механизм, в котором после пересечения drag-порога исходный узел временно превращается в Floating-композицию.
